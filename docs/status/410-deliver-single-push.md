# #410 deliver 의 진행 원장 갱신 푸시를 없애 PR 푸시를 한 번으로 (2026-10-21)

## 문제

`/harness:deliver` 는 PR 을 만든 뒤 진행 원장을 `리뷰`·`#PR번호` 로 고쳐 `docs: 진행 원장 갱신` 커밋을 한 번 더 푸시했다. 이 두 번째 푸시가 `synchronize` 이벤트로 Actions 검사 7개를 통째로 다시 돌려, Actions 분(job 개수로 과금)이 PR 하나당 두 배가 됐다.

## 결정

- 방법 (1) 을 골랐다: 푸시 전에 다음 PR 번호를 예측해 원장을 고치고 첫 푸시에 담는다. 번호는 `gh api repos/<repo>/issues?state=all&sort=created&direction=desc&per_page=1` 의 최신 번호 + 1 이다(issues 끝점은 PR 도 포함하므로 이슈·PR 공통 번호열).
- (2)(마지막 PR 칸을 병합 때 Actions 가 채움)를 고르지 않은 이유: 마지막 PR 칸은 코드가 읽지 않고 `ledger_complete.py` 가 병합 때 덮어쓸 뿐이다. 다만 리뷰 중인 사람이 PR 을 찾는 데 쓰므로, 비워 두는 (2) 보다 처음부터 채워 두는 (1) 이 낫다. Actions·다른 하네스 코드는 바뀌지 않는다.
- `deliver/SKILL.md`: 푸시(옛 8단계) 앞에 원장 갱신 단계를 새 8단계로 두고, 옛 10단계(PR 뒤 원장 푸시)는 "PR 을 만든 뒤 예측과 실제 번호 비교"(11단계)로 바꿨다. 이후 단계 번호를 하나씩 밀고 "병합 순서 기록" 의 단계 참조를 고쳤다.
- 이미 PR 이 있는 브랜치(갱신)는 예측하지 않고 원장 번호가 그 PR 번호와 같은지만 확인한다.
- `완료` 행 처리는 그대로(상태는 덮지 않고 마지막 PR 만, 되돌릴지 묻기).
- 길잡이 deliver 탭 흐름 그림의 순서를 "원장 갱신 → 푸시 한 번 → PR(번호 확인)" 으로 고쳤다. plugin.json 0.10.101.

## 경쟁 조건과 fallback

예측과 PR 생성 사이에 다른 사람이 이슈·PR 을 만들면 번호가 어긋난다(드묾). PR 을 만든 뒤 실제 번호와 비교해 다르면 원장을 고쳐 `docs: 진행 원장 갱신` 커밋을 하나 더 만들고 다시 푸시한다. 이때만 푸시가 두 번이다. 같으면 아무것도 하지 않는다.

## 알려진 한계

- 불일치 시 두 번째 푸시가 여전히 검사를 다시 돌린다. 예측이 틀릴 확률을 낮추는 방법(번호 예약 등)은 구현하지 않았다.
- 스킬 문서는 절차 지시라 새 자동 시험이 없다. public-cloud PR 로 푸시가 실제 한 번만 나가는지는 병합 뒤 확인이 필요하다.
