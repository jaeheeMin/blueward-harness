# #742 올린 매뉴얼 pptx 를 작업본으로 읽어 들이기

## 배경
매뉴얼을 개발 전에 먼저 쓰는 사람은 고객 양식 pptx 에 실제 데이터로 직접 써서 올린다. 지금까지는 작업본(md) → pptx 산출(`checker.export_pptx`)만 있어, 올린 pptx 를
작업본으로 되돌릴 길이 없었다. 매뉴얼 먼저 쓰기·시험 흐름 4건 중 둘째다(#741 설명 보충 → #742 pptx 읽어 들이기 → #743 조회 시험 → #744 끝까지 시험).

## 조사 결론
- 지도의 `찾기` 는 견본 쪽의 **예시 글자** 앞부분 일치라 사람이 데이터로 바꾼 pptx 에서는 쓸 수 없다.
- 대신 견본 쪽에서 `_Locator` 로 칸 도형의 위치(왼쪽·위)를 얻고, 올린 pptx 에서 같은 위치(허용 오차 안)의 도형 글을 읽는다. 이미 산출된 Production 매뉴얼 6개(표지·목차·본문·번호
  설명·그림 124항목)가 원본 작업본과 같았다.
- 함정: 쪽 번호 필드(`a:fld`)를 가진 도형이 번호 설명 번호 조건(`왼쪽_이상`, 숫자 글자)을 통과한다 → 제외. 번호 설명 짝은 견본 간격이 아니라 번호 도형 오른쪽·같은 높이의 가까운 글상자로 잡는다.

## 바꾼 것
- `checker/import_pptx.py` 새 모듈: `python -P -m checker.import_pptx --pptx <올린 pptx> --root <저장소> [--form <양식>] [--dev DEV-001,…] [--check]`. 종료코드 0 `ok` / 1 `incomplete`(`missing`·`unmapped`) /
  2 `error`(아무것도 안 씀). 지도 고르기·검증은 `export.load_map`/`validate_map` 을 재사용했다. 파일명 틀(`산출.파일명`)을 거꾸로 써서 자리 값과 판을 읽고, 작업본은 `산출.폴더` 의
  자리를 채운 폴더에, 그림은 캡처 도구와 같은 `docs/manual/img/<작업본 폴더 이름>/<화면 제목>_v<판>.<확장자>` 에 쓴다. 쓴 작업본에 `rules/` 문서 검사를 돌려 `doc_guard` 로 싣는다.
  `--dev` 를 주면 `## 묶은 개발 건` 표를 채운다(형식이 틀리면 2).
- `checker/tests/test_import_pptx.py` 시험 41개: 왕복(작업본·그림 바이트 같음, 다시 산출하면 글자 같음), 칸 조금/크게 옮김, 메모 글상자, 칸 지움, 여러 줄, 쪽 번호 필드, 쪽당_최대로 넘어간 쪽 합치기,
  다른 pptx(쪽 크기·칸 안 맞음), 이미 있는 작업본·그림, `/` 가 든 화면 제목, `--check`, 매뉴얼 규칙으로 문서 검사, `--dev`, 작업본 이름 자리, 위험한 자리 값, 파일명 분할 모호함,
  칸을 다 지운 본문 쪽, 양식 고정 글 제외, 읽지 못하는 그림.
- 독립 검토(reviewer) 지적으로 고친 것: 자리 이름 하드코딩 제거(작업본 이름 자리는 `산출.작업본_자리` 또는 파일명 자리에서 유도, 못 정하면 2 — `form-map.md` 에 키 문서화),
  파일명 자리 값에 `..`·예약 이름·금지 문자 검사, 파일명이 여러 방식으로 갈라지면 2, 칸 있는 쪽이 후보에 섞이면 끝 쪽으로 추측하지 않고 2, 양식 고정 글을 번호 설명 후보에서 제외,
  읽지 못하는 그림은 쓰지 않고 `미정`.
- `plugins/harness/skills/manual/SKILL.md` 에 "올린 pptx 읽어 들이기" 절, 머리말 한 줄, description 에 읽어 들일 때를 더했다. `docs/guide/harness-guide.html` 사용자 매뉴얼 탭에 안내.
- `workflow.json` 은 manual 근거 quote(`사용자 매뉴얼(고객 양식 pptx)을 쓰거나 고칠 때`)가 그대로 남아 있어 바꾸지 않았다. 새 스킬이 아니라 순서 항목도 더하지 않았다.

## 판단
- **넣은 값·기대 결과 자리는 #743 으로.** 사람은 데이터를 번호 설명 글 속에 쓰므로 #743 에서 Claude 가 설명·그림으로 시험 목록(`capture.yaml`)을 만들고 사람이 확인한다. 작업본 형식은 바꾸지 않았다.
- 실제 사람이 쓴 pptx 샘플이 없어 양식 모양 pptx 를 코드로 만들고 사람이 손댈 만한 변형을 시험했다. 실제 산출된 Production 6개(+ v0.2 1개)는 읽어 작업본·그림이 원본과 같은 것을 한 번 확인했다
  (시험 파일에는 넣지 않았다 — 고객 양식 파일은 저장소에 두지 않는다).
- 쪽 분류는 견본 칸 위치와 맞는 정도다. 절반을 넘게 맞는 쪽이 하나로 가려지면 확실한 쪽으로 보고, 나머지(칸이 일부 지워진 쪽, 칸 없는 끝 쪽)는 앞뒤 확실한 쪽의 순서 사이에서 하나로 정한다.
  하나로 못 정하거나 지도 순서와 다르면 2(읽지 못함)다.
- 지도가 안 가리킨 글은 `unmapped` 로 알린다. 견본에 있던 같은 글·같은 자리의 글(양식 고정 문구)은 사람이 쓴 글이 아니므로 알리지 않는다. 견본의 예시 글·예시 그림이 그대로면 쓴 것이 아니라 `missing` 이다.
- `## 묶은 개발 건` 은 스킬이 먼저 DEV 를 물어 `--dev` 로 넘긴다. 모르면 `| 미정 | 미정 |` 로 쓰고, 이는 `rules/manual.yaml` 의 `md_table` 패턴(`DEV-\d{3,}`)에 위반이다(`doc_guard.status: violation`).
  규칙 파일은 바꾸지 않았다. 읽기 종료코드는 이 위반과 무관하고, 대신 `next` 와 스킬에 "종료 0 이어도 `doc_guard` 가 `pass` 가 아니면 통과가 아니다" 를 적었다.
- 그림 폴더는 지도로 정할 수 없어 캡처 도구(`manual_capture.image_rel`)의 규칙(작업본 폴더 이름)을 따랐다.
