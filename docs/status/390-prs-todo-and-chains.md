# #390 `/harness:prs` 출력을 할 일 표와 줄기 표로 (2026-10-20)

#370 의 PR 표는 PR 한 줄에 순서·상태(긴 승인 사유 포함)·다음 할 일·먼저 병합할 PR 을 담아, 열린 PR 이 32개인 저장소(public-cloud)에서 읽기 어려웠다. "PR 목록" 이 아니라 "내가 할 일" 로 보이게 사람용 출력만 바꿨다. 계산(`classify`·`compute`·병합 순서), `--json`, `--pr` 출력은 그대로다. 0.10.96.

## 결정

- **할 일 표**(`--mine` 만, 내 PR 만): `병합하기` = 상태가 병합 가능이고 앞 PR 이 없음(사람이 GitHub 에서 병합이면 그 말을 덧붙임). `고치기` = 검사 실패·충돌·base 뒤처짐·병합 막힘·검사 불안정·확인 불능, 그리고 순서 판정 불능(순환 등). `기다리기` = 승인 대기·검사 중·검사 시작 전·충돌 여부 확인 중·초안, 그리고 병합 가능이지만 앞 PR 이 있는 것("앞 [#n] 대기"). 병합하기, 고치기, 기다리기 순으로 정렬한다. `—` 뒤 사유는 승인자 이름들·실패한 검사 이름·"앞 [#n] 대기"·"검사 중" 같은 한 구다. 병합하기·고치기가 하나도 없으면 "지금 할 수 있는 일: 없음(모두 기다리는 중)" 을 표 위에 둔다.
- **기호**는 기존 state 에서 옮긴다: ✅ 병합 가능 · ⏳ 승인 대기·검사 중·검사 시작 전·충돌 여부 확인 중 · ❌ 검사 실패·충돌·base 뒤처짐 · 📝 초안 · ❓ 병합 막힘·검사 불안정·확인 불능과 순서 판정 불능(순환 등). 새 상태는 만들지 않았다. 병합 가능이지만 앞 PR 이 있는 PR 도 줄기 표에서는 ✅ 다(앞 PR 대기는 순서가 보여 주고, 할 일 표에서 기다리기로 나온다).
- **줄기 = DEV 번호 그룹**. 처음에는 `after` 로 이어진 연결 성분을 줄기로 했으나, 실제 public-cloud 에서 #316 의 `먼저: #244, #312` 한 줄 때문에 DEV-007·DEV-009·결함 PR 이 한 덩어리로 합쳐졌다. 그래서 번호로 묶는다.
- **PR 의 번호**: `compute` 가 항목에 두 필드를 **추가**한다(`--json` 의 기존 필드 값은 불변). `devs` = 엔진의 `_dev_numbers`(제목·브랜치·본문·`docs/spec/DEV-xxx-*.md` 파일에서 읽은 번호 전부, 정렬). `dev` = 그중 줄기용 번호 하나(`_primary_dev`): 제목 끝 `(DEV-xxx)`·`[DEV-xxx]` > 제목 맨 앞 번호 > 브랜치 > 바꾼 Spec 파일(여럿이면 작은 번호) > 본문에서 처음 나온 번호. `devs` 가 하나면 그 번호다. 둘 이상일 때 "가장 작은 번호" 로 하지 않은 이유: 결함 PR 본문이 "DEV-006 앱에서 DEV-007 과 같은 결함" 처럼 다른 번호를 언급해(public-cloud #252·#264 는 `devs` 가 [6, 7] 인데 Spec 파일은 DEV-007) 작은 번호가 틀렸다. `render` 는 `dev` 를 쓰고, `dev` 가 없는 항목이면 제목·브랜치 번호, 없으면 `devs` 의 가장 작은 번호로 물러난다.
- **줄 만들기**: 그룹 안에서만 "앞 PR 을 거친 가장 긴 길이(깊이)" 가 같은 PR 을 한 칸으로 묶어 `→` 로 잇고, 칸에 둘 이상이면 `(#a, #b)`. 순서를 정하지 못한 PR(순환·순환 뒤 대기)은 줄 끝에 따로 묶는다. **그룹 밖의 앞 PR** 은 줄을 합치지 않고 그 PR 뒤에 꼬리표로 단다: `[#316] ⏳(앞: [#244])`.
- **번호가 없는 PR**(`dev` 없음)은 번호 없는 PR 끼리 앞 PR 관계로 이어진 묶음 단위로 본다. 묶음이 닿는(앞뒤 이웃) DEV 그룹이 하나뿐이면 묶음 전체가 그 그룹에 들어간다(전이적). 둘 이상에 닿거나 하나도 안 닿으면 따로 두고, 둘 이상 PR 이면 맨 앞 PR 제목 28자를 이름으로 한 줄, 혼자면 "줄기 없음" 한 줄에 꼬리표와 함께 ` · ` 로 나열한다(맨 아래). PR 하나뿐인 DEV 그룹도 "줄기 없음" 이다.
- **줄기 이름** `DEV-xxx(제목)`, 제목은 24자: ① 제목 끝이 `(DEV-xxx)` 인 PR 이 있으면 그 제목에서 `feat: ` 같은 접두어와 `(DEV-xxx)`(앞머리의 `DEV-xxx ` 포함)를 뗀 것, ② 없으면 `DEV-xxx` 뒤 문구를 ` Spec`·` SRS`·`·`·` 에 ` 앞에서 자른 것, ③ 없으면 줄기에서 가장 먼저인 PR 의 제목(접두어 뗌), ④ 그것도 비면 번호만.
- **REQ-n 도 같은 번호**로 DEV 줄기에 묶이고 이름은 `DEV-00n` 으로 보인다(기존 `_DEV_REF` 동작, REQ-n == DEV-n).
- **이름 경계**: 제목 끝 표기는 `(DEV-004)`·`[DEV-004]`·`(DEV-004, DEV-005)`(앞 번호가 줄기 번호) 뒤에 `.` 가 와도 잡는다. ①·② 에서 `Spec`·`SRS` 로 시작하는 문구는 이름으로 쓰지 않고 다음 PR 로 넘어가며, ② 의 양끝 `,.` 는 뗀다.
- **상태 주의(원칙 7)**: PR 상태에 붙은 주의(예: 사람이 병합할 경로인지 확인 불능)가 있는 PR 은 줄기 표에서 기호 뒤에 `⚠` 를 붙이고, 표 바로 아래에 `주의: [#n](url) …` 줄을 `--verbose` 없이도 낸다(`--all` 과 `--mine` 줄기 속 남의 PR 포함, 잘린 줄기의 것도). 범례에 `⚠ 주의 있음(아래 줄)`. "같은 파일" 주의만 `--verbose` 에 남는다.
- **public-cloud 확인**: DEV-007 이 #244→#248→#252→#256→#258→#264→#273 한 줄, #267·#275 는 `devs` [6, 7] 이지만 Spec 파일이 DEV-006 이라 DEV-006 줄(`#267 ⏳(앞: #244) → #275`)로 간다.
- **알려진 한계**: 번호를 어디서도 못 읽는 PR 이 두 DEV 그룹에 걸치면 "줄기 없음" 으로 간다. 본문이 다른 DEV 번호만 먼저 언급하고 Spec 파일도 안 바꾼 PR 은 엉뚱한 줄기에 들어갈 수 있다.
- **`--mine` 범위**: 할 일 표는 내 PR 만. 줄기 표는 내 PR 이 든 줄기만이고, 남의 PR 도 그 줄기 안에 있으면 보인다(내 뒤에 올 남의 PR 포함). 이를 위해 `run` 이 전체를 계산한 뒤 `filter_mine` 으로 거르고(`--json` 은 이전과 같은 값), `render` 에 전체(`full`)를 같이 넘겨 줄기를 묶는다. `--all` 은 할 일 표 없이 줄기 표를 저장소 전체로(혼자는 맨 아래).
- **`--verbose`**: 승인 사유 전문·다음 할 일을 담은 예전 형식 표와 "같은 파일" 주의를 표 아래 "자세히" 에 붙인다. 평소엔 빠진다. 일부만 읽었다는 주의·경고(version 못 읽음 등)와 사람이 병합할 경로인지 확인 불능 같은 상태 주의는 원칙 7 때문에 평소에도 낸다.
- **`--max-rows N`** 은 줄기 표의 줄기 수 제한("… 외 N개 줄기 — /harness:prs"). "줄기 없음" 한 줄은 제한과 무관하게 싣는다. `--quiet-empty` 는 그대로(내 PR 이 없으면 무출력). 세션 시작 훅·start·deliver 의 호출 형태는 그대로다.
