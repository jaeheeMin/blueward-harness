# #744 매뉴얼 쓰기 시험 흐름 (2026-11-11)

## 배경
#743 의 확인은 조회 화면만 다뤘다. 실제 업무 흐름(대상 앱: public-cloud 생산실적 모니터링 `#ZPP_AUTO1_PRODUCT_STATUS-display`, sap.ui.table GridTable 다중 선택)은
행을 골라 취소 버튼을 누르면 `sap.m.MessageBox.confirm` 이 뜨고, 확인하면 표가 새로고침되며 MessageToast("취소 완료 N건, 실패 M건…")가 잠깐 뜬다. 실패하면 `MessageBox.error`.
엔진은 준비 단계 뒤 대화상자를 모두 검사 불능으로 쳤고(MessageBox 는 alert 취급) 행 선택도 단계로 없었다.

## 한 일
`checker/manual_capture.py`·`checker/manual_capture_js.py`.

- 화면 키 `바꿈: true`(bool). `창 누르기` 단계는 `바꿈: true` 화면에서만 허용(아니면 `ListError`). `바꿈` 인데 `창 누르기` 가 없는 것도 허용.
- 새 준비 단계: `{행 고르기: <열>, 행: N}`(행 선택 칸을 실제 마우스 클릭, 뒤이어 선택 확인), `{창 누르기: <버튼 글자>}`(대화상자 정확히 하나 안의 같은 글자 버튼 하나를 클릭).
- `누르기` 뒤 다음 단계가 `창 누르기` 면 대화상자 1개(alert 포함)를 허용한다. 그 밖은 예전 규칙.
- `--allow-write` 없음 = 연습: 첫 `창 누르기` 앞까지 돌고 그 버튼이 있는지만 확인한 뒤 그 상태를 찍고, Cancel·취소 버튼(없으면 Escape)으로 닫는다. 화면 상태 `멈춤`, 사유 "쓰기 허락(--allow-write) 없이 데이터를 바꾸는 단계 앞에서 멈췄다. …닫은 결과". 작업본은 고치지 않는다.
  `창 누르기` 가 없는 `바꿈` 화면은 브라우저를 건드리기 전에 `멈춤`("어디서 멈출지 몰라 실행하지 않았다").
- `멈춤` 화면이 있으면 전체 `status` 는 `incomplete`(종료 1). 바꿈 화면이 있으면 결과에 `쓰기: 연습|허락`.
- `--allow-write` 에서 첫 `창 누르기`(클릭 직전에 표시) 뒤 검사 불능·미완이 된 화면은 `데이터 바뀜: true` 와 사유 앞 "데이터가 바뀌었을 수 있다 — ". 완료여도 `데이터 바뀜: true`. `창 누르기` 뒤에 대화상자가 남으면 검사 불능(창 글 포함).
- 알림: 바꿈 화면이거나 `{알림}` 확인이 있는 화면은 준비 단계 중(각 단계 직후·`wait_ready` 반복마다) `.sapMMessageToast`·`[role=status]` 글을 모아 화면 행 `알림` 에 낸다(중복 없이, 나타난 순서). `{알림: 글}` 확인 — 포함하면 `맞음`, 없거나 하나도 못 모았으면 `다름`(실제: 모은 목록), 읽기 실패는 `검사 불능`.
- 기록: `{열, 행}`(값 없음) → 결과 `기록`, `실제` 에 칸 값. 판정·status 영향 없음. `{열}` 만은 여전히 거부. opaque·못 찾음은 검사 불능.
- JS: `rowSelector`·`rowSelected`·`dialogButton`·`toasts`.
- `/harness:manual` 에 새 키·단계·확인 형식·결과 설명과 새 소절 "쓰기 시험"(사용자에게 테넌트·흐름·생긴 문서 처리 먼저 묻기 → 연습 → 허락 → `--allow-write` 한 건 → 결과 표). 길잡이 매뉴얼 탭·`checker/README.md` 도 맞췄다.
- 시험: `checker/tests/test_manual_capture.py`(파싱, 연습 멈춤·닫기·Escape, `--allow-write` 끝까지, 창 찾기 실패, 쓰기 뒤 오류 창, 행 고르기, 알림, 기록, 하위 호환, JS 이름).

## 판단
- 연습 모드의 `멈춤` 그림은 표시를 못 찾으면 예전처럼 `_미완` 이름으로, 다 찾으면 정식 이름으로 저장하되 작업본은 고치지 않는다(끝까지 돈 그림이 아니다).
- 연습에서도 첫 `창 누르기` 의 버튼이 있는지(대화상자 하나·버튼 하나)는 확인한다 — 누르지는 않는다. 그래야 연습이 "창 찾기 확인" 이 된다.
- `창 누르기` 뒤에 대화상자가 남으면 종류와 상관없이 검사 불능이다(오류·경고 창이면 그렇게 말한다). `창 누르기` 를 연달아 쓰는 흐름은 두 번째 확인 창을 알려진 오류 창과 가릴 수 없어 아직 허용하지 않는다.
- `창 누르기` 가 없는 `바꿈` 화면이 `--allow-write` 로 돌 때는 `누르기` 자체가 쓰기일 수 있어 그 단계를 누르기 직전에 `데이터 바뀜` 대상으로 친다.
- 알림은 `알림` 키를 바꿈 화면이나 `{알림}` 확인이 있는 화면에만 낸다(그 밖의 목록 결과는 예전과 같다). 준비 단계가 하나도 없으면 모으지 않는다.

## 확인 못 한 것
- 실제 화면 시험 아직. 가짜 탭 시험만 했다. 특히 아래는 추측이다.
  - 행 선택 칸이 `.sapUiTableRowSelectionCell`·`[role=rowheader]`·`[role=checkbox]`·`.sapMCb` 중 무엇인지, 같은 `aria-rowindex` 로 본문 칸과 이어지는지, 선택 뒤 `aria-selected="true"` 나 체크 클래스가 실제로 켜지는지.
  - MessageBox 버튼의 한국어 글자(`OK`·`Cancel` 인지 `확인`·`취소` 인지). 연습은 `Cancel`·`취소` 순으로 찾고 없으면 Escape 다.
  - MessageToast 의 클래스(`.sapMMessageToast`)와 토스트가 `wait_ready` 반복 안에 읽힐 만큼 오래 떠 있는지.
- JS(`rowSelector`·`rowSelected`·`dialogButton`·`toasts`)는 문법만 확인했고 실제 Chrome·UI5 에서 돌려 보지 못했다.
