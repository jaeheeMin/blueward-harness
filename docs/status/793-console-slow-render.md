# #793 웹 콘솔 세션 화면 그리기가 느린 원인 조사 (2026-11-10, 판 0.10.255)

## 결론
- **이 PC(헤드리스 Chrome 156, 소프트웨어 렌더링)에서는 원본도 세션 화면·홈이 59~60fps 였다. 이슈의 "2초에 2~3번" 은 재현하지 못했다.** 이슈 댓글(11-08)의 추정(보이지 않는 탭)을 이번에 뒤집거나 확인하지도 못했다.
- 숫자로 잡힌 병목은 둘이다. (1) `GET /api/sessions/<id>/files` 가 요청마다 git 을 5번 넘게 실행해 0.4~2.4초 걸리고, 홈의 "최근 산출물"이 최근 6개 세션이 바뀔 때마다 20개 넘는 세션에 이 요청을 다시 보낸다. (2) 이벤트마다 세션 읽기·목록·머리줄·대화·홈 표를 통째로 다시 만들었다(메인 스레드가 10초 중 1.5~1.8초 바쁨).
- 사용자 콘솔(4873·4874)은 측정할 때 떠 있지 않아 실제 값은 재지 못했다.

## 측정 방법
측정 스크립트는 저장소에 넣지 않았다(시험 콘솔 전용 임시 도구). 방법만 적는다.
- 시험 콘솔을 포트 4886 에 띄운다(`checker/tests/console_mockup/fake_console` 의 `lib.start_server`). 훅으로 세션 24개를 만들고, 서버를 끈 뒤 `sessions.json` 에 세션마다 대화 200(상한 `CHAT_LIMIT`)·기록 200(`LOG_LIMIT`)을 채워 다시 띄운다. 훅으로 200개를 쌓으면 Stop 마다 `refresh_git` 이 git 을 수천 번 돌려 시험이 막힌다(실제로는 몇 주에 걸쳐 쌓인다).
- 헤드리스 Chrome 에 DevTools 프로토콜로 붙어 세션 화면(`/s/s00`)과 홈(`/`)을 1440×900·2457×1479 로 연다. 열기 전에 `Page.addScriptToEvaluateOnNewDocument` 로 Long Task 관찰자·rAF 프레임 기록·`appendChild`/`replaceChildren` 호출 세기·MutationObserver 를 넣는다.
- 첫 표시 = `main.main > *`·`[data-chat]` 가 처음 나타난 시각. 3초 가라앉힌 뒤 훅 이벤트 초당 약 50개(40% 는 열어 둔 세션)를 10초 흘리며 `Performance.getMetrics` 앞뒤 차이(Script·Layout·RecalcStyle·Task)와 프레임 간격을 잰다. API 는 파이썬으로 5번씩 재 중앙값을 낸다. 서버 cProfile 은 Python 3.12 의 cProfile 이 모든 스레드를 한 번에 본다는 점을 써서 래퍼 한 겹으로 돌렸다.
- 이 PC 의 크롬은 launcher 프로세스가 먼저 끝나고 자식이 이어 받아 `checker/tests/console_mockup/cdp.py` 가 "브라우저가 바로 종료됨" 으로 실패한다(#855 가 고친다). 측정은 launcher 종료를 허용하는 임시 클라이언트로 했다.

- 목표 중 못 맞춘 것: `/files` 평소 호출(캐시 없는 첫 호출)은 git 실행 때문에 이 PC 에서 0.4~0.9초다(git 한 번이 0.25~0.4초). 캐시(3초)와 호출 횟수 줄이기로 폭풍 중 응답은 줄였지만 첫 호출 자체는 100ms 안이 아니다.

## 고친 것
- `server.py`: `/files?cache=1` 은 못 읽은 결과가 아니면 3초(`FILES_CACHE_SECONDS`) 동안 마지막 결과를 쓴다. `a_session_files` 를 `session_files` 로 나눠 같은 `git rev-parse` 를 두 번 하던 것을 한 번으로 줄였다(`gitstate.status_paths` 의 `checked` 인자). `?lite=1` 은 `log` 를 뺀다. SSE `session` 이벤트는 id 만 보낸다.
- `app.js`: 세션 읽기를 세션마다 묶고(열어 본 세션 0.3초, 나머지 1초에 한 번), 안 보는 세션은 `?chat=0&lite=1` 로 받는다. 세션 화면은 이벤트 다시 그리기를 0.25초에 한 번 프레임에 맞춰 한다. 맨 위 띠·머리줄·세션 목록은 `patchChildren` 으로 달라진 곳만 고치고, 대화는 바뀌지 않은 칸의 노드를 다시 쓴다(`chatCached`, `keepLeading`).
- `flow-ui.js`: 홈 표는 0.5초에 한 번 다시 그린다. "최근 산출물"은 5초에 한 번까지만 다시 읽는다. 목록·홈의 `/files` 는 `?cache=1`.

## 시험
- `test_web_console.py`: `/files?cache=1` 두 번째 호출이 git 을 실행하지 않음, 못 읽은 결과는 기억하지 않음, `lite=1` 은 `log` 만 뺌, SSE 이벤트는 id 만.
- `test_web_console_ui.py`: 이벤트를 몰아 읽고 그리는 줄이 빠지지 않았는지 확인하는 글 검사. 텍스트 검사 두 곳(`renderAnn` 구조, `/files?cache=1`)을 새 코드에 맞췄다.
- `console_ui_smoke.js`(가짜 DOM): `patchChildren` 이 쓰는 `childNodes`·`attributes`·`isEqualNode` 등을 더했다. 글 설정은 진짜 DOM 처럼 글 노드 하나를 자식으로 둔다.

## 확인 못 한 것·남은 일
- 사용자 콘솔의 실제 응답 시간과 세션 수·대화 길이(측정 때 서버가 꺼져 있었다).
- 실제 GPU·일반(headed) Chrome 에서의 fps. 이슈의 "2초에 2~3번" 이 보이지 않는 탭 때문인지는 여전히 추정이다.
- `patchChildren` 은 옛 노드의 이벤트 핸들러를 남긴다. 핸들러가 노드 모양 밖의 값을 쥐지 않는 조각(맨 위 띠·머리줄·세션 목록)에만 썼다.
