- `skills/srs/SKILL.md` 만들기 마무리: 다음 단계를 `다음 단계` 값별로 안내한다. `개발` 은 `/harness:spec`, `설정` 은 Spec 없이 설정하기(`/harness:start` 로 그 `DEV-xxx` 시작, 설정 뒤 SRS 상세 절에 기록), `미정` 은 사람이 개발인지 설정인지 정할 때까지 대기(`## 미결 사항` 에 남기고, 정해지면 `/harness:srs` 로 열을 고친다).

- 길잡이 `docs/guide/harness-guide.html`: SRS 탭 "내가 할 일"에 병합 뒤 길 한 줄, Spec 탭에 설정 건 deliver 안내와 "Spec PR 병합 뒤 start" 한 줄.

## 결정 필요 (4~6번, 고치지 않음)

### 4. 원장 없는 저장소에서 설정 요구사항의 설정하기 갈래

- 지금 동작: SRS 에서 `설정` 으로 정해도 원장이 없으면 원장 줄 올리기를 건너뛴다(알리기만). 그런데 콘솔 설정하기 갈래는 start 가 "원장의 그 줄을 대기에서 진행으로" 바꾸고 deliver 가 "완료" 로 담는다는 전제다. 줄이 없으면 이 두 동작이 할 일이 없다.
- 선택지:
  - A. 원장 없으면 설정하기 갈래도 원장 단계 없이 돈다고 문서에 못박는다(start 로 이슈·브랜치 → 설정 → SRS 기록 → PR). 스킬 문장 몇 줄만 바뀐다.
  - B. 원장이 없으면 설정 건도 새 원장 파일을 만들게 한다(`templates/harness/audit-ledger.md` 틀). 갈래가 항상 같아지지만 원장 안 쓰는 저장소에 파일이 생긴다.
  - C. 원장 없는 저장소에선 `설정` 을 못 고르게 막고 `미정` 으로 둔다. 가장 단순하지만 팀원이 설정 건을 못 적는다.
- 추천: A. 팀원 입장에서 하는 일(이슈 열고 설정하고 SRS 에 적고 올리기)이 똑같고, 원장은 있을 때만 쓰는 부가 기능이라는 지금 설계와 맞다.

### 5. scaffold 직후(templates 원본을 넣기 전)에도 콘솔이 "준비됨" 으로 본다

- 지금 동작: 콘솔 `project-ready` 는 `templates/` 와 `rules/` 폴더를 함께 가진 폴더가 (깊이 3 안에) 있는지만 본다(`workflow.json` conditions, 플러그인 저장소 자신은 예외). scaffold 는 `templates/harness/*`, `rules/*.yaml` 을 만들므로 직후에 곧바로 "준비됨" 이다. 고객사 양식 원본(`templates/` 에 넣기)과 `templates/forms/` 지도는 비어 있어도 통과한다. 폴더 칩과 첫 열기 안내(#646)도 같은 조건이다.
- 선택지:
  - A. 지금대로 둔다. "구조가 있다" 만 뜻한다고 문구를 분명히 한다.
  - B. 조건을 더해, 고객사 양식 원본이 `templates/` 에 들어오기 전에는 "구조는 됐고 양식 원본을 넣어야 해요" 라는 두 번째 안내를 보인다("준비됨" 은 유지). 양식 쓰는 작업 전에 빠진 걸 알려 준다.
  - C. "준비됨" 자체를 양식 원본이 있어야 되게 한다. 양식 안 쓰는 프로젝트(md 만 쓰는 곳)는 영영 준비 안 됨이 되어 부작용이 크다.
- 추천: B. 팀원은 "준비됨" 인데 매뉴얼·CTS 산출에서야 양식이 없다는 걸 알게 되는 일이 줄고, 양식 없이 쓰는 프로젝트는 영향이 없다. 단 훅(`session-start-sync.sh`)의 안내와 같은 기준이어야 하니 같은 PR 에서 맞춘다.

### 6. 에이전트의 자기 PR 병합 예외와 콘솔 병합 대기 문구

- 지금 동작: governance 는 문서만 바꾼 PR(`docs/` 아래, `docs/ssot/`·`docs/spec/` 제외 등)이고 검사가 모두 통과했으면 에이전트가 자기 PR 을 `--squash` 로 병합해도 된다고 한다. 반면 콘솔 병합 기다리기 단계(workflow.json 의 `merge` 힌트)는 "자동 병합 / 승인자 Approve / 사람이 GitHub 에서 직접 병합" 세 경우만 말하고, 에이전트가 병합하는 길은 안 나온다. 콘솔 PR 칩 문구도 "승인자 확인을 기다리는 중 · 승인은 GitHub 에서 해" 로 고정이다.
- 선택지:
  - A. 그대로 둔다. 에이전트가 병합하면 상태가 곧 "합쳐졌어" 로 바뀌므로 대기 문구는 잠깐만 보인다.
  - B. 병합 힌트에 "문서만 바꾼 PR 은 Claude 가 검사 통과 후 병합하기도 해요" 한 줄을 더한다(basis: governance 예외 문장).
  - C. 콘솔이 PR 의 바뀐 파일을 보고 "사람 승인 필요 / Claude 병합 가능" 을 구분해 문구를 달리한다. 정확하지만 콘솔이 규칙을 두 번 구현하게 된다(규칙은 데이터라는 원칙과 어긋남).
- 추천: B. 팀원이 "왜 아무도 안 눌렀는데 합쳐졌지?" 를 겪지 않게 하고, 규칙 로직은 늘지 않는다.
