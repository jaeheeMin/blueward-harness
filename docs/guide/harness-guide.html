시작 전에

저장소 두 개, 검사관 두 명

우리가 쓰는 건 두 저장소야. 하나는 일하는 곳(public-cloud), 하나는 일하는 법과 검사 도구를 담은 곳(blueward-harness).

쉽게
말하면

public-cloud는 고객사 일을 하는 작업장이야. 문서와 코드, 그리고 "이 회사 문서는 이렇게 생겨야 해" 하는 기준표(templates/, rules/)가 같이 들어 있어.

blueward-harness는 모든 작업장에 나눠 주는 공구함이야. 일을 대신 처리해 주는 단축 명령(Skill), 실수하면 문 앞에서 막는 경비원(Hook), 문서를 재는 자(검사 엔진)가 들어 있어.

내 PC(Personal Computer) 의 경비원(Hook)은 Claude 를 쓸 때만 서 있어. GitHub 검문소(Actions)는 누가 올리든 항상 서 있어.

처음이라면 이 순서로

번호 순서대로 따라가면 돼. 상자를 누르면 그 액티비티로 가. 새 개발은 SRS 만들기부터야. SRS·Spec 스킬이 이슈와 브랜치를 알아서 만들어 줘서, 그 단계에선 /harness:start 를 따로 안 불러도 돼. start 는 Spec 이 끝나고 개발을 시작할 때, 또는 버그 수정·문서 손보기처럼 SRS·Spec 을 안 거치는 일을 시작할 때 써. 끝은 언제나 작업 올리기야.

꼭 기억할 세 가지

  1. main 에 직접 손대지 않는다. 일은 SRS·Spec 스킬이나 /harness:start 가 만들어 주는 내 브랜치에서 해.
  2. 푸시는 /harness:deliver 로 한다. 맨손 git push 는 경비원이 돌려보내.
  3. "검사를 못 했다" 는 통과가 아니다. 확인을 못 했으면 못 했다고 말해.

Claude 와 일하는 방식

대화하는 Claude(메인 세션)가 무엇을 할지 정하고 결과를 판정해. 실제로 찾고 고치는 일은 보조 Claude(서브에이전트)가 나눠 맡아.

보조맡는 일
harness:researcher읽고 조사만. 파일은 못 고침
harness:implementer정해 준 범위만 고침. 커밋·푸시는 안 함
harness:reviewer고친 걸 다른 눈으로 검토. 자기 결과는 승인 안 함

보조를 부를 때 모델(model)을 직접 적으면 경비원이 돌려보내. 모델은 보조의 정의 파일이 정해 둬서, 직접 적으면 그 약속이 깨지거든. 이름 없이 부르거나 general-purpose 같은 기본 보조를 부르는 것도 돌려보내고 위 셋 중에서 고르라고 알려 줘. 그 밖의 보조(검색·웹 읽기 등 내장 보조, 다른 플러그인의 보조)는 그대로 쓸 수 있어.

보조가 스크립트로 파일을 고치면 못 끝내게 막아. 보조는 파일을 Edit·Write 도구로만 고쳐야 해. 파이썬이나 셸 명령으로 몰래 쓰면 그 도구에 걸린 검사가 안 돌거든. 보조가 시작할 때 세션이 열린 폴더뿐 아니라 같은 저장소의 다른 작업 폴더(worktree)들의 상태도 모두 적어 두고, 끝나려 할 때 그 사이에 바뀐 파일을 — 세션 폴더와, 보조에게 넘긴 지시문이나 보조가 실행한 명령에 경로가 나온 작업 폴더, 보조가 Edit·Write 한 작업 폴더에 한해 — Edit·Write 기록과 맞춰 봐. 고치기 전 모습부터 고친 뒤 모습까지 기록이 끊김 없이 이어져야 인정해서, 스크립트로 먼저 고친 뒤 Edit 으로 덮어 가려도 잡혀. 안 맞는 파일이 있으면 "이 파일을 다시 고쳐라" 하고 돌려보내. 같은 보조가 두 번 돌려보내져도 그대로면 더는 막지 않고 경고만 하는데, 이 경고는 화면에만 뜨지 않고 메인 Claude 가 다음에 보조를 부른 뒤에 한 번 전해 줘서 메인도 알게 돼. 보조가 그 사이에 커밋을 했으면 막지 않고 경고만 해. git 폴더가 아니거나 기준을 못 읽거나 작업 폴더 목록을 못 읽으면 "확인 못 함" 이라고만 알려. 같은 저장소의 다른 세션이 일하는 작업 폴더는 보조와 이어지지 않았으면 점검하지 않아(그쪽 변경을 보조 탓으로 돌리지 않으려고). 이어진 작업 폴더에서는 거기서 다른 세션이 Edit·Write 로 고친 기록도 인정해. 보조가 다른 저장소 파일을 Edit·Write 로 처음 건드리는 순간 그 저장소도 기준에 더하지만, 그 전에 스크립트로 고친 것과, 상대 경로만 써서 지시문·명령에 경로가 안 나온 작업 폴더는 못 봐. 시작 뒤에 만든 작업 폴더는 이어진 뒤부터만 봐서 "확인 못 함" 으로 알려. 메인이 Bash 로 고친 파일, 동시에 도는 다른 보조의 Bash 수정, Edit 뒤에 파일을 다시 쓰는 포맷터는 가려내지 못해서 잘못 돌려보낼 수 있어.

처음 준비하기

출입증을 받고 공구함을 챙기는 단계야. 한 번 해 두면 다음부터는 세션을 열 때 자동으로 점검돼.

쉽게
말하면

작업장(public-cloud)을 내 PC(Personal Computer) 로 복사해 오고, 공구함(harness 플러그인)을 그 작업장에 꽂아 두는 거야. SAP(Systems, Applications and Products) 를 만질 사람은 SAP 출입증(로그인 쿠키)도 받아 둬.

순서대로 따라 하기

  1. Git 설치 — winget install --id Git.Git -e, 그다음 이름과 이메일을 등록해.
  2. 저장소 받기 — GitHub 초대를 수락하고 blueward-26/public-cloud 를 clone 해. (예전 이름 jaeheeMin/public-cloud 에서 옮겨 왔어.)
  3. Claude 에서 폴더 열기 — Claude Desktop 의 Code 탭 → Local 에서 받은 폴더를 열고 Trust 를 수락해.
  4. 플러그인 설치 — 설정 → 플러그인에서 마켓플레이스 jaeheeMin/blueward-harness 를 추가해. 목록의 설치 버튼은 누르지 말고, Claude 에게 이렇게 시켜:
    claude plugin install harness@blueward-harness --scope project
    설치 버튼으로 깔면 내 모든 폴더에 경비원이 서게 돼. --scope project 는 이 작업장에만 세워 둬.
  5. GitHub 로그인 — 입력창에 ! gh auth login 을 쳐서 로그인해.
  6. 도구 확인 — uv, jq, gh, gitleaks 가 필요해. Windows 는 세션을 열면 winget 으로 알아서 깔아 줘. 깔리면 Claude Code 를 한 번 껐다 켜.
  7. SAP 를 쓸 사람만 — Node.js 22 이상과 Chrome 을 깔고, MCP(Model Context Protocol) 승인 창을 승인한 뒤 /c080(개발), /c100(조회)으로 로그인해. Chrome 이 열리면 본인 SAP 계정으로 들어가면 돼.

터미널(CLI(Command Line Interface))로 쓰는 사람

/plugin marketplace add jaeheeMin/blueward-harness
/plugin install harness@blueward-harness

저장소의 .claude/settings.json 에 마켓플레이스와 자동 업데이트가 적혀 있어서, 폴더를 열면 설치 안내가 떠.

세션을 열 때마다 자동으로

  • 필요한 도구가 있는지 보고, 없으면 설치
  • git hook(커밋·푸시 검사) 설치
  • GitHub 최신 내용을 받아 내 브랜치에 맞춤. 저장 안 한 변경이 있으면 건너뜀
  • 공통 개발 규칙(CR-001(CR = 공통 개발 규칙)~009) 요약을 보여 줌
  • 지난 세션에 못 올린 변경이 있으면 알려 줌
하지 마
GitHub Desktop 은 쓰지 않아. 그 안의 git 에는 bash 가 없어서 경비원(.githooks)이 안 돌아. Claude 세션이나 Git Bash 를 써.
충돌 주의
내 개인 폴더(~/.claude/skills)에 c080, c100 이 따로 있거나 같은 이름의 MCP 서버가 있으면 포트가 겹쳐서 하나만 떠. 개인 쪽을 정리해.
도구 없음
jq 가 없으면 git 명령이 전부 거절되고, uv 가 없으면 문서 검사가 "검사 불능" 으로 막혀. 둘 다 통과가 아니라 멈춤이야.
업데이트
Plugin updated … Run /reload-plugins 알림이 뜨면 /reload-plugins 를 쳐. 이미 열린 세션은 처음 받은 버전을 계속 써. 자세한 건 아래 "플러그인 갱신" 을 봐.
엔진 판
훅은 플러그인 버전에 맞는 엔진 판(v0.10.xx 태그)을 받아. 새 판이 병합된 직후엔 태그가 붙기까지 잠깐 걸려서, 그 사이 업데이트하면 "엔진을 받을 수 없다" 고 나올 수 있어. 조금 뒤 다시 해.

플러그인 갱신 — 언제, 어떻게

  • 자동 — Project Repository 의 .claude/settings.json 에 자동 업데이트(autoUpdate: true)가 켜져 있어서, Claude Code 를 쓰다가 첫 메시지를 보낸 뒤 최대 10분 안에 새 판을 받아 둬. 열려 있는 세션은 처음 받은 버전을 계속 쓰고, 새 판은 다음에 열 때부터 적용돼. 켜 두지 않으면 자동으로는 안 받아져(/plugin → Marketplaces → Enable auto-update).
  • 열린 세션에서 바로 — /reload-plugins 를 쳐. 훅·MCP 서버가 새 판으로 바뀌어.
  • 한 번에 (/harness:update) — 터미널 없이 Claude 에 /harness:update 를 입력해. 마켓플레이스 새로고침 → 업데이트를 대신 실행하고, 이 세션에 실제로 실린 판이 최신인지로 확인해(같은 저장소의 작업장마다 설치 기록이 따로라 다른 작업장 기록이 갱신되거나 세션이 그 판을 싣는 일이 있었어). 업데이트 뒤에도 이 세션은 reload 전까지 옛 판이라, /reload-plugins 를 네가 직접 입력하고 /harness:update (또는 /harness:version)를 한 번 더 입력해서 확인해. reload 직후 첫 호출은 옛 판으로 보일 수 있어서, 그때는 /harness:update 를 한 번만 더 입력해 달라고 안내해. 그 두 번째에도 최신이 아니면 "갱신 확인 불능" 이라고 알려 주니 새 세션을 열어. claude plugin uninstall 은 하지 마 — 묻지 않고 공유 .claude/settings.json 의 enabledPlugins 를 비워서, 커밋되면 팀원 전체의 harness 가 꺼져.
  • 손으로 — 터미널에서 순서대로. 폴더별로 깔았으니 그 작업장 폴더에서 해.
    claude plugin marketplace update blueward-harness
claude plugin update harness@blueward-harness --scope project
    끝나면 "Restart to apply changes" 가 떠. Claude Code 를 다시 열거나 열린 세션에서 /reload-plugins.
  • 작업 중에 새 판이 나오면 — 메시지를 보낼 때 Claude 가 한 번 알려 줘(세션당, 같은 판은 한 번). 갱신은 알려 준 방법(/harness:update 포함)으로 네가 직접 해. HARNESS_NO_UPDATE_NOTICE=1 로 끌 수 있어.
  • 이 폴더 판 확인 (/harness:version) — 설치된 플러그인마다 판(harness 는 이 세션에 실린 판, 나머지는 설치 판), 최신 판, 상태(최신 / 갱신 있음 / 이 폴더에 설치 없음 / 최신 판 확인 불가)를 4칸 표로 보여 줘. harness 의 상태는 설치 기록이 아니라 실린 판으로 정해. 이 폴더에서 안 쓰는 플러그인 줄은 빼고(harness 는 남겨), 이 폴더 판·다른 폴더 설치까지 다 보려면 --all-entries(갱신이 있거나 실린 판을 못 읽을 때 표 아래에 안내가 나와). 폴더마다 설치 기록이 따로라 claude plugin list 로는 어느 줄이 이 폴더 것인지 헷갈리는 걸 풀어 줘. reload 직후 첫 호출은 옛 판으로 보일 수 있어, 한 번 더 부르면 바로잡혀. 보기만 하고 갱신은 안 해 — 갱신이 필요하면 /harness:update.
  • 지금 버전 확인 — 터미널에서 claude plugin list. harness@blueward-harness 아래 Version 이 지금 받아 둔 판이야. 이 가이드 레일 아래 "harness 0.10.xx 기준" 이 최신이라고 보면 돼.

  • 세션을 열어 둔 채 작업 중이어도 새 판이 나오면 Claude 가 한 번 알려 줘. 갱신은 직접 해.
  • 검사 엔진은 새 판이 나오는 즉시 PR(Pull Request) 검사(최종 판정)에 쓰이지만, 내 PC 훅(미리 검사)은 플러그인을 갱신해야 새 판을 써.
  • 그래서 갱신 전에는 PC 훅과 PR 검사 결과가 다를 수 있어. 그럴 땐 먼저 갱신하고, 그래도 다르면 최종 판정은 PR 검사를 따라.

웹 콘솔 열기 (/harness:open)

Claude 세션이 여러 개일 때 한 화면에서 보는 브라우저 페이지야. 터미널 창을 오가지 않고 각 세션이 뭘 하는지, 끝난 결과가 뭔지 보고, 승인·질문에 답하고, 새 일을 맡길 수 있어. 내 PC 안에서만 열려(127.0.0.1:4873), 밖에서는 못 들어와.

  • 여는 법 — Claude 에 /harness:open 을 입력해. 서버가 꺼져 있으면 띄우고 기본 브라우저를 열어. 결과는 한 줄로만 알려 줘. Windows 에서는 처음 열 때 바탕화면에 Blueward Harness 바로가기가 생겨. 그다음부터는 Claude 를 켜지 않아도 그 아이콘만 누르면 서버를 띄우고 인증된 화면을 열어 주고, 서버가 다시 떠서 화면이 끊겼을 때도 아이콘을 다시 누르면 돼. 바로가기를 지우면 다시 만들지 않아(다시 만들려면 콘솔 설정의 "바탕화면 바로가기 → 만들기" 를 눌러). 못 만들면 바로가기를 만들지 못함(이유) 한 줄이 더 나와. 서버를 끌 때는 uv run --no-project python <플러그인 폴더>/console/open.py --stop. uv 가 필요해. Windows 에서는 서버가 콘솔 창 없이 뜨고, 화면 이름은 "Blueward Harness" 야.
  • 보는 것 — 세션을 내가 할 일(승인·질문 대기, 다음 스킬 차례), Claude가 하는 일, 쉬는 중 으로 나눠 보여 줘. 세션마다 지금 스킬과 행동, 결과 보고, 바뀐 파일, PR 링크, 로그가 나와. "다음 스킬 차례" 는 브랜치·변경·PR 로 판단하는데, gh 로 PR 을 못 보면 "확인 불가" 로 표시해.
  • 작업 화면 — 세션 화면은 위에 제목·숫자 띠(단계·AI 진행·요구사항·개발 번호·작업 기록·검토 요청), 가운데 밝은 대화 판, 오른쪽(좁으면 아래)에 만든 산출물이 있어(만든 문서가 아직 없으면 이 칸을 두지 않고 대화 판이 본문 전체 너비를 써). 순서 알약과 층 그림은 AI 가 일을 마치고 올릴 차례일 때와 갈래가 끝났을 때만 제목 옆에 보여(승인을 기다리는 동안엔 없어). 승인을 기다리는 세션과 합쳐진 세션은 '내 차례' 로 세지 않아서, 사이드바에는 "승인 기다림 · PR #n" · "끝 · PR #n 합쳐짐" 으로 보이고 합쳐지면 맨 위 띠가 "PR #n이 합쳐졌어 — 다음은 …" 으로 알려 줘. 승인 기다림 화면의 검토 요청 카드는 문서 검사 · 비밀값 검사 · 팀 승인 세 줄이야. 숫자 띠에 기억 칸은 없고(기억은 사이드바 링과 배너에 있어), 질문은 대화 안에서 바로 골라(직접 적기 를 고르면 그 질문 카드 안에 입력칸이 열리고, 답 보내기 는 카드들 아래 오른쪽에 있어). "지금 하는 일"(왼쪽 목록·내 일·홈 표·세션 제목)은 영문 도구 이름 대신 "파일 고치는 중"·"명령 실행 중"·"요구사항 문서 진행 중" 같은 쉬운 말로 보이고, 원문(도구 이름과 입력)은 "자세히" 의 기술 정보 "현재 동작"에만 있어. 오른쪽은 문서 미리보기 한 장이고, AI 가 일하는 중엔 다른 문서 목록을 다른 문서 n개 보기 로 접어 둬(일을 마치면 미리보기 아래에 목록이 보여). 대화 판에는 내 말(콘솔이 첫 말 앞에 붙인 /harness:… 명령 줄은 숨겨)·AI 말·질문과 승인 요청(답한 것은 "→ 고른 답" 한 줄)이 시간 순으로 쌓이고, 새로 고쳐도 남아. 12개가 넘으면 앞은 "… 앞 대화 N개 접힘" 으로 접혀. 터미널에서 연 세션은 훅으로 받는 것만 있어서 내 말과 AI 마지막 답만 보인다고 알려 줘. 하네스 훅(git 명령·파일 쓰기·Agent 위임·SAP 소스 쓰기 검사·서브에이전트 수정 점검·마무리 확인)이 막으면 그 이유와 고치는 법이 대화 안에 빨간 ✕ 막힘 카드로, 검사를 못 해서 멈췄으면 보라 점선 ? 확인 못 함 카드로 떠. 막힘 카드에는 그렇게 고쳐 줘(콘솔로 띄운 세션만) · 내가 직접 볼게(단추를 접고 직접 보기로 표시) · 검사 원문(훅 문구 전체 펼치기)이, 확인 못 함 카드에는 검사 다시 돌리기(콘솔로 띄운 세션만) · 관리자에게 알리기(보낼 내용을 복사해 줘 — 팀 메신저에 붙여 넣으면 돼)가 있어. 막힘이 풀리기 전(그 뒤로 내 말·AI 말이 없는 동안)에는 그 세션이 홈 표·왼쪽 목록에 ✕ 막힘 / ? 확인 못 함 으로 따로 보이고(세션 숫자 띠의 단계 칸에도 "1 / 3 쓰기 · 막힘" 처럼 막힘은 빨강, 확인 못 함은 보라로 붙어), 맨 위에는 초록 띠 한 줄("막힌 일 1건 · 확인 못 한 검사 1건")로 알려 주며 "내 차례" 숫자에는 안 들어가. 이때는 "어떤 일인가요?" 대신 "막힌 걸 고친 뒤 이어서 하자" 안내가 먼저 나오고(그래도 먼저 일 고르기 로 넘어갈 수 있어), 내가 직접 볼게 를 누르면 다음 할 일과 다시 고르기 가 보여. 터미널에서 연 세션은 보내는 단추 대신 "터미널에서 고쳐 줘" 안내가 카드 안에 나와. 마무리 확인(커밋 안 한 변경 알림)도 세션을 붙잡으면 막힘 카드로 떠. uv 가 없어 검사 훅을 못 돌렸거나 ABAP 활성화 기록을 남기지 못했을 때도 막힘이 아니라 확인 못 함 카드로 떠. 세션 이름은 첫 요청에서 사람이 쓴 줄로 정해("[Image #3]" 같은 그림 자리표시나 다른 세션이 보낸 메시지 표시는 걷어 내). 쓸 글이 없으면 브랜치(예: "#683 console session names")나 스킬 이름, 그것도 없으면 "이름 없는 세션 · 폴더" 로 보여. 값을 모르는 칸은 만들지 않고, AI 진행 %는 순서의 끝난 단계 수로 계산한 값이야(칸에 올리면 근거가 나와). 새 작업은 종류 버튼 → 한두 줄 → 참고 파일(누르면 @ 로 파일 고르기) → "이렇게 진행돼"(스킬 명령 대신 "AI가 몇 가지 물어봐" 같은 쉬운 설명) → 작업 시작 순서이고 모델·권한은 맨 아래 접힌 "고급 설정" 에 있어. 분석 뒤 확인 화면은 AI 말 한 줄(이해한 내용과 갈래), 순서 칸(지금 단계는 굵은 테두리, 맨 끝에 "다음 세션" 칸), AI가 읽을 자료(체크)·AI가 물어볼 것(미리 골라 두기)·이대로 시작 이야. 설정하기·표준 기능으로 처리는 종류 칸 대신 "그 밖의 종류" 줄에 있어. 개발 요구사항·원장이 있는 프로젝트라면 종류 버튼 밑에 "Spec 있는 건 없음 — 개발 Spec 먼저", "할 차례 REQ-001(제목)" 같은 글이 미리 떠(읽지 못하면 아무것도 안 보여). 종류 버튼으로 고른 갈래와 AI 가 추천한 갈래가 다르면 AI 가 조용히 덮어쓰지 않고 "AI 는 개발 Spec 부터 하자고 해" 하고 먼저 물어봐. Spec 이 없다고 확실한데 "그래도 개발하기" 를 누르면 Spec 없이 개발은 시작할 수 없다고 알려 주고 시작하지 않아. 질문은 알약 보기로 답하고, 도구 허락은 "이번만 허락 / 하지 마" 카드로 떠(명령 원문은 "자세히" 에 있고, 설명이 없는 명령은 펼쳐져 있어).
  • 문제·해결 기록 — 위 메뉴의 기록 에서 팀이 PR 작업 중 겪은 문제와 푼 방법을 봐. 기록은 각 프로젝트 저장소의 type:trouble 이슈이고, 콘솔은 목록(전체·아직 안 풀림·해결됨, 프로젝트·쓴 사람·낱말로 찾기)과 한 건(증상·원인·해결 방법, 시도·후보·해결 이력, 관련 PR 상태, 비슷한 기록)을 gh 로 읽어 와(60초 기억). 저장소를 못 읽으면(로그인 안 됨 등) "기록 없음" 이 아니라 보라 점선 ? 확인 못 함 줄과 이유가 나와. + 새 기록 에서 프로젝트·PR 번호·단계·제목·증상·원인·해결 방법을 적고 GitHub 에 올리기 를 누르면 콘솔이 바로 이슈(제목 머리말 [기록] + 라벨)로 올려. 비슷한 기록이 있으면 먼저 "거기에 더하기" 를 권하고, 비밀번호·키처럼 보이는 값은 붙여 넣거나 치는 즉시 •••••••• 로 바뀌고, 원래 값은 입력칸에도 GitHub 에도 남지 않아. 가린 줄이 있으면 카드로 "비밀번호·키처럼 보이는 글이 있어 · 가렸어" 와 몇 번째 줄인지 알려 주고, 필요 없는 줄이면 그 줄 지우기 로 뺄 수 있어. 이미 가렸으니 올리기는 잠기지 않아. 그래도 가리지 못한 비밀 모양이 남으면 빨간 카드로 알리며 그 줄을 지울 때까지 올릴 수 없어. 콘솔의 다른 화면(대화·막힘 카드 원문·승인 화면의 명령과 입력 전체·관리자에게 보낼 글)에서도 비밀 값은 •••••••• 로 가려 보여 — 보이기만 가리고 Claude 에게 가는 글과 허락한 명령은 그대로야. 라벨이 저장소에 없으면 라벨 없이 올리지 않고 만드는 명령을 알려 줘. 올리기가 잠겨 있으면(프로젝트·단계·제목·증상, 해결됐다면 해결 방법이 비었을 때) 단추 옆에 비어 있는 칸을 알려 주고, 단계는 처음에 개발 로 골라져 있어. 한 건 화면은 제목 위에 기록 번호 #15 · 프로젝트 PROJ 로 보여 주고, 시도해 봤어 / 해결 후보 / 해결됐어 로 댓글을 더하고(처음엔 해결 후보 가 골라져 있고, 올리기 옆 글이 어느 종류로 올라가는지 알려 줘)(맨 앞 시도·안 됨: · 해결 후보: · 해결:), 후보의 이걸로 해결 은 본문 해결 방법을 고치고 이슈를 닫아. 콘솔이 쓰는 건 이슈 만들기·댓글·해결 닫기뿐이야.
  • 세션 화면에서 기록 만나기 — 하네스 검사에 막힌(✕) 카드 아래에는 막힌 이유 낱말로 찾은 비슷한 기록 n건 이 지난 기록 링크로 붙어(기록 목록을 못 읽으면 "없음" 이 아니라 ? 확인 못 함). 막힘 뒤에 AI 가 이어서 일을 마쳤거나, 이 세션 PR 의 검사가 실패로 보였다가 통과로 바뀌면 대화 끝에 기록해 둘까? 카드가 떠. 기록하기 를 누를 때만 AI 가 그 세션 대화로 초안(제목·증상·원인·해결 방법·단계)을 써서 새 기록 화면을 채우고(비밀번호처럼 보이는 줄은 가려), 괜찮아 는 그 제안을 다시 띄우지 않아. 초안을 못 만들면 이유와 빈 칸으로 쓰기 가 나와.
  • 산출물·설정·표시 약속 — 위 메뉴의 산출물 에서 모든 세션이 만든 문서를 한곳에 모아 봐(요구사항·설계 / 고객 양식 / 기록). 칩은 파일마다 따로 정해: 안 올림(커밋 전이거나, 커밋은 됐어도 열린 PR 이 없고 main 과 내용이 달라) · 검토 중(열린 PR 의 바뀐 파일에 들어 있어, 올려둔 칩에 PR 번호가 나와) · 합쳐짐(main 에 같은 내용이 있어) 이고 git·gh 를 못 읽어 알 수 없으면 확인 못 함 이야. 어느 세션의 PR 인지는 따지지 않아. 문서를 골라 열기·폴더에서 보기를 하고, 고쳐 달라고 하기 나 고객 양식으로 뽑기 는 그 문서를 만든 세션에 말을 보내는 거야(콘솔이 직접 뽑지는 않아). 고객 양식 xlsx 를 방금 뽑았으면 목록 없이 고객 양식으로 뽑았어 화면이 먼저 떠: 원본 → 양식 줄, 양식 칸 n개 모두 채움(또는 n개 중 m개), 넓은 미리보기 표, 노란 비어 있는 칸 n개 안내, 폴더에서 보기 · 내려받기, 빈 칸을 알려 다시 뽑아 달라고 하는 입력칸이 있어. 칸 수를 못 세면(표가 커서 일부만 읽은 때 등) 지어내지 않고 확인 못 함 으로 보여. 오른쪽 위 문서 목록 보기 로 목록 화면에 가. 검토 요청의 자동 검사가 실패하면 빨간 ✕ 막힘, 결과를 못 읽으면 보라 점선 ? 확인 못 함 카드로 보여(통과도 실패도 아니야). 설정에서는 글자 크기, AI가 묻는 범위(꼭 필요할 때만 · 권장 / 문서를 바꿀 때마다 / 모든 명령마다 — 이 PC 에 저장되고 어떤 걸 골라도 위험한 일은 하네스가 막아. "꼭 필요할 때만" 은 작업 폴더 안 파일 고치기, 간단한 읽기(git status·gh pr view·cat 등), 커밋, 그 프로젝트 env/adt-tiers.yaml 에 적힌 SAP 서버의 읽기 도구는 묻지 않아. 지우기·작업 폴더 밖 쓰기·GitHub 올리기·SAP 쓰기·설치는 노란 "되돌릴 수 없어" 카드로, 비밀값 파일·시험 실행·하네스 설정 파일 쓰기처럼 판단하기 애매한 건 보통 카드로 물어), 연결 상태(GitHub · 하네스 판 · 프로젝트)를 봐(설정 제목은 보기와 알림). 권한 모드(계획만 세우기 · auto 포함)는 설정이 아니라 새 작업의 고급 설정 에서 고르고, 고른 값은 다음 새 작업에도 기억해. 설정의 알림 스위치 셋(내 차례가 오면 · 막히거나 확인 못 한 일이 생기면 · AI가 일을 끝낼 때마다)을 켜면 콘솔 탭이 열려 있고 지금 보고 있지 않을 때 브라우저 알림이 떠(처음 켤 때 브라우저가 허락을 물어, 알림을 누르면 그 세션 화면으로 가. 허용창 답을 기다리는 중 · 답 없이 닫음 · 막힘 · 켜짐을 알림 아래 한 줄이 구분해서 알려 주고, 막혔으면 브라우저 설정에서 켜는 법도 보여). 탭을 닫으면 알림도 없어. 콘솔 연결이 끊긴 사이 AI가 허락이나 질문을 터미널로 넘겼으면 다시 연결됐을 때 위쪽 띠가 몇 번이었는지 알려(이 탭이 열리기 전 일은 알 수 없어). 세션 화면 아래 도구·권한·기록 같은 옛 칸은 "자세히" 에 접혀 있어.
  • 기억이 거의 찼을 때 — 세션이 쓴 기억(context)은 그 세션의 대화 기록 파일 끝에서 읽어. 공식 문서에 기억 창 크기가 적힌 모델(예: Opus 4.7 이상 100만 토큰)이면 몇 %인지 보이고, 모르는 모델이면 토큰 수만 보여(%를 지어내지 않아). 90% 이상이면 세션 화면 맨 위(제목 위)에 노란 "이 세션 기억이 거의 찼어" 배너가 떠. 새 세션으로 넘기기 를 누르면 지금 하던 일을 인계해서 새 세션이 이어 받고, 계속하기 는 그 세션의 배너를 닫고, 새로고침해도 닫은 채로 둬(이 브라우저에만 기억). 터미널 세션은 버튼 대신 /harness:handoff 안내가 나와. 읽지 못하면 ? 와 "확인 못 함" 이야.

GitHub 이 안 되면 첫 실행이 아니어도 먼저 고칠 게 있어 화면이 뜨고 고치는 법(예: 터미널에서 gh auth login)과 다시 점검 이 나와. 하네스가 옛 판이면 홈은 그대로 열고 맨 위 띠에만 알려. 원격이나 로그인을 못 읽으면 확인 못 함 이라고만 적고 문제로 치지 않아(Claude Code 로그인은 claude auth status 로 확인해서, 로그인이 안 돼 있으면 "먼저 고칠 게 있어" 로 막고 claude auth login 을 알려 줘. claude 를 못 찾으면 확인 못 함). 설정의 처음 화면 다시 보기 로 언제든 다시 봐.

  • 자동완성 — 입력칸에서 / 를 치면 스킬 이름이, @ 를 치면 작업 폴더의 파일 이름이 후보로 떠. @ 파일은 콘솔이 아는 작업 폴더 안만 찾고 한 번에 50개까지 보여. 파일 이름에 공백이 있으면 멘션이 거기서 끊겨.

Enter 로 보내고 Shift+Enter 로 줄을 바꿔(한글을 치는 중에 누른 Enter 는 보내지 않아). 칸이 내용만큼 늘다가 6줄쯤에서 스크롤돼. 스크린샷 같은 이미지(png · jpg · gif · webp)나 PDF 는 칸에 붙여 넣거나, 끌어다 놓거나, 첨부 단추로 골라서 같이 보낼 수 있어. 칸 위에 작은 그림(이미지)이나 이름(PDF) 칩이 뜨고 × 로 뺄 수 있어. 이미지는 한 장에 5MB, PDF 는 한 개에 20MB, 한 번에 5개·합쳐서 20MB 까지고, 넘으면 이유를 한 줄로 알려 줘. 대화 판 내 말 밑에도 첨부가 보여(기록에는 이름·종류·크기만 남고 파일 원본은 안 남아서, 새로 고침하면 그림 대신 이름만 보여). 콘솔이 띄운 세션에서만 돼 — 터미널에서 연 세션은 첨부 단추가 없어.
  • 화면 모양 — 맨 위에는 내가 답할 일이 있을 때만 초록 띠("내 차례 1건 — …")가 떠. 그 아래 헤더에 로고·메뉴(내 일 / 작업 / 새 작업. 세션이 없어도 같고, 세션이 없을 때 작업 은 새 작업으로 가)·프로젝트 이름(세션이 없으면 마지막으로 연 폴더 이름)·설정이 있고, 왼쪽에는 세션 목록이 있어. 세션마다 기억 사용량 링(채워진 링 + %, 80% 넘으면 노랑·90% 넘으면 빨강. 모델의 기억 창 크기를 모르면 24만 처럼 토큰 수만, 못 읽으면 ?)·이름·단계 막대·한 줄 상태가 보여. 색은 어두운 초록 바탕 한 가지로 정해져 있고(테마·디자인 고르기는 없어졌어), 설정에서는 글자 크기(작게 · 보통 · 크게, 보통이 디자인 시안 크기)만 바꿀 수 있어. 화면은 넓은 창에서도 오른쪽 끝까지 차. 세션 목록은 목록 위 줄 오른쪽 끝 ‹ 단추로 접고 같은 자리 › 로 펼쳐(키 [ 도 돼). 접어도 세션마다 동그라미가 남아 눌러서 바로 갈 수 있어. 글꼴(Pretendard)은 플러그인에 들어 있어서 어느 PC 에서나 같게 보여.
  • 갈래와 순서 막대 — 세션마다 "요구사항 만들기 → 개발 Spec → 개발하기" 같은 갈래(작업 흐름)를 골라 순서 막대로 지금 단계를 보여 줘. 갈래는 요구사항 만들기·개발 Spec·개발하기·설정하기·표준 기능으로 처리·작은 수정 여섯 개야(새 작업의 종류 버튼에도 "설정하기" 옆에 "표준 기능으로 처리 — SAP 표준 앱으로 끝나는 건" 이 있고, 밑의 작은 글에 설정 건·표준 건 수가 따로 보여). 순서의 정본은 콘솔이 아니라 플러그인의 workflow.json 이고, 단계마다 근거가 되는 스킬·규칙 문장이 달려 있어(콘솔은 그 파일을 읽어 그리기만 해). SRS 다음 단계가 설정 인 요구사항은 "설정하기" 갈래로 가고 화면에는 "설정 DEV-003" 처럼 보여(표준 도 같아). 설정·표준 건 세션은 숫자 띠에 "SRS 상태" 칸이 더 생겨서 그 요구사항의 Status 를 진행 중·끝처럼 보여 줘(작업 폴더의 SRS 를 읽고, 못 읽으면 "확인 못 함"). 개발하기에 ATC 단계는 없어(ATC 는 도구야). 개발이 안 끝나서 deliver 가 "브랜치에만 올리기" 를 고르면 PR 이 생길 때까지 올리기 단계가 안 끝나는데, 정상이야. 병합 기다리기는 위험하지 않은 PR 은 검사 통과 시 자동 병합, 위험한 PR 은 승인자 Approve, 사람 병합 경로는 사람이 GitHub 에서 병합이야. 작은 수정 갈래에서는 README 나 일반 문서(docs/ 아래, SRS·Spec 제외)만 바꾼 PR 은 검사가 모두 통과하면 Claude Code 가 바로 병합하기도 한다는 말이 병합 기다리기 힌트와 PR 카드에 붙어. 지금 단계의 스킬만 누를 수 있고, 건너뛰려면 이유를 적어야 해. "끝났어요" 는 실제로 바뀐 내용이나 검토 요청이 있는지 확인한 뒤에만 넘어가. 단계 이름은 쉬운 말이야("작업 시작하기", "올리고 검토 요청하기", "합쳐지기 기다리기"). srs·spec·start 스킬은 각각 시작할 때 작업 기록(이슈)과 작업 공간(브랜치)을 스스로 만들어.
  • 홈과 도구 줄 — 홈에는 숫자 타일(내 차례 · AI가 일하는 중 · 승인 기다리는 PR · 이번 주 산출물 — 이번 주 산출물은 최근 7일 안에 바뀐 문서 수 · 팀 기록 — "아직 안 풀린 문제 n건" 과 기록 화면으로 가는 [보기]. 기록을 못 읽으면 0건이 아니라 "? 확인 못 함"), 타일 바로 아래에 내가 올린 열린 PR 중 자동 검사가 실패한 것을 "고쳐야 할 내 PR n건" 줄로 보여 주고 [AI 에게 고치라고 하기] 를 누르면 그 PR 의 세션(없으면 새 작업 입력칸)에 고쳐 달라는 말을 넣어(내 PR 목록을 못 읽으면 줄이 아니라 "? 확인 못 함" 줄이 떠. 세션 표 상태 칩은 검사가 실패한 세션이면 "고쳐야 함". 검사가 실패한 내 PR 세션은 "내 차례" 숫자에도 들어가고 맨 위 띠가 "PR 의 검사 실패를 고쳐야 해" 로 알려 — 노랑 내 차례 카드에는 넣지 않고 이 빨간 줄이 대신해. 막힌 세션은 따로 세), 내 차례 노랑 카드(가장 오래 기다린 한 건만 카드로 두고, 나머지는 카드 아래 "외 n건" 을 누르면 펼쳐져),"내 세션" 표(작업·단계 막대·번호·기억·상태)와, GitHub 저장소에서 내가 승인자일 때만 "내가 승인할 PR" 이 나와(GitHub 저장소가 아닌 폴더는 따지지 않아). 세션 화면 아래에는 판 보기·최신 받기·플러그인 갱신·인계·남은 일·내 PR·다시 불러오기·ATC(env/adt-tiers.yaml 이 있을 때)·Role·CTS·매뉴얼 도구 줄이 늘 열려 있어. 작업 폴더에 templates/ 나 rules/ 가 없으면 홈과 세션에 "프로젝트 준비 안 됨" 안내가 뜨고 관리자용 "프로젝트 구조 만들기" 도구가 보여(새 고객사 갈래는 없어졌어). 준비 여부를 읽지 못하면 숨기지 않고 "확인하지 못했어요" 로 알려. 준비됐는데 templates/ 에 고객 양식 원본이 없으면 같은 자리에 "고객 양식이 아직 없어 · templates/ 에 고객사 양식 파일을 넣어야 문서를 양식대로 뽑을 수 있어. 양식 없이 md 로만 쓰는 프로젝트면 신경 안 써도 돼" 가 떠(읽지 못하면 안 떠). 플러그인 판이 바뀐 뒤 콘솔을 처음 열면 홈 맨 위에 "이번에 바뀐 것" 카드가 한 번 떠서(지난번 본 판 이후 판들의 줄, 새 판부터) [알겠어] 를 누르면 닫혀.
  • 글로 물어본 세션 — 세션이 결과 보고 끝에 물음표로 질문하고 멈추면 제목이 "내 답을 기다리는 듯해요(추정)." 로 나와. 물음표로 끝났는지 보고 짐작하는 거라 제목·홈 카드·할 일 목록 모두에 "추정" 이 붙어. 이번 턴에 받은 보고만 보니까, 답한 뒤 새 턴이 시작되면 풀려. git 상태로 짐작한 차례("작업 시작 차례" 등)는 그 아래 참고 한 줄로 내려가.
  • 승인 화면의 명령 칸 — 여러 줄 명령(heredoc 로 이슈·PR 본문을 쓰는 것 등)도 줄바꿈 그대로 보여 줘. 긴 줄은 접혀.
  • 만든 문서 — 세션이 만든 문서(md·xlsx·pptx 등)를 목록으로 보고 바로 미리볼 수 있어. 목록에는 폴더를 포함한 경로가 나와서 같은 이름 README.md 도 구분되고, 커밋한 뒤에도 이 세션이 만든 문서는 남고, "아직 커밋 안 됨" 인지 "지금 바뀐 것 없음(git 기준)" 인지 같이 보여(git 저장소가 아니면 커밋 여부를 모른다고 알려). 시작할 때 이미 바뀌어 있던 파일은 빼지만, 같은 폴더에서 다른 세션이 바꾼 파일은 구분 못 해서 섞일 수 있어(화면에도 적혀 있어). 목록이 500개를 넘어 잘리거나 git 상태를 못 읽었으면 그 뒤 30분 동안 그렇다고 알려 줘. 판 이름 파일(이름_v0.1.xlsx)은 한 줄로 묶고 이전 판은 접어서 보여 줘. 엑셀의 날짜 칸은 2023-03-01 처럼 날짜로 나와. 열기와 위치 보기도 돼.
  • 다음 갈래로 넘어가기 — 버튼 하나로 지금 세션에서 이어 가기 글을 받아 같은 폴더에 새 세션을 띄워. 새 세션은 최신 받기·플러그인 판 확인을 먼저 점검하고, 넘어간 이전 세션은 정상 종료되어 "다음 세션으로 넘어감 → 새 세션" 링크가 남아. 같은 폴더에서 다른 세션이 일하면 알려 주고 작업용 폴더를 따로 만들 수 있어.
  • 쉬는 터미널 세션은 못 움직여 — 이미 열려 있는 터미널 세션이 쉬는 중이면 바깥에서 새로 시킬 수 없어서 입력칸이 막히고, 그 이유는 입력칸 아래에 반말로 한 번만 나와. 일하는 중이면 턴이 끝날 때 이어서 전달돼.
  • 권한 확인을 건너뛰는 모드(bypassPermissions) 로 도는 세션은 승인 요청이 안 와서 웹에서 답할 일이 없어. 화면에 그렇게 표시해.

훅이 늘었어. 이 플러그인을 켜면 도구 호출 전후·프롬프트·턴 끝·서브에이전트·세션 시작과 끝 같은 이벤트를 127.0.0.1:4873 으로 알려 주는 훅과, 승인(PermissionRequest)·질문(AskUserQuestion)을 웹에 물어보는 훅이 같이 걸려. 상태만 알리는 훅은 async 로 돌아서 세션을 기다리게 하지 않고, 승인·질문·턴 끝·세션 끝 훅만 동기야. 콘솔이 꺼져 있으면 연결 실패를 조용히 넘겨서 오류 줄 없이 세션이 막히지 않고 평소대로 터미널에서 물어봐. 콘솔이 켜진 채 브라우저를 열어 두면 그 동안 터미널 세션의 질문은 웹에서 최대 5분 기다린 뒤 터미널로 넘어가. 고객이 원하는 걸 요구사항정의서(SRS, Software Requirements Specification) 한 장에 처음 정리하는 일이야. 예전 이름 "PRD(Product Requirements Document)" 로 불러도 같은 스킬이 돌아.

이럴 때
고객 요구사항을 처음 받았을 때. docs/ssot/SRS.md 가 빈 틀일 때. 새 프로젝트라면 여기가 첫 단계야.

고객사에 낼 때는 이 주문서를 고객사 양식(Backlog 엑셀)으로 옮겨 찍어. 그리고 "처음 썼다" 는 사실을 일기장(audit/changes/)에 남겨.

SRS 의 생김새

절

배경과 목표 · 범위 · AS-IS/TO-BE · 요구사항 · 참조 · 미결 사항. 맨 위에 버전: 0.1 줄이 있고, 이 값이 엑셀 파일명의 버전이 돼.

요구사항 표 열

ID(Identifier), Title, LoB, Type, Status, Priority (PO), Development RICEFW(Reports, Interfaces, Conversions, Enhancements, Forms, Workflows) ID, 출처, 다음 단계. 양식 지도에 있는데 표에 빠진 열이 있으면 Claude 가 열을 더하고 채워. 출처와 다음 단계는 마크다운에만 있고 엑셀에는 안 나가. 이 밖의 이름(양식 지도에 없는 열, 오타 낸 열)은 쓸 수 없어 — 표 열과 상세 절 #### 소제목 모두 저장할 때와 PR 에서 거절돼.

### REQ-002 판매오더 조회
#### Short Description
요청: 홍길동(영업팀), 2026-10-12, 회의록
판매오더를 기간별로 조회한다 (요약만)
#### Acceptance Criteria
- 세부 기능은 여기에
…

상태(Status)는 이 일곱 가지뿐이야

NewPlannedIn ProcessDoneOn HoldDroppedDuplicate

다음 단계에 따라 길이 갈라져

요구사항이 SRS 다음에 어디로 가는지는 표의 다음 단계 열에 적어. 값은 넷뿐이고, 오타를 내거나 비워 두면 PR 검사(번호 짝)가 위반으로 막아. Development RICEFW ID 가 빈칸이어도 이 열을 보면 "설정·표준이라 비웠다" 인지 "아직 안 정했다" 인지 알 수 있어.

다음 단계RICEFW ID그다음
개발DEV-003(구매요청 승인, REQ 와 같은 번호)Spec(Specification) 을 만들어 → 개발해 (/harness:spec → /harness:start)
설정비움Spec 없이, 진행 원장에도 안 올리고 SRS 의 Status 로 관리해 → [DEV-003] 이슈로 시작하면 Status 가 In Process → 설정을 마치고 무엇을 설정했는지 SRS 의 Configuration Considerations 에 적으면 Done
표준비움SAP 표준 기능(표준 앱)으로 해결되는 건이야. 설정과 같이 Spec 도 원장도 없이 SRS 의 Status 로 관리해. 어느 표준 앱·기능으로 되는지를 SRS 의 Configuration Considerations 에 적고 Done
미정비움미결 사항에 남겨 두고(/harness:srs), 정해지면 이 열을 고쳐. 바로 Spec 을 만들고 싶으면 /harness:spec 이 그 자리에서 개발인지 설정·표준인지 정해
보류 · 취소그대로다음 단계가 아니라 Status 로 적어: On Hold · Dropped · Duplicate 면 Spec 도 안 만들고 멈춰. 원장에 줄이 있으면 지우지 않고 내용 앞에 [보류] · [취소] 만 붙여
설정·표준 → 개발로 바뀜DEV-003 을 채움옛 원장에 설정 줄이 있었다면 그대로 쓰고 Spec 칸만 "-" 로 되돌려. 그다음 /harness:spec 이 이어받아

고객 양식에 Type 같은 종류 드롭다운이 있고 양식 지도에 대응표가 있으면, Type 을 고르는 것으로 다음 단계가 정해져(예: SSCUI → 설정, Process → 표준, Developer Extensibility → 개발). 따로 또 묻지 않고, 하나로 안 정해지는 값(예: Key User Extensibility)만 개발/설정을 한 번 더 물어. 서로 어긋나게 적으면 PR 검사가 경고로 알려 줘(막지는 않아).

다음 단계를 나중에 바꾸면(미정 → 설정·표준, 개발 → 설정) 변경 기록에 종류 "결정" 으로 남아.

내 번호 알아 두기

요구사항 한 줄에 번호 하나야. REQ-003(구매요청 승인)을 받으면 그 일의 이슈는 [DEV-003], Spec 은 DEV-003-….md, 원장의 개발 건도 DEV-003 이야. 다음 단계는 다 이 번호로 말해. Claude 도 번호를 말할 때 늘 REQ-003(구매요청 승인) 처럼 제목을 괄호로 붙여서, 번호만 보고 무슨 일인지 헷갈리지 않게 해.

  • Spec 만들 때: "REQ-003(구매요청 승인) 스펙 만들어줘"
  • 요구사항이 바뀌거나 취소될 때: "REQ-003(구매요청 승인) 취소됐어"
  • 개발 시작할 때: [DEV-003] 이슈로 /harness:start

SRS 를 만들거나 고친 끝에 Claude 가 새로 찜한 번호를 표로 꼭 알려 줘. 잊었으면 docs/ssot/SRS.md 요구사항 표의 ID 열, 또는 GitHub 이슈 제목 앞의 [DEV-xxx] 에서 찾아. 고객사 양식의 개발 ID(CO-006-01)와는 다른 번호야.

번호
REQ 번호는 Claude 가 번호표 기계로 받아서 붙여. 마지막 번호에 손으로 1 을 더하지 않아. 새 제목이 이미 있는 REQ 제목을 포함하거나 반대로 그 안에 들어 있으면 번호표 기계가 번호를 안 주고 "기존 개발의 하위 작업이야, 새 개발이야?" 를 물어봐. 하위 작업이면 새 줄 대신 그 REQ 를 넓히고, 정말 새 개발이면 확인했다는 표시를 붙여 다시 받아.
다른 번호 적기
상세 절에 다른 요구사항 번호(REQ-002(판매오더 조회 앱), DEV-002)를 적으면 저장이 거절돼. 같은 개발이면 새 REQ 로 쪼개지 말고 그 REQ 의 범위를 넓혀. 정말 별개면 ### REQ-003 제목 바로 아래, 첫 #### 소제목 앞에 관계: 별개 — 이유 한 줄을 적어(이 자리는 엑셀로 안 나가). 자기 번호의 DEV(Development) 와 옛 REQ-001 처럼 앞에 "옛" 이 붙은 표기는 괜찮아.
양식 밖 열
요구사항 표의 열과 상세 절 소제목(#### …)은 양식 지도의 열 이름, 지도의 md 전용 열(출처 등), 다음 단계 만 쓸 수 있어. 열을 새로 만들거나 이름을 틀리게 쓰면 저장이 "양식 밖 열: X. 허용: …" 으로 거절되고, PR 의 doc-guard 도 같은 이유로 막고, 엑셀 산출도 멈춰(조용히 빠뜨리지 않아). 지도에 있는 열이 표에 빠진 건 괜찮아. 정말 필요한 열이면 열을 만들지 말고 양식 지도를 먼저 고쳐. 지도가 없는 저장소는 SRS 틀의 열(ID, Title, Status, Priority (PO), 출처, 다음 단계)과 소제목 설명 · 완료 조건 이 기준이야.
긴 칸
Short Description 은 몇 줄짜리 요약으로 써. 엑셀 한 칸은 높이 한계(409pt)를 넘으면 잘려 보여. 세부 기능은 Acceptance Criteria 로 나눠. 산출 때 cell-too-tall 경고가 나오면 그 칸이 너무 긴 거야.
옛 이름
docs/ssot/PRD.md 만 있는 옛 구조면, 조용히 새로 만들지 않고 옮길지 먼저 물어봐.
승인 필요
SRS 를 바꾼 PR 은 작성자 말고 다른 승인자의 Approve 가 있어야 병합돼.

SRS(Software Requirements Specification) 고치기

고객이 요구사항을 바꾸거나, 더하거나, 취소했을 때 정본을 고치는 일이야.

이럴 때
요구사항이 추가·변경·취소됐을 때. 우선순위나 상태가 바뀌었을 때.
이렇게 말해
요구사항 바뀌었어SRS 수정REQ-002(판매오더 조회 앱) 취소됐어/harness:srs
쉽게
말하면

주문서를 고칠 때는 지우개를 쓰지 않고 줄을 그어. 취소된 주문도 "취소" 라고 적어서 남겨 둬야 나중에 "그거 왜 없어졌어?" 에 답할 수 있어.

주문서를 고치면 그걸 보고 만들던 레시피(Spec(Specification))도 영향을 받아. 그래서 Claude 가 어떤 레시피가 걸리는지 같이 찾아 줘.

REQ 고치기번호는 그대로
영향 찾기걸리는 Spec · 원장 보여 줌

지우지 마

승인 받은 뒤에 커밋을 더 올리면 승인을 다시 받아야 해. 승인은 마지막 커밋에 찍힌 것만 쳐줘.
덮어쓰기
main 에 이미 있는 판(같은 파일명)은 덮어쓰지 않아. 그래서 버전을 꼭 올려.
하지 않는 것 꼬리표
범위의 "하지 않는 것" 항목이 특정 요구사항에서 뺀 일이면 항목 끝에 (REQ-001) 을 붙여(여러 개면 (REQ-001, REQ-002)). 꼬리표가 없으면 프로젝트 전체에서 안 하는 일이야. 새 요구사항 제목이 이런 항목과 포함 관계이거나 핵심 단어가 둘 이상 겹치면 번호 찜이 멈추고 "REQ-001 에서 안 하기로 한 일" 이라고 알려 줘. 꼬리표만 붙이거나 떼는 건 PR(Pull Request) 에서 "항목이 바뀜" 으로 안 쳐. 범위 절은 엑셀로 안 나가.
새 줄 말고 넓히기
새 요구사항을 넣기 전에 Claude 가 지금 있는 개발 목록을 보여 주고 "기존 개발의 일부야, 새 개발이야?" 를 물어. 일부면 새 줄을 만들지 않고 그 REQ 의 범위와 완료 조건을 넓혀. 그 REQ 의 "하지 않는 것" 에 적혀 있던 걸 하게 된 거라면 거기서 빼서 범위로 옮겨. 변경 기록 종류는 "요구사항 변경" 이야. 설정만 하는 별개 건처럼 정말 따로면 새 줄이야.
관계 줄
고치다가 상세 절에 다른 번호를 적게 되면 그 절 제목 아래(첫 #### 앞)에 관계: 별개 — 이유 를 적어야 저장돼. 같은 개발이면 번호를 적을 게 아니라 범위를 넓히는 거야.

Spec(Specification) 만들기

SRS(Software Requirements Specification) 의 요구사항 하나를 골라 개발 설계(Spec)를 쓰는 일이야. 요구사항 1건 = 개발 1건 = Spec 1장.

이럴 때
개발에 들어가기 전, 무엇을 어떻게 만들지 정할 때. 고객사가 개발사양서를 달라고 할 때.
이렇게 말해
스펙 만들어줘REQ-002(판매오더 조회 앱) 개발 스펙/harness:spec
쉽게
말하면

주문서(SRS)에 "판매오더를 조회하고 싶다" 가 있으면, 요리사가 보는 레시피 카드(Spec)를 한 장 써. 주문 번호가 REQ-002 면 레시피 번호도 DEV-002(DEV = Development) 야.

고객사가 자기 양식(개발사양서 엑셀)으로 달라고 하면, 레시피 카드를 그 양식에 옮겨 찍어 줘.

고객사 양식은 빈 틀이고, 양식 지도(templates/forms/*.yaml)는 "이 칸엔 제목, 저 칸엔 상태" 하고 적어 둔 안내도야. 엔진은 안내도를 보고 정본의 내용을 틀에 찍어 내.

틀의 서식과 그림은 건드리지 않아. 내용 칸만 채워. 다만 개발사양서 화면 시트는 지도에 화면: 영역이 있으면 Spec 의 #### 화면 N 그림(필터 바·액션·결과 테이블)을 그 영역에 셀과 색으로 그려 넣어. 영역을 넘으면 자르지 않고 거절해. 새 판이면 main 에 있는 지난 판 Spec 과 화면 그림을 비교해, 추가·수정은 노란색, 삭제는 회색 취소선으로 번호(①②…)와 함께 표시하고 지도 변경: 의 변경 내용 표에 구분·대상·내용을 채워(순서만 바뀐 건 표시 안 해). 지난 판을 못 읽으면 통과시키지 않고 "검사 불능" 으로 멈추니 git fetch 뒤 다시 해. 지도에 캡처: 가 있는 화면은 Spec 의 #### 화면 N 캡처 의 PNG(Portable Network Graphics) 를 그 영역에 비율대로 넣고(늘리지 않고, 원본의 50% 미만으로 줄여야 하면 멈춰) 번호별 설명을 지도가 정한 칸에 채워. 파일 이름의 판이 산출 판과 다르거나 파일이 없으면 멈춰. 표가 샘플보다 길어져도 지도에 서식_행·묶음_열 이 있으면(예: Public Logic) 이벤트 묶음마다 샘플의 테두리 모양(첫·중간·끝·한 행)을 그대로 복제하고, 안 쓴 샘플 행의 테두리는 지워.

양식 지도에 견본_검사: true 가 있으면, 템플릿에 남은 다른 개발 건의 견본(글자·그림·메모)이 산출물에 섞일 때 산출이 거절돼(leftover-sample). 어느 시트 몇 번 칸인지 알려 주고, 빈 양식 만들기로 템플릿을 비우거나 고정 문구면 지도의 유지 에 넣으라고 안내해. 머리글·바닥글과 직접 적은 드롭다운 목록은 견본인지 가를 수 없어 경고로만 알려.
직접 고친 엑셀
엑셀을 오피스로 직접 고쳐도 돼. 다만 경비원(Hook)은 그걸 못 보니까, PR 에서 Actions 가 처음 검사해.

사용자 매뉴얼 만들기

화면 캡처와 설명을 담은 작업본(마크다운)을 쓰고, 고객사 매뉴얼 양식(pptx)으로 뽑는 일이야. 매뉴얼은 업무 영역(LoB(Line of Business))별 폴더에 업무 제목마다 파일 하나씩 둬.

이럴 때
개발이 끝나 사용자에게 줄 매뉴얼이 필요할 때. 예전에 마크다운으로 쓴 매뉴얼을 고객사 양식으로 옮길 때. 개발 전에 내가 양식 pptx 에 직접 써서 올린 매뉴얼을 작업본으로 읽어 들일 때.
이렇게 말해
매뉴얼 만들어줘내가 쓴 매뉴얼 pptx 읽어 들여줘매뉴얼 캡처해 줘생산계획 보드 매뉴얼 pptx 로 뽑아줘/harness:manual
쉽게
말하면

가전제품 사용설명서를 만드는 일이야. 제품(개발 건)마다 설명서를 따로 쓰지 않고, 쓰는 사람 입장의 업무(예: 생산계획 보드) 하나에 설명서 한 부를 쓰고, 그 안에 관련 개발 건 번호를 적어 둬.

화면 위의 빨간 네모와 번호는 캡처 도구가 그림에 직접 그려 줘. "매뉴얼 캡처해 줘" 라고 하면 네가 로그인해 둔 전용 Chrome 에 붙어서 화면을 찍고, 화면에 보이는 이름으로 위치를 찾아 네모와 번호를 그려. 산출(pptx)은 그림 파일의 경로만 받아서 양식의 그림 자리에 넣어.

매뉴얼을 개발보다 먼저 쓰는 사람은 거꾸로 해도 돼. 양식 pptx 에 실제 데이터로 직접 써서 올리면 Claude 가 칸 위치를 보고 작업본(마크다운)과 그림 파일로 읽어 들여. 못 읽은 글은 버리지 않고 목록으로 보여 주면서 어디에 넣을지 너한테 물어봐. 올린 파일은 첫 판(v0.1)으로 그대로 남고, 개발 뒤 캡처를 반영한 판이 다음 판(v0.2)이야.

  • LoB, 업무 제목, 묶을 개발 건(DEV(Development) 번호)을 알려 줘
  • 화면 캡처는 "매뉴얼 캡처해 줘" 라고 하면 돼. 먼저 화면마다 찍을 요소(필터·버튼·열·그 밖)와 번호 설명을 작업본 옆 <번호>.<업무 제목>.capture.yaml 에 적어. 테넌트 주소는 env/manual-capture.yaml 에 테넌트: https://… 만 적어(비밀번호·토큰은 넣지 마. 클라이언트는 ?sap-client=100 처럼 sap-client·sap-language 쿼리만 붙일 수 있어)
  • 전용 Chrome 이 뜨면 그 창에서 네가 직접 로그인하고, 찍을 앱 탭을 하나만 남겨. 캡처 중에는 그 창을 최소화하지 마(다른 창 뒤에 있는 건 괜찮아). 최소화돼 있으면 Claude 가 다시 띄우고, 그래도 안 보이면 찍지 않고 멈춰. 끝나면 Claude 가 창을 닫고 로그인 정보가 든 임시 프로필 폴더를 지워
  • 필터에 기본값이 이미 들어 있으면 찍을 화면 목록에 그 값을 또 넣지 마. 같은 값을 다시 넣으면 SAP 이 오류 창을 띄우고, 오류 창이 떠 있는 화면은 찍지 않고 멈춰. 버튼 이름은 로그인한 언어로 화면에 보이는 글자 그대로 적어(예: Go 가 아니라 실행)
  • 같은 이름이 화면에 둘 이상이면 도구가 고르지 않아. 어느 것인지 index(1부터, 위에서 아래·왼쪽에서 오른쪽)를 네가 적어. 못 찾은 요소는 그리지 않고 목록으로 알려 줘. 찾은 것만 그린 그림은 _미완_ 이 붙은 이름으로 따로 저장되고 작업본은 안 바뀌어
  • 화면마다 캡처 파일(PNG(Portable Network Graphics))은 docs/manual/img/<LoB>/<화면 이름>_v<판>.png 로 생기고 작업본의 그림 경로와 번호 설명이 채워져. 캡처가 없는 화면은 빈칸으로 통과시키지 않고 어느 화면이 빠졌는지 목록으로 알려 줘
  • 캡처가 끝나면 Claude 가 새 그림과 설명을 맞대 보고, 빠졌거나 달라진 설명의 고친 안을 화면별 표로 보여 줘. 네가 고른 것만 작업본에 반영해. 그림만으로 맞는지 모르는 건 지어내지 않고 너한테 물어봐. 빠진 항목은 찍을 목록(capture.yaml)에 더해서 그 화면만 다시 찍는데, 이때 다시 로그인해야 해. 번호 설명을 고치면 목록의 설명도 같이 고쳐서 다음 캡처가 되돌리지 않아
  • 화면의 값이 맞는지 시험하고 싶으면 "매뉴얼 데이터로 시험 목록 만들어 줘" 라고 해. Claude 가 작업본 글에서 넣을 값과 나와야 할 결과를 뽑아 표로 보여 주고, 네가 고른 것만 capture.yaml 의 확인 에 써. 조회 화면만 해(저장·전기는 안 해). 시험할 화면과 테넌트를 먼저 확인하고 운영 테넌트는 쓰지 않아
  • 매뉴얼을 먼저 썼다면 양식 pptx(templates/)에 직접 쓰고, 파일 이름은 산출 파일명 규칙대로(사용자매뉴얼_<LoB>_<번호>.<업무 제목>_v0.1.pptx) 지어서 "내가 쓴 매뉴얼 pptx 읽어 들여줘" 라고 해. 칸을 옮겨도 조금이면 괜찮지만 크게 옮기거나 지우면 그 칸은 "못 찾음" 이 되어 작업본에 미정 으로 남아. 메모로 붙인 글상자처럼 옮기지 못한 글은 목록으로 보여 주고 어디에 넣을지 물어봐. ## 묶은 개발 건 은 pptx 에 없는 정보라서 DEV 번호를 물어봐서 채워
  • 산출된 pptx 는 PowerPoint 로 열어 쪽마다 눈으로 확인해. 글이 넘치거나 겹치는지는 화면 없이 확인할 수 없어서 엔진이 "검사 불능" 으로 알려 줘
  • 내용이 바뀌면 작업본 머리의 버전: 을 올리고 다시 뽑아. 이전 판 pptx 는 지우지 않고 남아

작업본은 머리의 버전: 0.1, ## 묶은 개발 건 표(| DEV | 제목 |), ## 양식 항목 순서야. ## 양식 항목 아래 ### <양식> · 표지 · 목차 · 끝은 한 소절씩, 본문은 ### <양식> · 본문 · <화면 이름> 소절을 화면마다 하나씩 써. 본문 소절에는 | 항목 | 값 | 표(업무명·화면 제목·기능 설명), #### 그림(저장소 루트 기준 PNG 경로), #### 번호 설명(1. 글 목록)이 들어가. 쪽 이름과 항목 이름은 양식 지도에서 읽으니 양식이 바뀌면 지도의 이름을 따라. 지도에 없는 쪽·항목은 저장할 때와 PR 이 "양식 밖" 으로 거절하고, 파일 이름(^\d+\..+\.md$)과 묶은 개발 건 표도 rules/manual.yaml 이 검사해. 산출 폴더와 파일 이름의 {LoB} 같은 자리는 작업본 값으로 채워져.

산출 ≠ 통과
pptx 가 나왔다고 문서 검사를 통과한 건 아니야. 파일 이름은 PR(Pull Request) 의 doc-guard 단계가 rules/manual-output.yaml 로 검사해.
캡처 보안
전용 Chrome 의 디버깅 포트는 127.0.0.1(내 PC 안)에만 열려. 다른 주소로 붙으라고 하면 도구가 거부해. 로그인 정보가 든 프로필 폴더는 저장소 밖 임시 폴더에 두고 끝나면 지워. 캡처 그림에는 화면의 업무 데이터가 그대로 찍히니 올리기 전에 고객에게 내도 되는 데이터인지 확인해.
캡처 못 하는 것
여러 화면을 거쳐야 하는 준비는 못 찍어. 가로 스크롤 밖 열 여러 개는 다 보이는 위치 하나로 한 번에 넘겨서 찍고, 한 화면에 안 들어가면 "검사 불능" 으로 알리면서 화면을 나눌 방법(1화면 [상태, 취소], 2화면 […])과 필요한 배율: 0.9 를 제안해. 화면에 배율(0.5~1.0)을 적으면 그 화면만 축소해 찍고 그림은 그대로 1600x900 이야. 준비 단계는 필터 값 넣기, 드롭다운 고르기("선택"), 버튼 누르기, 팝업 열기뿐이야. 팝업은 준비: [{누르기: 실행}, {팝업: 그루핑}] 처럼 마지막에 한 번만 쓰고, 그 버튼을 눌러 대화상자가 딱 하나 떠야 해(안 뜨거나 오류·경고 창이면 "검사 불능"). 표 칸을 더블클릭해야 열리는 팝업은 {팝업: 백로그상태, 행: 3} 처럼 열 이름과 보이는 행 번호를 적어(칸 안 아이콘이 있으면 그 아이콘을 눌러). 비어 있는 칸이라 안 뜨면 다른 행을 고르라고 알려 줘. 더블클릭은 데이터를 바꾸지 않는 칸에만 써. 표시 요소는 그 팝업 안에서만 찾고, 확인·저장은 누르지 않아. 앱이 기억해 둔 필터 값이 이미 같으면 넣지 않고 넘어가고, 다른 값이면 지우고 넣어. 페이지가 30초 안에 준비되지 않으면 통과가 아니라 "검사 불능" 으로 알려 줘. 확인({열, 값}·{열, 행, 값}·{글자})은 값을 읽기만 하고 화면마다 "맞음/다름/검사 불능" 을 알려 줘. 읽지 못한 건 맞음도 다름도 아니고 "검사 불능" 이야. 값 은 "0010" 처럼 따옴표로 감싼 글자로 써(숫자 그대로면 거부해). 입력칸·체크박스·아이콘 칸은 글자로 읽을 수 없어 "검사 불능" 이고, 열 전체 확인은 보이는 행만 읽으니 결과의 "읽은 행 수" 를 같이 봐.
그림 이름
그림 파일 이름 끝에 판(_v0.1)을 붙이길 권하지만, pptx 산출은 이 이름을 검사하지 않아. 판을 올릴 때 캡처를 다시 찍었는지는 사람이 챙겨.
예시 글자
양식에 예시 글(날짜, "예시:" 안내)이 있는 쪽은 지도가 가리킨 것만 바뀌어. 지도의 칸 이나 지우기 에 넣지 않은 글은 산출물에 그대로 남으니 PowerPoint 확인 때 같이 봐.
읽어 들일 때
올린 pptx 에서 표는 읽지 않고, 같은 작업본이나 그림이 이미 있으면 덮어쓰지 않고 멈춰. 양식과 쪽 크기가 다르거나 쪽을 양식에 맞춰 보지 못해도 아무것도 쓰지 않고 "검사 불능" 으로 알려 줘. 넣은 값과 나와야 할 결과는 작업본 글에서 Claude 가 시험 목록으로 뽑아 네 확인을 받아(조회 화면만).
옛 매뉴얼
예전 docs/manual/DEV-xxx-….md 는 화면 단위로 잘라 새 작업본으로 옮겨 줘. 화면에 묶이지 않는 글(자주 묻는 질문 등)은 목록으로 알려 주고, 옛 파일은 네가 정할 때까지 지우지 않아.

CTS 관리대장 쓰기

트랜스포트 요청(CTS(Change and Transport System)) 한 건을 한 줄로 적어 두는 관리대장이야. 요청 건과 Error 내역을 작업본(마크다운)에 쌓고, 고객사 양식(엑셀)으로 뽑아. 대장은 Configuration 용과 CBO(Custom Business Object) 용 두 가지야.

이럴 때
트랜스포트 요청을 만들었거나 처리해서 관리대장에 남겨야 할 때. CTS 처리 중 Error 가 나서 조치를 적어 둬야 할 때.
이렇게 말해
CTS 관리대장에 추가해줘트랜스포트에서 채워줘Error 내역 추가해줘관리대장 엑셀로 뽑아줘/harness:cts
쉽게
말하면

택배 접수 장부 같은 거야. 요청이 들어올 때마다 한 줄씩 적고, 장부가 두꺼워지면 "2권" 으로 새로 묶되 1권은 그대로 서랍에 둬.

이 스킬은 네가 알려 준 값과, SAP 에서 읽기만 해서 가져온 트랜스포트 정보를 적어. 요청 번호·설명·요청자·대상 시스템은 "트랜스포트에서 채워줘" 라고 하면 SAP 에서 읽어 오고, 요청일·오픈단계·모듈처럼 SAP 가 모르는 칸은 비워 두니 네가 알려 줘.

이럴 때
Spec 이 끝나고 개발을 시작할 때([DEV-xxx] 이슈로). 버그 수정, 문서 손보기, 설정 건처럼 SRS·Spec 스킬을 안 거치는 일을 시작할 때. SRS·Spec 을 만들거나 고칠 땐 부르지 않아도 돼 — 그 스킬이 브랜치부터 알아서 확인해.
이렇게 말해

쉽게
말하면

main은 가게 진열대야. 손님(고객사)이 보는 완성품만 올라가. 진열대 위에서 바로 만들다가 넘어뜨리면 큰일이니까, 뒤편에 내 작업대(브랜치)를 하나 펴고 거기서 만들어.

이슈는 작업대 옆에 붙이는 작업지시서야. "왜, 무엇을, 언제 끝난 걸로 칠지" 가 적혀 있어.

브랜치에서 여러 번 커밋해도, 병합할 때는 하나로 접혀서(squash) 진열대에 올라가.

start 가 해 주는 일

  1. 저장 안 한 변경이 있으면 먼저 정리할지 물어봐
  2. main 으로 가서 GitHub 최신 상태를 받아 와. worktree 에서 열어 main 으로 못 옮기면 GitHub 의 최신 main(origin/main)에서 바로 브랜치를 따
  3. GitHub 이슈를 만들어 (제목 명사형, 본문은 배경 / 해야 할 일 / 완료 조건, 라벨 type:feat 등)
  4. 개발 건(feat, fix)이면 먼저 지금 있는 개발 목록(번호·제목·LoB·다음 단계·상태)을 보여 주고 "기존 개발의 하위 작업이야, 새 개발이야?" 를 물어. 새 개발이면 이슈 제목 앞에 번호를 찜해. 예: [DEV-003] 구매요청 승인
  5. SAP 소스(src/)를 고치는 개발은 그 개발의 Spec 이 main 에 이미 있어야 시작해. 없으면 이슈도 브랜치도 안 만들고 "Spec 이 아직 main 에 없어서 시작할 수 없어요, 먼저 /harness:spec" 이라고 멈춰. Spec 이 있어도 그 개발의 요구사항(REQ)이 SRS 에 없으면 시작하지 않고 "먼저 /harness:srs 로 요구사항을 올려요" 라고 멈춰. 새 개발이면 요구사항(/harness:srs)과 Spec 이 먼저 병합돼 있어야 해. src/ 를 안 고치는 일(템플릿·규칙·문서 수정)과 SRS·Spec 을 쓰는 일은 안 막아. 개발인지 애매하면 "이번 작업이 SAP 소스를 고치는 개발이야?" 하고 물어. 원장 SRS 다음 단계가 설정·표준 인 건(옛 원장은 Spec 칸이 설정 인 건)은 개발이 아니라서 안 막아. 나중에 PR 검사(spec-ready)가 같은 기준으로 한 번 더 봐
  6. 기능이 여럿인 개발은 하위 작업으로 쪼개 시작해. 하위 작업 하나가 PR(Pull Request) 하나라서, 앱 통째로 PR 하나가 되지 않게 이번에는 기능 하나만 이슈 범위로 잡아
  7. 하위 작업이면 번호를 새로 안 받아. 제목 끝에 붙여: Launchpad 타일 노출 (DEV-002). 본문에는 "DEV-002(DEV = Development) 하위 작업" 과 대표 이슈 링크를 적어
  8. 규칙에 맞는 브랜치를 만들고 이동해
  9. 내 열린 PR(Pull Request) 이 있으면 "먼저 병합할 수 있는 내 PR: #n" 을 알려 주고, 승인 대기·검사 실패인 PR 은 한 줄로 요약해. 알려 주기만 하고 시작은 막지 않아. 상태를 못 읽으면 "PR 상태 확인 불능" 한 줄만 말하고 계속해
  10. 진행 원장에 이미 있는 건(예: /harness:spec 이 Spec 만 올려 둔 건)은 묻지 않고 "대기" 줄을 "진행" 으로 바꿔 ("완료" 줄이면 바꿀지 물어. "리뷰" 줄은 GitHub PR 로 이유를 확인해서, 이미 합쳐진 Spec PR 때문이고 같은 개발의 열린 PR 이 없으면 묻지 않고 "진행" 으로 바꿔. 열린 PR 이 있거나 확인하지 못하면 물어). 원장에 없는 새 건(feat, fix)이면 줄을 넣을지 물어봐 (넣으면 상태 "진행")

개발 · 기타 작업 열기 · /harness:prs

내 PR(Pull Request) 확인하기

내 PR 이 지금 어디까지 왔는지, 무엇부터 병합해야 하는지를 GitHub 에서 계산해서 보여 줘. 읽기만 하고 아무것도 바꾸지 않아.

이럴 때
PR 을 여러 개 올려 놓고 어떤 게 막혔는지 모르겠을 때. 다른 세션에서 만든 PR 까지 한눈에 보고 싶을 때. 병합 순서를 정해야 할 때.
이렇게 말해
내 PR 어때?PR 상태뭐부터 병합해?팀원별로 보여 줘/harness:prs
쉽게
말하면

계산대 앞에 줄 선 손님들을 한 번에 보여 주는 전광판이야. 누가 지금 계산할 수 있고, 누가 서류(승인)를 기다리고, 누가 앞사람을 기다려야 하는지 적혀 있어. 세션을 열 때도 내 PR 이 있으면 자동으로 띄워 줘. 세션 시작은 안 붙들고 뒤에서 만들어 두었다가 첫 프롬프트에 보여 줘.

출력은 표 두 개야

첫 표는 "내가 지금 할 수 있는 일", 둘째 표는 "내 PR 과 그 줄기" 야. 예를 들면 이런 모양이야.

할 일PR
병합하기#244 제목… (사람이 GitHub 에서 병합해야 하면 그 말이 붙어)
고치기#321 제목… — 검사 실패: ai-review / review
기다리기#303 제목… — blueward-huiseong·csh-dot123 승인

  • 할 일 — 병합하기는 병합 가능이고 앞에 기다릴 PR 이 없는 것, 고치기는 검사 실패·충돌·순서 판정 불능처럼 내가 손볼 것, 기다리기는 승인 대기·검사 중·앞 PR 대기·초안이야. — 뒤는 짧은 사유야.
  • 줄기 — 같은 DEV 번호를 가진 PR 묶음 한 줄이야(번호는 PR 제목 끝의 (DEV-007), 브랜치, 바꾼 Spec(Specification) 파일, 본문 순으로 읽어). 내 PR 은 굵게 나오고, 남의 PR 도 내 줄기 안에 있으면 내 앞뒤라서 같이 보여. 같은 단계의 갈래는 (#a, #b) 로 묶고, 다른 줄기의 PR 이 먼저여야 하면 ✅(앞: #244) 꼬리표로 알려 줘. 줄기 이름은 DEV-007(제목) 이고, 제목은 그 줄기 PR 중 제목 끝이 (DEV-007) 인 것의 제목(없으면 DEV-007 뒤 문구, 그것도 없으면 가장 먼저인 PR 의 제목)에서 가져와. 번호를 못 읽은 PR 은 앞뒤로 이어진 DEV 줄기가 하나뿐이면 그 줄기에 들어가고, 둘 이상에 걸치거나 혼자면 "줄기 없음" 에 모여.
  • 기호 — ✅ 병합 가능 · ⏳ 기다리는 중 · ❌ 고쳐야 함 · 📝 초안 · ❓ 판정 불능 · ⚠ 주의 있음(기호 뒤에 붙고, 내용은 표 바로 아래 "주의:" 줄에 있어. 예: 사람이 병합할 경로인지 확인 못 함)
  • 팀원별 현황 — "팀원별로 보여 줘", "팀 현황" 이라고 하면 --team 으로 사람마다 진행(최근 7일 병합, 열린 PR 의 마지막 커밋)·막힘(검사 실패 이름과 사유, 충돌, 승인 대기, 앞 PR 대기)·오래 머문 일(사람이 마지막으로 손댄 때 — 커밋·코멘트·리뷰, 봇 제외 — 로부터 PR 3일, 담당 이슈 14일 넘게 움직임 없음)·맡은 개발 건(audit/ledger)을 묶어 보여 줘. 여러 PR 이 같은 사유로 실패하면 맨 위 "공통 원인" 에 한 번만 나오고, 읽지 못한 칸은 "확인 불능" 으로 적혀(없다는 뜻이 아니야). 담당자 없는 열린 이슈도 따로 나와. 원장 담당 칸에 실명이 적혀 같은 사람이 두 칸으로 갈리면 기본 브랜치의 .github/harness-team.yaml 에 별칭: 아래 이름: GitHub아이디 를 적어 합칠 수 있어. --json 으로 같은 내용을 받을 수 있어.
  • 원장 줄 — 표 아래에 ⚠ #347 원장 DEV-010(…) 이 '리뷰' 야 가 나오면, 그 PR 이 대표 [DEV-xxx] 이슈를 닫는데 PR 브랜치의 진행 원장이 아직 완료 가 아니라는 뜻이야(옛 판으로 만든 PR). 병합 전에 고쳐야 해서 Claude 가 먼저 "원장을 완료로 고쳐 다시 올릴까?" 하고 물어. "응" 하면 그 PR 브랜치에서 작업 올리기가 원장만 고쳐 올려 줘. 하위 작업 PR 이나 이미 완료인 건 안 나오고, 원장 행을 못 읽으면 ❓ 판정 불능 으로 따로 나와.
  • 더 자세히 — /harness:prs --verbose 를 주면 표 아래에 긴 승인 사유와 "같은 파일을 고친 PR" 주의를 예전 표 모양으로 덧붙여.

상태는 이렇게 읽어

  • 초안 — 아직 준비 중인 PR
  • 충돌 — main 과 부딪혀. /harness:sync 로 받아서 풀어
  • 검사 실패 / 검사 중 — 어떤 검사인지 이름을 같이 보여 줘
  • 검사 시작 전 — 푸시 직후라 검사가 아직 안 붙었어. 조금 뒤 다시 봐
  • 승인 대기 — 누구의 승인이 필요한지 알려 줘. 승인한 뒤 새 커밋을 올렸으면 "낡은 승인" 이라 다시 받아야 해
  • risk-gate: 사유 — 승인 말고 다른 이유(예: AI(Artificial Intelligence) 리뷰 검사 못 함)로 risk-gate 가 막았어. 사유는 PR 의 risk-gate 코멘트에 있어
  • base 보다 뒤처짐 / 병합 막힘 / 검사 불안정 — GitHub 가 아직 병합을 막는 상태야. 뒤처졌으면 /harness:sync 로 받아
  • 충돌 여부 확인 중 — GitHub 가 계산 중이야. 충돌이 없다는 뜻이 아니니 조금 뒤 다시 봐
  • 병합 가능 — 앞에 기다릴 PR 이 없으면 바로 병합. 위험한 경로를 건드렸으면 "사람이 GitHub 에서" 병합해

병합 순서는 이렇게 정해

  1. 다른 PR 위에 쌓은 PR(기준 브랜치가 그 PR 의 브랜치)은 그 PR 뒤
  2. PR 본문의 먼저: #12 줄이 가리키는 PR 뒤. /harness:deliver 가 PR 을 만들 때 적어 줘
  3. 같은 DEV 번호면 SRS(Software Requirements Specification) → Spec → 개발 순. PR 이 어느 DEV 인지는 제목·브랜치·바꾼 Spec 파일로 정하고, 거기에 번호가 없을 때만 본문의 첫 번호 하나를 써(본문에 스치듯 적은 번호로는 묶지 않아)
  4. 하네스 저장소는 plugin.json 판이 낮은 PR 먼저

서로 앞이라고 가리키면 "순서 판정 불능(순환)" 이라고 하고 순서를 지어내지 않아. 같은 파일을 고친 PR 쌍은 순서는 그대로 두고 "다시 맞춰야 할 수 있음" 이라고만 알려 줘.

이 순서는 병합할 때도 지켜져. 앞 PR 이 열려 있으면 Claude 의 gh pr merge 가 거절돼(사람이 GitHub 화면에서 하는 병합은 못 막아). 새 작업을 /harness:start 로 열 때도 먼저 병합할 수 있는 내 PR 을 알려 줘.

못 읽으면
GitHub 를 못 읽으면 "PR 상태 확인 불능" 이라고 하고 사유를 보여 줘. PR 이 없다거나 문제없다고 말하지 않아.
세션을 열 때
내 PR 상태는 세션 시작 때 뒤에서 만들어 두었다가 첫 프롬프트에 보여 줘. 세션이 늦게 열리지 않고, 검사 엔진 새 판을 처음 받는 세션에도 표가 나와. 시작 화면에는 "뒤에서 확인하는 중" 한 줄만 나오고, 내 열린 PR 이 없으면 첫 프롬프트에도 아무것도 안 나와. 확인이 첫 프롬프트까지 안 끝났으면 다음 프롬프트에 나와. 못 읽거나 시간이 너무 걸렸으면 "PR 상태 확인 불능" 이라고 알려 주니 /harness:prs 로 다시 봐. 궁금하면 언제든 /harness:prs 로 바로 볼 수 있어.
PR 링크

작업 올리기

커밋, 원격과 맞추기, 푸시, PR(Pull Request) 만들기를 한 번에 해. 문서든 코드든 마지막은 늘 이거야.

이럴 때

택배 보내기랑 같아. 물건을 상자에 담고(커밋), 받는 사람 주소가 바뀌진 않았는지 확인하고(fetch · rebase), 트럭에 싣고(push), 송장을 붙여(PR).

맨손 git push 는 창구를 안 거치고 트럭에 상자를 던지는 거야. 그래서 경비원이 막아.

원장을 PR 뒤에 고치면 푸시가 두 번 나가서 Actions 검사가 두 번 돌아. 그래서 원장은 푸시 전에 고쳐. 원장 줄에는 PR 번호를 적지 않아(같은 개발 건의 PR 이 여럿 열려도 그 줄에서 충돌하지 않게). 개발 건별 최근 PR 은 "팀원별 현황" 이 GitHub 에서 찾아 보여 줘. 옛 원장에 "마지막 PR" 칸이 남아 있어도 읽지도 고치지도 않아.

고친 게 없어도 멈추지 않는 경우가 하나 있어. 지금 브랜치의 열린 PR 이 대표 [DEV-xxx] 이슈를 닫는데 진행 원장이 완료 가 아니면(옛 판으로 만든 PR), deliver 가 원장 행만 완료 로 고쳐 커밋하고 한 번 푸시해. "내 PR 확인하기" 의 원장 줄을 보고 Claude 가 먼저 제안해. 이미 승인받은 PR 이면 새 커밋 때문에 승인이 취소돼 다시 받아야 해서, Claude 가 그 점을 먼저 말하고 물어봐.

커밋한 뒤 deliver 가 먼저 물어봐 — 세 갈래

PR 을 바로 낼지는 deliver 가 상황을 보고 추천 하나를 말해 줘. 내가 "네" 하거나 다른 걸 고르면 돼. 기준은 외울 필요 없어.

  • PR 내기 — 하위 작업 하나가 끝났을 때. 지금까지 하던 대로 올려. PR 은 하위 작업 이슈 하나에 하나야. 같은 개발의 Spec(Specification)을 같이 고친 건 섞임이 아니야. 다만 개발 결과 기록은 Spec 이 아니라 audit/changes/ 에 적어(종류 "구현 결과"). 새 Spec 파일은 승인이 필요하지만 이미 있는 Spec 을 고치는 건 승인이 필요 없어.
  • 여기까지를 PR 로 내기 — 개발하다 src/ 변경이 1,000줄을 넘으면(저장소 .github/branch-growth.yaml 의 notify_src_lines 로 바꿀 수 있어) "변경이 커지고 있어요. 여기까지를 PR 로 내고 나머지는 하위 작업으로 뺄까요?" 하고 물어. 막는 건 아니라서 "그대로 PR 내기" 를 골라도 돼. 아직 안 끝난 개발이어도 줄 수는 세서, 그때는 "끝난 기능만 하위 작업으로 떼어 PR 내기" 를 보기에 더해 줘. 줄 수를 못 세면 "변경 크기를 확인하지 못했어요" 라고 알려 줘(통과로 넘기지 않아).
  • 브랜치에만 올리기 — 080 묶음이 아직 안 끝났거나, 앞 PR 이 아직 열려 있을 때. 저장만 해 두고 PR 은 안 내(그래서 검사도 아직 안 돌아). "아직 080 묶음이 끝나지 않았어요. 지금은 저장만 해 두고, 다 끝나면 PR 을 낼게요." 다음에 다시 /harness:deliver 하면 이어서 판단해.
  • 나눠서 올리기 — 서로 다른 개발이 섞였거나, SRS 와 개발이 한 덩어리로 섞였을 때(개발과 그 개발의 Spec, SRS 와 Spec 은 같이 올려도 돼). 어떤 파일을 어느 PR 로 나눌지 제안해 줘. 그대로 올려도 되는데, 그러면 이유가 PR 에 적혀.

이미 승인받은 PR 에 더 고치려 하면 "그 PR 은 먼저 합치고, 이번 건은 새 PR 로" 를 추천해. 승인은 새로 고친 내용을 본 게 아니거든. PR 을 낸 뒤 저장소가 자동 병합을 허용하고 필수 검사가 걸려 있으면, 승인과 검사가 끝나는 순간 알아서 합쳐지게 예약도 걸어 줘(조건이 안 되면 "자동 병합은 아직 꺼져 있어요" 라고 알려 주고 안 걸어).

검사 불능을 "아마 괜찮겠지" 하고 통과로 치지 않아. 그렇다고 문서가 틀렸다고 하지도 않아. .hwp, .pdf 처럼 읽을 수 없는 형식도 검사 불능이야. PR 이나 main 푸시에서 "바뀐 파일 목록" 자체를 못 구했을 때(기준 브랜치를 못 받음, 비교 기준점이 없음, 푸시 직전 커밋이 없는 첫 푸시)도 저장소 전체를 검사하지 않고 검사 불능으로 끝내고, 사유에 실패한 git 명령과 오류를 남겨.

승인이 필요한 위험 경로

docs/ssot/docs/spec/rules/templates/conventions/.github/.claude/CLAUDE.md

이 경로를 건드린 PR 은 작성자가 아닌 승인자가 마지막 커밋에 Approve 해야 통과해. 승인자 명단은 .github/ssot-approvers 에 있어. 명단이 비면 저장소 관리자만 승인자인데, 관리자가 작성자 혼자면 승인할 사람이 없으니 명단에 다른 사람을 더하거나 다른 관리자를 둬.

빨간 불
검사가 실패하면 PR 댓글의 이유를 읽고 고친 다음, 다시 /harness:deliver 해. 같은 PR 이 갱신돼.
엔진 판
Actions 는 엔진을 main 이 아니라 배포 태그 stable 로 받아. harness 쪽 검사 변경은 새 판이 배포돼 stable 이 옮겨질 때 내 PR 검사에 반영돼, main 에 병합된 순간이 아니야. 새 검사 규칙을 켜는 것도 그 뒤에 해.
main 규칙(ruleset)
조직이 GitHub Team 요금제로 바뀌어서 public-cloud 의 main 에 규칙이 걸렸어. main 은 PR 로만 바뀌고, 필수 검사 pr-checks / check 가 통과해야 Merge 버튼이 열려. 새 커밋이 오면 이전 승인은 취소되고, 강제 푸시와 브랜치 삭제는 막혀. 예외(bypass)는 Owner 만 돼. 승인 수는 서버에 걸지 않았어 — 승인이 필요한지는 risk-gate 가 판단하고, 필요한 PR 은 승인 전까지 pr-checks 가 빨간 불이라 병합이 막혀. 다만 merge-order 는 필수 검사가 아니라서 Merge 버튼을 잠그지 않아. 그래도 승인 없이 병합된 일이 생기면 main-checks 가 나중에 이슈를 열어 알려 줘.

병합 뒤 할 일

  • 진행 원장 줄은 대표 [DEV-xxx] 이슈를 Closes 한 PR(Pull Request) 이면 deliver 가 처음부터 완료로 써서 PR 에 담아(병합되면 main 원장도 완료). 하위 작업 PR 은 "리뷰" 이고 그때 완료는 직접 PR 로 바꿔. 병합 뒤 Actions 는 원장을 쓰지 않고 "완료" 인지만 보고, 아니면 이슈를 열어(main 보호 규칙 아래서는 Actions 가 push 할 수 없어서)
  • 다음 일을 하기 전에 /harness:sync 로 최신 상태를 받아
  • 못 끝낸 일이 있으면 /harness:wrapup

자동 병합 — 위험한 PR 은 승인이 곧 병합 결정이야

  • PR 은 하위 작업 이슈 하나만 담아. 다른 개발이 섞이거나 SRS 와 개발이 같이 있으면 deliver 가 나누자고 해(같은 개발의 Spec 은 같이 올려도 돼).
  • 끝난 PR 은 조건이 갖춰지는 순간 GitHub 가 알아서 합쳐(자동 병합). 위험하지 않은 PR 은 검사 통과, 위험한 PR 은 승인자 Approve 까지야. .github/human-merge-paths 경로를 바꾼 PR 은 자동 병합을 안 걸고 사람이 GitHub 에서 직접 합쳐. 그때까지 기다리면 돼.
  • 개발 PR 은 다른 PR 위에 쌓지 않아. 앞 PR 이 열려 있으면 브랜치에만 올려 두고, 앞 PR 이 합쳐지면 다시 deliver 해서 PR 을 내.
  • Spec(Specification) PR 은 설계가 정해지면 합쳐. 개발하다 알게 된 건 원장·변경 기록에 적고, 설계가 바뀌면 새 판으로 새 PR 을 내.
  • 이미 승인된 PR 에 더 고치고 싶으면 먼저 합치고 새 PR 을 내.

검사를 건너뛰는 병합(--admin)은 쓰지 않아. 필수 검사가 아직 없는 저장소에서는 자동 병합을 걸지 않아(걸면 검사 없이 바로 합쳐지니까). public-cloud 는 저장소 설정에서 자동 병합이 켜졌고 main 규칙에 필수 검사 pr-checks / check 가 걸려 있어.

병합 순서
먼저 병합해야 하는 PR(다른 PR 위에 쌓은 것, 본문 먼저: #n, 같은 DEV(Development) 의 SRS → Spec → 개발 순, 하네스는 plugin.json 판 순)이 아직 열려 있으면 Claude 의 gh pr merge 가 거절돼. 거절 메시지가 앞 PR 과 이유를 알려 줘. 앞 PR 부터 병합하거나, 순서가 틀렸으면 PR 본문의 먼저: 줄을 고쳐. 순서를 못 정하거나(순환, GitHub 못 읽음) 때도 통과시키지 않아. 사람이 GitHub 화면에서 병합하는 것은 막을 수 없으니 /harness:prs 로 순서를 보고 지켜.
남의 PR
작성자가 지금 로그인한 계정과 다른 PR 은 Claude 가 병합·수정·댓글하지 않아. 읽고 내 작업에 주는 영향만 알려. 사람이 웹이나 터미널에서 하면 훅이 못 막아서, 작성자가 아닌 계정의 push 와 리뷰 해제를 나중에 이슈·Teams 로 알려 줘.

  • 승인자 명단은 .github/ssot-approvers 에 있어
  • 팀원이 올린 PR 은 운영 담당(jaeheeMin)이 찍어
  • 운영 담당이 올린 PR 은 명단의 다른 사람이 찍어
  • 작성자 본인의 Approve 는 안 쳐줘
  • Approve 는 PR 의 Files changed 탭 → 오른쪽 위 Review changes(새 화면은 Submit review) → Approve → Submit 으로 찍어. Conversation 탭에는 버튼이 없어
  • Claude 가 내 계정으로 연 PR 은 작성자가 나라서 나는 Approve 를 못 해. 승인자에게 리뷰를 요청해

도장이 무효가 되는 때

  • Approve 뒤에 커밋을 더 올리면 다시 받아야 해. 마지막 커밋에 찍힌 것만 쳐줘
  • 나중에 누가 Request changes 를 하면 앞선 Approve 가 취소돼
  • 승인을 받으면 빨간 불이던 검사가 자동으로 다시 돌아. 내가 다시 올릴 필요 없어

사람이 Merge 버튼필수 검사가 빨간 불이면 버튼이 안 열림 (예외는 Owner 만)
그래도 병합되면자동으로 이슈가 열림 · 승인자가 사후 검토
승인 없이 병합하려 하면 이렇게 돼. 마지막 안전망은 사람이야.

SAP 코드 수정문법 검사를 통과시킨 뒤, 바꿀 코드를 보여 주고 승인받아약속
ATC(ABAP Test Cockpit) 대상 고르기패키지면 오브젝트 목록을 보여 주고 범위를 확인해. 검진표(variant) 이름은 짐작하지 않고 물어약속
ATC "자동" 수정묶음마다 무엇을 바꿀지 보여 주고 확인받아약속
ATC "확인 후" 수정동작·성능·의미가 바뀔 수 있는 건 한 건씩 확인받아약속
ATC 면제("#EC, exemption)근거를 보여 주고 승인받아. 면제 신청은 제안서까지만 만들고 제출은 사람이 해약속
SRS 작성 중 모르는 점한 번에 묶어서 물어. 답이 없으면 짐작하지 않고 "미결 사항" 에 남겨약속
문서 버전 크게 올리기보통은 0.1 씩 올리고, 크게 바뀌면 얼마나 올릴지 물어약속
고객사 양식으로 산출어떤 양식으로 할지, 나올 파일명이 맞는지 확인받아약속
진행 원장 등록/harness:start 때 개발 건으로 올릴지 물어약속
올리기 전 정리 안 된 변경/harness:sync 가 멈추고 올릴지, 임시 커밋할지, 그만둘지 물어약속
리베이스 충돌혼자 풀지 않아. 멈추고 알린 뒤 새 브랜치(-v2)로 옮길지 물어약속
못 끝낸 일을 이슈로/harness:wrapup 이 초안을 보여 주고, 내가 고른 것만 등록해약속
릴리즈 내기릴리즈 노트를 보여 주고 승인받은 뒤에 발행해약속

훅이 물어봐는 내 PC(Personal Computer) 의 경비원(Hook)이 확인 창을 띄우는 거야. 약속은 스킬과 규칙에 적힌 대로 Claude 가 스스로 멈추는 거라, 장치로 막혀 있지는 않아.

주의사항 총정리

한 장으로 보는 요약이야. 헷갈리면 여기부터 봐.

항상 해

  • 새 일은 이슈와 브랜치부터. SRS(Software Requirements Specification)·Spec(Specification) 은 그 스킬이 알아서 만들어 주고, 그 밖의 일은 /harness:start
  • 올릴 땐 /harness:deliver
  • REQ(Requirement)·DEV(Development) 번호를 말할 땐 뒤에 괄호로 제목 — REQ-002(판매오더 조회 앱) (이슈 제목 [DEV-xxx]·파일명은 그대로)
  • 다른 사람 변경을 받을 땐 /harness:sync
  • 못 끝낸 일은 /harness:wrapup 으로 이슈에
  • 문서 버전은 파일명에 (첫 판 _v0.1.xlsx, 고칠 때마다 0.1 씩), 이전 판도 남겨
  • 이름 짓기 전에 conventions/naming.md
  • SRS 를 바꾸면 다른 사람 승인
  • 병합은 필수 검사 pr-checks / check 가 초록일 때만 열려. 빨간 불이면 이유를 읽고 고쳐
  • 원장 "완료" 는 대표 이슈를 닫는 PR(Pull Request) 이면 deliver 가 PR 에 담아 줌 (하위 작업 PR 이면 직접)
  • 검사를 못 했으면 "검사 불능" 이라고 말해

절대 하지 마

  • main 에 직접 커밋하거나 푸시
  • 맨손 git push, --force, --no-verify

  • SAP(Systems, Applications and Products) 100 에 쓰기
  • src/ 를 SAP 보다 먼저 고치기
  • 팀원이 운영 파일(.github/, rules/ …) 바꾸기
  • SRS 요구사항 행 지우기 (Dropped 로 남겨)
  • 한 개발을 REQ 두 개로 쪼개기 (기존 개발에 이어 붙는 일은 새 줄 말고 범위를 넓혀)
