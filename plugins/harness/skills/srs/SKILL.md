# /harness:srs

`docs/ssot/SRS.md`(SRS, 요구사항정의서)를 만들거나 고치는 입구다. SRS 는 이 프로젝트의 SSOT 라,
바꿀 때마다 근거와 영향을 남긴다. `<이 스킬의 base directory>` 는 이 스킬이
로드될 때 위에 표시되는 경로다.

`git rev-parse --show-toplevel` 로 Project Repository 루트를 확인하고,
그 아래 `docs/ssot/SRS.md` 를 대상으로 한다.

## 0단계: 브랜치 확인

SRS 를 쓰기 전에, 지금 브랜치가 이번 SRS 작업에 맞는지 확인한다(#281). 확인은
`<이 스킬의 base directory>/../start/SKILL.md` 의 "다른 스킬이 부르는 브랜치 확인" 을 그대로 따른다 — 미커밋 변경,
main 이면 start 절차, 다른 작업 브랜치면 같은 일인지 판단·질문, 판정 불능이 거기 있다. 이 확인이 끝나기 전에는 SRS 를
쓰지 않는다. start 를 따로 부르라고 하지 않는다. 이 스킬에서 정하는 것은 아래뿐이다.

- **이번 작업 설명**은 "SRS 변경 — <무엇을 넣거나 고치는지>" 한 줄이다. 입력 문서를 읽어야 설명을 쓸 수 있으면 읽기
  (만들기 1~2)까지 먼저 하고, 파일을 쓰기 전에 이 확인을 끝낸다.
- **main 이면 번호 없는 작업 이슈를 만든다.** start 절차를 `docs` 작업으로 수행한다 — 이슈는 `gh issue create`
  (`type:docs`)로 만들고 제목은 `SRS 변경 — <무엇을 넣거나 고치는지>`, 브랜치는 `docs/{이슈번호}-…` 다. 요구사항별
  `[DEV-xxx]` 찜 이슈를 이 브랜치의 이슈로 쓰지 않는다. 이유: 찜 이슈는 개발 본체용이라 개발 PR 이 병합될 때 닫혀야
  하는데, SRS 브랜치의 PR 은 `Closes #{이슈번호}` 로 병합 때 그 이슈를 닫는다. `docs` 라서 start 의 "기존 개발과의 관계"
  확인·번호 찜·원장 등록은 이 단계에서 일어나지 않는다 — 새 REQ 의 확인과 번호 찜은 아래 "요구사항 단위와 번호" 에서
  한 번만 한다(그래서 사용자에게 같은 질문이 두 번 가지 않는다). 새 REQ 가 여럿이어도, 기존 REQ 만 고쳐도 작업 이슈는 하나다.
- **같은 일의 판단 기준.** 브랜치 이슈가 이 스킬이 만든 SRS 작업 이슈이면 같은 일이다. 알아보는 기준은 두 가지를 함께
  본다 — 이슈 제목이 `SRS 변경 — ` 로 시작하고, 브랜치 타입이 `docs/`(또는 이슈 라벨 `type:docs`)다. 하나라도 안 맞으면
  (예: 직접 만든 `docs` 이슈, `feat/` 브랜치) 같은 일로 단정하지 않고 묻는다. 새 REQ 를 넣는데 브랜치 이슈가 다른 DEV 의
  이슈이거나 SRS 와 무관한 작업이어도 번호를 받기 전에 반드시 묻는다(PR #177 사례: 판매오더 작업 브랜치에서 REQ-003 이
  추가돼 한 PR 에 섞였다). 새로 시작을 고르면 위 작업 이슈를 만드는 경로로 간다.

**옛 구조 확인(먼저).** `docs/ssot/PRD.md` 가 있고 `docs/ssot/SRS.md` 가 없으면
조용히 `SRS.md` 를 새로 만들지 않는다. 이 저장소는 예전 이름(PRD)으로 만든
것이라고 사용자에게 알리고, 옮기는 방법을 안내한 뒤 사용자가 원하면 옮긴다.
옮기려면 아래 순서대로 한다. 순서가 중요하다 — 규칙(`rules/ssot.yaml`)이 없는
템플릿을 가리키는 순간이 생기면 doc-guard 훅이 모든 쓰기를 막는다.

1. 새 템플릿 `templates/harness/SRS.md` 를 옛 템플릿 내용으로 만든다(제목 줄의
   "PRD" 는 "SRS" 로).
2. `rules/ssot.yaml` 의 템플릿 경로(`PRD.md`)와 `filename` 패턴(`'^PRD\.md$'`)을
   SRS 로 바꾼다.
3. `git mv docs/ssot/PRD.md docs/ssot/SRS.md` 한 뒤 제목 줄의 "PRD" 를 "SRS" 로
   바꾼다.
4. `git rm templates/harness/PRD.md`
5. `docs/spec/`, `audit/` 등에 있는 `PRD.md` 링크를 `SRS.md` 로 바꾼다.

(설정이 깨져 훅이 막은 경우에도 `rules/` 의 yaml 과 `templates/` 아래 파일을 고치는
쓰기는 허용되고 오류 상태임을 알려 준다. 그래도 위 순서를 지켜 깨진 순간을 만들지
않는 것이 먼저다.)

옮기는 PR 도 `docs/ssot/` 를 바꾸므로 사람 승인이 필요하다. 사용자가 옮기지
않겠다고 하면 이 스킬은 거기서 멈춘다(`PRD.md` 를 그대로 고치지도, `SRS.md` 를
따로 만들지도 않는다).

위 경우가 아니면, 이 문서가 아직
`templates/harness/SRS.md` 의 빈 스텁 그대로면(각 절에 "아직 작성 전이다"
placeholder만 있으면) **만들기**, 이미 내용이 채워져 있으면 **고치기** 로
판단한다.

## 요구사항 단위와 번호

**단위.** 요구사항 1건 = 개발 또는 설정 1건이고, 개발이면 Spec 1건이다. 한 개발 안의 세부
기능은 줄을 나누지 말고 그 요구사항의 설명·완료 조건에 쓴다. 한 개발로 묶이지
않는 것은 별개 요구사항(별개 줄)이다. 기존 개발에 이어 붙는지 별개인지는 아래 "기존 개발과의 관계" 로 묻고 정한다.

**기존 개발과의 관계.** 새 REQ 를 넣기 전(번호를 받기 전)에 현재 개발 목록을 본다. 한 개발이 REQ 두 개로 쪼개지는 일을 막으려는
단계다.

```bash
uv run --no-project python "<이 스킬의 base directory>/../start/reserve_number.py" list
```

결과(번호·제목·LoB·다음 단계·상태 등)와 종료코드는 `<이 스킬의 base directory>/../start/SKILL.md` 의 "기존 개발과의
관계" 를 따른다(3 이면 건너뛰고, 2 면 사유를 알리고 멈춘다). 목록이 비면 묻지 않고 새 REQ 다. 아니면 표로 보여 주고
`AskUserQuestion` 으로 "기존 개발의 일부인가, 새 개발인가" 를 묻는다(쉬운 말, 보기마다 무엇이 달라지는지).

- **기존 개발의 일부** — 새 줄을 만들지 않는다. 그 REQ 의 상세 절에서 범위·완료 조건을 넓힌다. 넓히려는 것이 그 REQ 의
  `하지 않는 것`(범위 제외)에 적혀 있던 항목이면 거기서 빼고 범위로 옮긴다. 변경 기록 종류는 "요구사항 변경" 이다(고치기 4).
  새 번호를 받지 않는다.
- **새 개발** — 아래 "번호" 대로 번호를 받는다. 정말 별개인 건(설정만 하는 별개 건 등)이 여기 해당한다.

**범위 `하지 않는 것` 을 적을 때(꼬리표).** 특정 요구사항에서 뺀 일이면 그 항목 끝에 `(REQ-001)` 을 붙인다(여러 번호는
`(REQ-001, REQ-002)`). 꼬리표가 없으면 프로젝트 전체에서 하지 않는 일이다. 꼬리표는 항목 맨 끝에 한 번만 쓴다. 번호는 쉼표로만 잇고(`(REQ-001, REQ-002)`), 대문자 `REQ`, 괄호 하나다. `/`·`~`·소문자는 꼬리표로 안 읽히고, 괄호를 나눠 쓰면 마지막 괄호만 읽힌다 —
머리말 줄에 `A, B (REQ-001)` 로 이어 쓰면 B 에만 붙는다. 새 REQ 제목이 이런 항목과 겹치면 번호 찜이 종료코드 4 로 멈추고
(`excluded_matches`), 같은 PR 에서 항목이 지워지거나 바뀌면 risk-gate 가 어느 REQ 의 항목인지 근거로 적는다. 꼬리표만
붙이거나 떼는 변경은 항목이 바뀐 것으로 치지 않는다. 범위 절은 엑셀 산출에 나가지 않는다.

**다른 번호를 적을 때(관계 줄).** 상세 절(`### REQ-n`) 본문에 다른 요구사항 번호(`REQ-m`, `DEV-m`)를 적으면 doc-guard
(`req_cross_reference` 규칙, #261)가 저장과 PR 검사에서 거절한다. 같은 개발이면 새 REQ 로 쪼개지 말고 그 REQ 의 범위를
넓힌다. 정말 별개이면 그 절의 `### REQ-n` 제목 바로 아래, 첫 `####` 소제목 앞에 `관계: 별개 — <이유>` 한 줄을 적는다.
이 자리의 줄은 엑셀로 나가지 않는다(소제목 아래에 두면 그 칸 값으로 섞여 나가므로 인정하지 않는다). 자기 번호의 `DEV-n`
과 `옛 REQ-003` 처럼 번호 앞에 `옛 ` 이 붙은 옛 표기는 세지 않는다.

**번호.** 요구사항, 그 Spec, 원장의 개발 건이 한 번호를 쓴다(`REQ-003` →
`DEV-003`). 번호는 이슈 제목에 찜한 번호다(`[DEV-003] ...`). 새 요구사항을 SRS 에
넣기 전에 번호를 받는다. 마지막 번호를 보고 직접 이어 붙이지 않는다.

- 사용자가 이미 만든 이슈를 줬으면 `claim --issue N` 으로 받는다(번호가 있으면 그
  번호, 없으면 붙인다).
- 아니면 `reserve --title "<요구사항 요약>" --label type:feat` 로 이슈를 만들며 받는다.

```bash
uv run --no-project python "<이 스킬의 base directory>/../start/reserve_number.py" reserve \
  --title "<요구사항 요약>" --body-file <본문 파일> --label type:feat
uv run --no-project python "<이 스킬의 base directory>/../start/reserve_number.py" claim --issue <번호>
```

`uv` 가 없으면 `python` 으로 바로 부른다. 종료코드와 결과 읽는 법은
`<이 스킬의 base directory>/../start/SKILL.md` 의 "번호 찜" 을 따른다. 종료코드 4(새 제목이 기존 REQ 제목이나 범위 `하지 않는 것` 항목과 겹침)면
`matches` 와 `excluded_matches`(항목과 꼬리표 번호 `reqs`, 있으면 "REQ-xxx 에서 안 하기로 한 일")를 보여 주고 "기존 개발의 하위 작업인가, 새 개발인가" 를 묻는다. 하위 작업이면 위 "기존 개발의 일부" 로 가서 그
REQ 의 범위를 넓히고(새 번호 없음), 새 개발이 맞다고 하면 `--confirmed-new` 를 붙여 다시 부른다. 받은
`number` 의 숫자로 SRS 표의 ID 를 `REQ-xxx` 로 적는다(`renumbered_from` 이 있으면
바뀐 번호를 사용자에게 알린다. 받은 번호는 마무리 안내에서 모아 표로 알린다). 종료코드 3(원장 없는 저장소)이면 찜하지 않고,
SRS 의 마지막 REQ 번호 다음으로 이어 붙인다. 종료코드 2 는 번호를 정하지 못한
것이니 사유를 알리고 멈춘다.

**다음 단계.** 요구사항 표에는 `다음 단계` 열이 있다. 이 요구사항이 SRS 다음에 어디로 가는지를 적는
md 전용 열이라 엑셀(고객 양식)에는 나가지 않고, 양식 지도에 안 적어도 된다(엔진 기본 md 전용 열).
값은 셋뿐이다.

| 값 | 뜻 | `Development RICEFW ID` | 그 뒤 |
|---|---|---|---|
| `개발` | 코드를 짜는 개발이다 | REQ 와 같은 번호의 `DEV-xxx` | `/harness:spec` 으로 Spec 을 만든다 |
| `설정` | 설정만으로 끝난다 | 비운다 | Spec 을 만들지 않고 진행 원장에서 관리한다(아래 "설정 요구사항") |
| `미정` | 아직 모른다 | 비운다 | `## 미결 사항` 에 남기고, 정해지면 이 열을 고친다 |

이로써 RICEFW ID 빈칸이 "설정" 인지 "아직 안 정함" 인지는 `다음 단계` 열로 구분된다. 요구사항을
SRS 에 넣을 때마다 다음 단계를 묻고, 모르면 `미정` 으로 둔다. 보류·취소는 이 열이 아니라 Status(`On Hold`·`Dropped`·
`Duplicate`)로 적는다. 다음 단계 값은 엔진이 검사해 막는다(번호 짝 검사). 위 셋 밖의 값이나 빈 칸은 위반이다.

**설정 요구사항.** 다음 단계가 `설정` 으로 정해지면(만들 때든 고칠 때든) 그 요구사항을 진행 원장에 올린다.
원장이 없는 저장소면 건너뛰고 그렇다고 알린다. 원장 파일(프로그램)은 `audit/ledger/*.md` 목록을 보여 주고
고르게 하고(새 프로그램이면 `templates/harness/audit-ledger.md` 틀로 새 파일), `## 개발 건` 표에
`| DEV-xxx | <제목> | 설정 | <담당 GitHub 아이디> | 대기 |` 행을 더한다(원장 표 머리의 칸 수에 맞춰 채운다(옛 원장에 `마지막 PR` 칸이 남아 있으면 빈칸으로 둔다))(담당은 실명이 아니라 GitHub 아이디) — Spec 칸에 `설정` 이라고 적고, 번호는 REQ 와 같은
`DEV-xxx` 다. 이미 그 번호 줄이 있으면 새로 더하지 않는다. 그 REQ 번호가 `## 관련 요구사항` 에 없으면 더한다.
설정을 시작하면 `/harness:start` 가 상태를 `진행` 으로 바꾸고, 완료는 그 `[DEV-xxx]` 이슈를 `Closes` 하는 PR 을 `/harness:deliver` 가 올릴 때 `완료` 로 담는다. 무엇을 어디서 어떻게
설정했는지는 그 요구사항 상세 절의 `#### Configuration Considerations`(Backlog 양식이 있을 때) 에 적는다.

## 양식 지도와 요구사항 표

SRS 를 쓰기 전에 고객사 산출물 양식(예: Backlog List)이 있는지 본다. 있으면 SRS 요구사항 표의 열과
허용 값이 그 양식에서 온다. 형식 정본은 `<이 스킬의 base directory>/../spec/form-map.md` 의
"원본이 SRS 인 지도" 절이다.

1. **지도 찾기.** `templates/forms/*.yaml` 을 모두 읽어 표에 `원본: SRS` 가 있는 지도를 찾는다.
   - 폴더가 없거나 `원본: SRS` 지도가 없으면 "지도 없음" 이다. 이 절의 나머지를 건너뛰고 지금처럼
     `templates/harness/SRS.md` 틀의 기본 열(ID, Title, Status, Priority (PO), 출처, 다음 단계)로 md 만 쓴다.
   - 읽지 못한 지도(파싱 오류, 필수 키 없음)가 하나라도 있으면 목록에서 조용히 빼지 않는다. 어느 파일이 왜
     안 읽히는지 알리고 멈춘다. `원본: SRS` 지도가 둘 이상이면 어느 양식으로 쓸지 묻는다.
2. **열.** 지도 표의 `열` 이름이 요구사항 표의 열 이름이고 상세 절 소제목이다. 짧은 값(LoB, Applicability, Scope item,
   Type, Responsible, Status, Priority (PO), Target Release, Target Sprint, Development RICEFW ID …)은
   `## 요구사항` 표의 열에 쓰고, 한 줄로 끝나지 않는 서술(Short Description, Acceptance Criteria, Proposed
   Solution, Dependencies, Impact, Configuration Considerations …)은 요구사항마다 상세 절 `### REQ-xxx <제목>`
   아래 `#### <열 이름>` 에 쓴다. 표에는 `ID`(= `REQ-xxx`, 지도 `번호_열` 의 숫자가 된다)가 있어야 하고, 엑셀에
   가지 않는 열(출처 등)은 지도 `md_전용` 에 적힌 이름으로만 둔다(`다음 단계` 는 엔진 기본 md 전용이라 지도에 안 적어도 된다). 지도에 없는 이름의 열·소제목은 쓰지 않는다 — 저장할 때(훅)·PR 의 doc-guard
   (`form_columns` 규칙)가 "양식 밖 열/소제목" 으로 거절하고, 산출도 멈춘다. 오타도 같다. 필요한 열이 지도에 없으면 열을 만들어 쓰지 말고
   사용자에게 알려 양식 지도를 먼저 고치게 한다. 지도 `설명` 이 어느 열에 무엇을 적는지 알려 주면 그대로 따른다.

   **지도에 있는데 표에 없는 열.** 지도 `열` 에 있는 짧은 열이 SRS 요구사항 표에 없으면(특히 Development RICEFW ID
   — 이 열이 없으면 엑셀 그 열이 빈다), 고칠 때 표에 열을 추가하고 요구사항마다 값을 채운다. 다음 단계가 `개발` 이면 REQ 와 같은 번호의
   `DEV-xxx`, `설정`·`미정` 은 비운다(아래 5). 값을 모르는 열은 사용자에게 묻고, 답이 없으면 비워 두고 `## 미결 사항` 에 남긴다.

   **Short Description 은 요약.** 엑셀 한 셀은 행 높이 상한(409pt)을 넘으면 위아래가 잘려 보인다. Short Description 은
   몇 줄짜리 요약으로 쓰고, 세부 기능 목록·조건은 Acceptance Criteria(또는 Proposed Solution)로 나눠 쓴다. 산출 때
   `type: cell-too-tall` 경고가 나오면 그 칸을 이렇게 나눈다.
3. **허용 값.** 드롭다운이 있는 열은 허용 값 안에서만 고른다. 지도 템플릿의 데이터 유효성에서 읽어 오며 따로 목록을
   관리하지 않는다.

   ```bash
   e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "산출 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
   uvx --from "$e" \
     python -P -m checker.export --root "$(git rev-parse --show-toplevel)" --form <지도 이름> --list-values
   ```

   첫 줄이 실패하거나 빈 값이면 `uvx` 로 넘어가지 말고 멈춰 사유를 알린다("산출 불능", `@main` 으로 대신 받지 않는다).

   stdout 은 JSON 한 줄이다. `sheets[].columns[]` 의 `column`(지도 열 이름)별 `allowed` 가 허용 값이다.
   그 열은 사용자에게 허용 값을 보기로 보여 주고 고르게 한다(`AskUserQuestion` 을 쓸 수 있으면 쓴다. 값이 많으면
   일부만 보여 주고 나머지는 말로 고르게 한다). 허용 값 밖의 값을 사용자가 말하면 그대로 쓰지 않고 허용 값을 다시
   보여 준다. `allowed` 가 `null` 이면(`unreadable` 에 사유, 이때 `status: warning`·종료코드 3) 허용 값을 읽지 못한 열이니 그렇다고 알리고,
   값은 사용자가 확인하게 한다. `allowed` 가 `[]` 이면(`empty`) 목록이 비어 있는 열(예: Responsible 목록을 아직 안 채운 양식)이라
   고를 값이 없다고 알린다. `enforced: false` 인 열은 엑셀이 목록 밖 값도 받는 설정이라 허용 값을 권장으로만 보여 준다. 명령이
   실패하거나 stdout 이 JSON 이 아니면 허용 값을 확인하지 못했다고 알린다 — 추측으로 값을 채우지 않는다.
4. **상태·우선순위.** 상태는 Backlog 의 Status 하나뿐이다: New / Planned / In Process / Done / On Hold / Dropped /
   Duplicate. 우선순위는 Backlog 의 값(`1. Must-Have` …)이다. 지도가 있으면 3 의 허용 값이 정본이고, 지도가 없을
   때의 상태는 위 일곱 값이다. 새 요구사항은 `New` 로 시작한다.
5. **Development RICEFW ID.** 다음 단계가 `개발` 이면 REQ 와 같은 번호의 `DEV-xxx`(`REQ-003` → `DEV-003`)를 적는다.
   `설정`·`미정` 이면 비운다 — 빈칸의 뜻은 `다음 단계` 열이 말해 준다. 개발 ID(`CO-006-01` 같은 모듈 체계)는 Spec 양식 쪽 이름이니 여기에 섞지 않는다.
6. **요청 출처.** 누가·언제·왜 요청했는지는 엑셀에 가는 Short Description 의 첫 줄에 적는다(`출처` 열은 `md_전용` 이라
   엑셀에 가지 않는다). 형식은 `요청: <사람(부서)>, <날짜 YYYY-MM-DD>, <근거(회의·메일·문서 링크)>` 다. 이슈 번호는 넣지
   않는다 — 한 개발에 이슈가 여러 건 붙을 수 있어서 추적은 DEV 번호(찜 이슈 제목 `[DEV-xxx]` 와 Development RICEFW ID)로
   한다. 만들 때도 고칠 때도 이 줄을 둔다. 모르는 부분은 사용자에게 묻고, 답이 없으면 추측으로 채우지 않고 그 부분을
   `미정` 으로 쓰고 `## 미결 사항` 에 남긴다. 그 아래 줄부터 요약을 쓴다. 예:
   `요청: 홍길동(영업팀), 2026-10-12, 10-10 킥오프 회의록(링크)`
7. **버전.** 산출 파일 이름의 버전은 SRS.md 문서 머리(제목 아래, 첫 `##` 앞)의 `버전: 0.1` 줄에서 온다. 줄이 없으면
   사용자에게 물어 적는다(처음이면 0.1).

## 만들기

1. 입력 문서를 확인한다. 사용자가 경로를 줬으면 그것을 읽고, 안 줬으면
   `docs/` 아래에서 요구사항 정리·AS-IS 문서·회의록 같은 후보를 찾아 목록으로
   보여 주고 고르게 한다. 이 저장소의 Template 은 `templates/`, Convention
   은 `conventions/` 에 있다.
2. 입력 문서를 읽고, 불명확하거나 서로 부딪히는 점을 목록으로 만든 뒤 한
   번에 묶어 사용자에게 묻는다. `AskUserQuestion` 을 쓸 수 있으면 쓰고,
   질문은 쉬운 말로 하고 보기마다 무엇이 달라지는지 적는다. 답이 없는
   것은 추측으로 채우지 않고 `## 미결 사항` 에 남긴다. 요구사항마다 다음 단계(`개발`/`설정`/`미정`)도
   이 질문에 함께 묶어 묻는다. 모른다는 답은 `미정` 으로 두고 `## 미결 사항` 에 남긴다.
3. `templates/harness/SRS.md` 틀대로 `docs/ssot/SRS.md` 를 쓴다. 요구사항은
   위 "요구사항 단위와 번호" 대로 나누고 번호를 받아 붙이며 출처(입력 문서·회의·질문
   답)를 적는다. 표의 열·상세 절·드롭다운 값·Short Description 첫 줄의 요청 출처는 위 "양식 지도와 요구사항 표" 를 따른다.
   `다음 단계` 열과 RICEFW ID 는 "요구사항 단위와 번호" 의 다음 단계 표대로 채운다.
   Convention·Template·규칙은 본문에 옮기지 않고 링크만 적는다. 다음 단계가 `설정` 인 요구사항은 같은
   절의 "설정 요구사항" 대로 진행 원장에 올린다(쓴 원장 파일은 마무리 안내에 적는다).
4. 변경 기록을 남긴다. `audit/changes/YYYYMMDD-SRS-최초작성.md` 를
   `templates/harness/audit-change.md` 틀로 쓴다. 종류는 "결정", 바뀐 것은
   전체 REQ 목록, 근거는 읽은 입력 문서 목록, 영향은 "이후 Spec 작성 대상"
   으로 적는다.
5. 저장 전에 doc-guard 훅이 이 틀을 검사한다. 막히면 사유를 읽고 빠진 절을
   채운다.
6. 양식 지도가 있으면 아래 "양식 파일 산출" 로 xlsx 를 만든다.
7. 마무리를 안내한다. 맨 앞에, 이번에 번호를 새로 받았으면 받은 번호를
   **반드시** 표로 알린다 — REQ 번호, 요구사항 제목, 찜한 이슈(`[DEV-xxx]` 이슈
   번호와 링크). 제목 열이 있으므로 번호 칸에는 제목을 또 붙이지 않는다. 표 밖 문장에서 번호를 말할 때는
   `REQ-002(판매오더 조회 앱)` 처럼 괄호로 제목을 붙인다(`<이 스킬의 base directory>/../../rules/issue-and-release.md` "REQ·DEV 번호를 말할 때"). 번호가 겹쳐 바뀐 것(`renumbered_from`)은 바뀌기 전 번호도 함께
   적는다. 표에는 `다음 단계` 열도 넣어 어느 번호가 Spec 으로 가고(`개발`), 원장에서 관리되고(`설정`),
   아직 안 정해졌는지(`미정`)를 보인다. 원장 없는 저장소(종료코드 3)에서 이어 붙인 번호는 이슈 칸을 "찜 안 함"
   으로 적는다. 사용자는 이 번호로 Spec 을 만들고(`/harness:spec`) 요구사항 변경을
   말하므로, 새 번호가 없었으면 "새로 받은 번호 없음" 이라고 적는다.
   SRS 는 SSOT 라 SRS 를 바꾸는 PR 은 사람이 승인해야 한다(승인 없는 PR 은 Actions
   `ssot-approval` 이 실패시키고 Claude 의 `gh pr merge` 는 훅이 거부한다. 사람이
   웹 Merge 버튼으로 병합하는 것만 못 막으며, 그 경우 병합 뒤 이슈가 열린다). 다음
   단계는 `/harness:spec` 으로 Spec 을 만드는 것이다.

## 고치기

1. 무엇이 왜 바뀌는지 받는다. 근거(고객 요청, 회의, 기술 제약 등) 없이
   고치지 않는다.
2. 해당 REQ 를 고친다(표 줄과 상세 절). 기존 REQ 의 번호는 새로 매기지 않는다. 상태는 Backlog Status
   하나뿐이라 "바뀜" 을 상태로 적지 않는다 — 내용이 바뀐 REQ 의 상태는 그대로 두거나 진행 상황에 맞게
   사용자가 정한 값으로 바꾸고(예: `Planned` → `In Process`), 바뀐 사실은 변경 기록(4)에 남는다. 없앤 REQ 는
   행을 지우지 않고 `Dropped` 로, 다른 요구사항과 겹치면 `Duplicate` 로 둔다. 새
   요구사항의 번호는 "요구사항 단위와 번호" 대로 받는다. 드롭다운 열의 값은 "양식 지도와 요구사항 표" 3 의
   허용 값에서 고른다. 고친 REQ 의 Short Description 에 요청 출처 첫 줄(같은 절 6)이 없으면 채우고, 표에 지도의 짧은 열이
   빠져 있으면 열을 추가해 값을 채운다. 표에 `다음 단계` 열이 없는 옛 SRS 면 열을 추가하고 요구사항마다 값을
   묻는다(모르면 `미정`, RICEFW ID 는 이미 채워진 `DEV-xxx` 가 있으면 `개발`). 다음 단계가 바뀐 요구사항(예: `미정` → `설정`,
   `개발` → `설정`)은 RICEFW ID 도 맞춰 고친다(`설정` 으로 바뀌면 비우되 Spec 이 이미 있으면 그 Spec 을 어떻게 할지
   사용자에게 묻는다). `설정` 으로 정해지면 "설정 요구사항" 대로 원장에 올린다. 원장에 이미 `개발` 건으로 있던 줄이
   `설정` 으로 바뀌면 줄을 새로 만들지 않고 Spec 칸만 `설정` 으로 고친다. 반대로 `설정`·`미정` 이 `개발` 로 바뀌면
   RICEFW ID 에 REQ 와 같은 `DEV-xxx` 를 채우고, 원장에 그 DEV 의 `설정` 줄이 이미 있으면 새로 만들지 않고 Spec 칸을
   `-` 로 되돌린다(상태는 진행 상황 그대로 둔다). 변경 기록의 종류는 아래 4 대로 "결정" 이다. 요구사항이 `On Hold`·
   `Dropped`·`Duplicate` 가 되어도 원장 줄은 지우지 않는다. 상태 값(대기/진행/리뷰/완료)은 그대로 두고 그 줄의 `내용`
   칸 앞에 `[보류]`(On Hold) 또는 `[취소]`(Dropped·Duplicate)를 붙이며, 다시 살아나면(`On Hold` 해제) 떼어 낸다.
   개발 건 줄에도 같게 적용한다.
3. 영향을 찾는다. 바뀐 REQ 번호로 `docs/spec/`, `audit/ledger/`, 그 밖의
   `docs/` 를 검색해 영향받는 파일 목록을 사용자에게 보여 준다. 사용자가
   원하면 그 Spec 들도 고친다 — 개발자는 왜 바뀌었는지 모르므로, 고친 Spec
   에 바뀐 REQ 번호와 이번 변경 기록 링크를 남긴다.
4. 변경 기록 `audit/changes/YYYYMMDD-<요약>.md` 을 `templates/harness/
   audit-change.md` 틀로 남긴다. 바뀐 것에는 REQ 번호와 파일을, 근거에는
   왜 바뀌었는지를, 영향에는 3 에서 찾은 목록을 적는다. 다음 단계가 바뀐 요구사항(`미정` → `설정` 처럼
   결정이 내려졌거나 뒤집힌 것)은 종류를 "결정" 으로 적는다.
5. 양식 지도가 있으면 문서 머리의 `버전:` 을 올리고(0.1 씩, 큰 변경이면 사용자에게 묻는다) 아래 "양식 파일 산출"
   로 새 판 xlsx 를 만든다. main 에 있는 이전 판은 덮어쓰지도 지우지도 않는다(이 브랜치에서 만든 미병합 판은 같은 버전으로 다시 산출된다).
6. 마무리를 안내한다. 맨 앞에, 새 요구사항을 추가해 번호를 새로 받았으면 만들기 7 과
   같이 표로 알리고, 없었으면 "새로 받은 번호 없음" 이라고 적는다. SRS 변경 PR 도 사람
   승인이 필요하다. 이번에 `다음 단계` 를 정하거나 바꾼 요구사항이 있으면 번호 표에 그 값도 적는다.
   `/harness:deliver` 로 올릴 때는 PR 본문에 "SRS 변경" 이라는 표시와 이번
   변경 기록 링크를 적는다.

## 양식 파일 산출

"양식 지도와 요구사항 표" 의 지도가 있을 때만 한다. `docs/ssot/SRS.md` 를 직접 읽어 지도의 템플릿 복사본에
요구사항을 4행부터(지도 `시작_행`) 한 줄씩 쓴다. 서식·드롭다운·다른 시트는 그대로 두고 값만 바꾼다.

0. `--form` 에는 지도 이름(`Backlog`) 또는 지도 파일 경로(`templates/forms/Backlog.yaml`, `--root` 기준 상대·절대)를
   쓴다. 같은 이름 산출 파일이 있을 때 엔진이 `origin/main` 을 보고 판단하며 fetch 는 하지 않으므로, 먼저
   `/harness:sync` 나 `git fetch origin` 으로 최신으로 맞춘다.
1. 먼저 파일을 쓰지 않는 확인을 한다.

   ```bash
   e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "산출 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
   uvx --from "$e" \
     python -P -m checker.export --spec docs/ssot/SRS.md --root "$(git rev-parse --show-toplevel)" --form <지도 이름> --check
   ```

2. 문제가 없으면 `--check` 를 빼고 같은 명령으로 산출한다. 명령 실행 방법(PowerShell 이면 `$e = uv run --no-project python
   "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py"; if ($LASTEXITCODE -ne 0 -or -not $e) { throw "산출 불능" }` 로 정해
   `uvx --from $e …`. 판을 못 정하면 uvx 로 넘어가지 않고 멈춘다)은 `<이 스킬의 base directory>/../spec/SKILL.md`
   의 "양식 파일 산출" 과 같다. 결과는 stdout 의 JSON 한 줄이다. JSON 으로 읽히지 않으면(uvx 실패 등) 종료코드와
   무관하게 "산출 불능" 이라고 알린다. 통과로도 위반으로도 넘기지 않는다.
3. 결과를 읽는다.
   - `status: ok` (0) — `files` 의 경로를 알리고 엑셀로 열어 드롭다운과 4행부터의 요구사항을 확인하라고 권한다.
     `warnings` 가 있으면(예: `type: dropdown-empty` — 목록이 비어 있어 검사할 값이 없다, `dropdown-missing` — 그 줄엔 드롭다운이
     없다) 그대로 보여 준다. 엑셀에서 4행부터의 줄 높이가 내용에 맞는지도 확인하라고 권한다.
   - `status: warning` (3) — 값이 드롭다운 목록 밖이거나(`type: dropdown`), 허용 값을 읽지 못해 검사하지 못한 열이 있다
     (`type: dropdown-unchecked`, `next` 에 "검사하지 못한 열이 있다"), 또는 셀이 엑셀 행 높이 상한을 넘어 잘릴 것으로
     보인다(`type: cell-too-tall` — `item`(REQ)·`column`·`est_lines`·`est_height_pt`, 열 너비로 어림한 값이라 틀릴 수 있다).
     `cell-too-tall` 은 Short Description 을 요약으로 줄이고 세부는 Acceptance Criteria 등으로 옮긴 뒤 다시 산출한다.
     드롭다운 쪽 앞의 것은 `item`(REQ-xxx)·
     `column`·`value`·`allowed` 를 그대로 보여 주고, 허용 값 중에서 고르게 해 SRS.md 를 고친 뒤 다시 한다(1 부터).
     `--check` 로 먼저 확인했다면 파일은 아직 없다. 이미 만든 파일이 있으면(아직 커밋 전이면) 그 파일만 지우고
     다시 산출한다. 허용 값 밖의 값을 그대로 둘지는 사용자가 정하고, 그대로 두면 그렇다고 마무리 안내에 적는다.
     뒤의 것(`dropdown-unchecked`)은 통과가 아니다 — 그 열의 값을 사용자가 허용 목록과 대조하게 하고, 검사하지 못했다고 마무리 안내에 적는다.
   - `status: rejected` (1) — 아무 파일도 만들지 않았다. `problems` 의 항목을 그대로 보여 주고 고친 뒤 다시 한다.
     버전 줄이 없다는 거부면 사용자에게 버전을 묻는다. 같은 이름 파일이 있다는 거부면: "main 에 이미 있는 판"이면 `버전:` 을
     올려 새 판으로 낸다. 이 브랜치에서 만든 판(origin/main 에 없음)은 거부되지 않고 그대로 다시 산출되며 JSON 에
     `replaced: true` 가 붙는다. "main 에 있는 판인지 판단하지 못해" 라는 거부는 검사 불능이다 — `git fetch origin` 후 다시 한다.
   - `status: error` (2) — SRS·지도·템플릿을 읽지 못했거나 SRS 의 열·소제목이 지도에 없다(양식 밖 이름을 모두 모아 알린다).
     산출하지 못했다고 알리고 `problems` 의 원인을 보여 준다. 통과로 넘기지 않는다. 양식 밖 이름이면 SRS 를 지도의 이름으로 고친다.
4. 산출한 xlsx 의 검사(파일 이름 등)는 PR 을 열 때 Actions(doc-guard)가 맡는다. 산출 성공은 doc-guard 통과가 아니다.

## 저장 전 검사

`docs/ssot/SRS.md` 를 쓰거나 고칠 때마다 doc-guard 훅(`pre_write_guard.py`)이
`rules/ssot.yaml` 로 파일 이름, 필수 절, 상세 절의 다른 번호 언급(관계 줄 필요)을 검사한다. 검사를 통과하지 못하면
저장이 막히고 사유가 나온다 — 그 사유대로 고친다. 훅이 죽어 검사를 못 한
경우에는 통과나 위반이 아니라 검사를 못 했다고 알린다.
