# /harness:spec

`docs/spec/` 의 개발 Spec 을 만들거나 고치는 입구다. 개발자는 설계에
참여하지 않고 이 Spec 만 보고 개발하므로, Spec 은 SRS 의 REQ 를 근거로
빠짐없이 적고 진행 원장(`audit/ledger/`)에 같은 번호로 등록한다. `<이 스킬의
base directory>` 는 이 스킬이 로드될 때 위에 표시되는 경로다.

`git rev-parse --show-toplevel` 로 Project Repository 루트를 확인한다.

## 0단계: 브랜치 확인

Spec 을 쓰기 전에, 지금 브랜치가 이 개발 건에 맞는지 확인한다(#281). 확인은
`<이 스킬의 base directory>/../start/SKILL.md` 의 "다른 스킬이 부르는 브랜치 확인" 을 그대로 따른다 — 미커밋 변경,
main 이면 start 절차, 다른 작업 브랜치면 같은 일인지 판단·질문, 판정 불능이 거기 있다. start 를 따로 부르라고 하지
않는다. 이 스킬에서 정하는 것은 아래뿐이다.

- **언제.** 미커밋 변경 확인은 바로 한다. 브랜치 비교는 대상 DEV 가 정해진 뒤에 한다 — 만들기는 3 에서 DEV 번호를
  정한 직후, 고치기는 고칠 Spec 이 정해진 직후다. 그 전에는 SRS·Spec·원장을 읽기만 하고 파일을 쓰지 않는다.
- **비교 대상.** 브랜치 이슈의 DEV(제목 `[DEV-xxx]` 또는 하위 작업 `(DEV-xxx)`)가 Spec 을 만들거나 고칠 DEV 와 같으면
  같은 일이다. 다르거나 DEV 가 없으면 묻는다.
- **main 이면: 항상 하위 작업 이슈로 브랜치를 만든다.** 대표 `[DEV-xxx]` 이슈(SRS 단계에서 찜해 둔 개발 이슈)는 개발
  본체용이라 개발 PR 이 병합될 때 닫혀야 한다. Spec PR 의 `Closes` 가 그 이슈를 닫으면 개발 단계가 쓸 이슈가 사라지므로,
  Spec 단계는 `[DEV-xxx]` 이슈를 브랜치에 쓰지 않는다. `reserve` 도 부르지 않고 start 의 하위 작업 방식대로 일반
  이슈를 만든다 — 제목 `<요약> (DEV-xxx)`(예: `판매오더 조회 앱 Spec 작성 (DEV-002)`), 본문 `DEV-xxx 하위 작업` 과
  대표 `[DEV-xxx]` 이슈 링크(`start/reserve_number.py list` 의 `issues` 에서 찾는다. 없으면 원장 줄이나 SRS 링크).
  브랜치는 `feat/{이슈번호}-…` 다. Spec PR 이 병합되면 이 하위 작업 이슈만 닫히고 `[DEV-xxx]` 는 열려 있다. 원장에 이미
  있는 DEV 면 start 의 "이미 원장에 있는 DEV" 단계가 상태를 `진행` 으로 바꾸고, `/harness:deliver` 는 하위 작업 이슈의
  `(DEV-xxx)` 로도 같은 줄을 찾아 `리뷰` 로 갱신한다.

## Spec 번호(DEV)

요구사항 1건 = Spec 1건 = 개발 1건이고 번호는 하나다. Spec 번호는 근거 요구사항의
번호를 그대로 쓴다(`REQ-003` → `DEV-003`). Spec 파일 하나가 그 번호를 갖고
(`docs/spec/DEV-003-<요약>.md`), 진행 원장의 개발 건 표 ID 칸에도 같은 번호를
적어 SRS·Spec·원장이 한 번호로 연결되게 한다. 숫자는 3자리로 0 을 채운다.

근거 REQ 가 없는 개발(SRS 를 거치지 않는 개발)이면 그 브랜치·이슈에 찜해 둔
번호(이슈 제목의 `[DEV-xxx]`)를 쓴다. 이 번호는 새로 계산하지 않는다 — 번호 찜과
계산식은 `<이 스킬의 base directory>/../start/SKILL.md` 의 "번호 찜" 에 있고
스크립트(`reserve_number.py`)가 한다. 찜 번호가 아직 없으면 `claim --issue <번호>`
로 붙인다. 종료코드 4(이슈 제목이 기존 REQ 제목이나 범위 `하지 않는 것` 항목과 겹침)면 `matches` 와 `excluded_matches` 를 보여 주고 "기존 개발의 하위 작업인가, 새 개발인가"
를 묻는다. 하위 작업이면 새 번호를 받지 않고 `<이 스킬의 base directory>/../start/SKILL.md` 의 "기존 개발과의 관계"
하위 작업 절차로 가고, 새 개발이 맞다고 하면 `--confirmed-new` 를 붙여 다시 부른다.

## 만들기

1. `docs/ssot/SRS.md` 를 읽는다. 없는데 `docs/ssot/PRD.md` 가 있으면 예전
   이름(PRD)으로 만든 저장소다 — 멈추고 그렇게 알린 뒤, 옮기는 방법은
   `/harness:srs` 스킬의 "옛 구조 확인" 절을 따르라고 안내한다. 아직 `templates/harness/SRS.md` 의 빈
   스텁 그대로면(요구사항 절에 표가 없거나 `REQ-001` 한 줄만 비어 있으면) 이 Spec 이
   근거로 삼을 SRS 가 없다는 뜻이니, 멈추고 먼저 `/harness:srs` 로 SRS 를
   만들라고 안내한다.
2. 이번 Spec 이 다룰 REQ 하나를 정한다(요구사항 1건 = Spec 1건). 사용자가 REQ 번호를 직접 줬으면 그것을
   쓰되, 그 REQ 의 상태(Backlog Status)가 `Dropped` 나 `Duplicate` 면 Spec 을 만들지 않고 그렇다고
   알린다. `On Hold` 도 만들지 않고 보류 중이라고 알린다(사용자가 `/harness:srs` 로 상태를 바꾸면 진행).
   그 REQ 의 `다음 단계` 열(SRS 요구사항 표)도 본다.
   - `개발` — 그대로 진행한다.
   - `미정` — 먼저 개발인지 설정인지 사용자에게 정하게 하고(모르면 멈춘다), `/harness:srs` 의 고치기대로 SRS 의
     다음 단계(개발이면 RICEFW ID `DEV-xxx` 도)를 고치고 변경 기록(`audit/changes/`, 종류 "결정")을 남긴 뒤 진행한다.
     `설정` 으로 정해지면 아래 `설정` 처럼 한다.
   - `설정` — Spec 을 만들지 않고 이 요구사항은 설정이라 Spec 이 없다고 알린다. 진행 원장에 그 DEV 번호 줄이
     없으면(방금 `미정` 에서 `설정` 으로 정한 경우 등) `/harness:srs` 의 "설정 요구사항" 대로 원장에
     `| DEV-xxx | <제목> | 설정 | <담당> | 대기 |  |` 줄을 올린다. 원장 파일(프로그램)은 아래 프로그램 선택처럼
     `audit/ledger/*.md` 목록에서 고르게 하고, 원장이 없는 저장소면 건너뛴다. 설정 내용은 SRS 상세 절의
     `Configuration Considerations` 에 쓴다고 안내하고 여기서 끝낸다.
   - 열이 없는 옛 SRS — 지금처럼 Spec 대상으로 보되, `/harness:srs` 로 `다음 단계` 열을 추가하자고 안내한다.

   번호를 안 줬으면 SRS 의 요구사항 표에서 `다음 단계` 가 `개발` 이고 상태가 `On Hold`·`Dropped`·`Duplicate` 가
   아니면서
   아직 어느 Spec 의 `## 근거 요구사항` 에도 적히지 않은 REQ(= 아직 Spec 이 없는 REQ)를 찾아 목록으로
   보여 주고 고르게 한다. `미정` 인 REQ 가 있으면 목록 끝에 "다음 단계 미정 N건" 으로 따로 알려 준다(고르면 위 `미정`
   처럼 먼저 정한다). `설정` 은 후보가 아니다. 상태 값은 Backlog Status(New / Planned / In Process / Done / On Hold /
   Dropped / Duplicate) 하나뿐이다 — 옛 `유효`·`변경됨`·`폐기` 로 적힌 SRS 면 `Dropped` 는 `폐기` 에 해당하고
   나머지는 Spec 대상으로 보되, 상태 값을 바꾸자는 안내는 `/harness:srs` 쪽 일이라고 알린다. 상세는 REQ 의
   `### REQ-xxx` 상세 절(Short Description, Acceptance Criteria …)에 있으니 함께 읽는다. 이 개발 건이 속할 프로그램(진행 원장 파일)도 함께
   묻는다 — `audit/ledger/*.md` 목록을 보여 주거나, 새 프로그램이면
   `templates/harness/audit-ledger.md` 틀로 새 파일을 만든다.
3. DEV 번호를 정한다. 2 의 REQ 번호가 있으면 그 숫자가 DEV 번호다(`REQ-003` →
   `DEV-003`). 그 번호가 `audit/ledger/*.md` 의 개발 건 표에 이미 있고 Spec 칸이
   `-` 이면 그 줄을 이어받는다. Spec 칸이 `설정` 이어도 SRS 의 그 REQ 다음 단계가 `개발` 이면 막지 않고 `-` 처럼
   취급해 이어받고, Spec 을 쓸 때 Spec 칸을 Spec 경로로 채운다. SRS 다음 단계가 `설정` 이면 설정 건이라 Spec 을 만들지
   않는다(2 의 `설정`). (2 의 프로그램 선택도 그 원장 파일로 정해진 것으로 보고 다시 묻지 않는다.) 근거 REQ 가 없으면 브랜치 이름의 이슈 번호로 `gh issue view`
   해 읽은 이슈 제목의 `[DEV-xxx]`(또는 본문의 `진행 원장: DEV-xxx` 줄)를 쓴다.
   어디서도 번호를 못 찾으면 위 "Spec 번호" 대로 `claim` 으로 찜한다. 번호를 직접
   계산하지 않는다. 같은 번호의 Spec 이 이미 있으면 새로 만들지 않고 "고치기" 로
   안내한다.
4. 양식을 고른다. `templates/forms/*.yaml`(양식 지도)을 모두 읽어 본다.
   - 폴더가 없거나 비었으면 "지도 없음" 이다. 이 단계를 건너뛰고 기존처럼
     `templates/harness/spec.md` 틀만 쓴다.
   - 읽지 못한 지도(파싱 오류, 필수 키 없음)가 하나라도 있으면 목록에서
     조용히 빼지 않는다. 어느 파일이 왜 안 읽히는지 알리고 멈춘다.
   - 모두 읽혔으면 각 지도의 `양식`·`설명` 을 목록으로 보여 주고, 이번
     개발 건에 쓸 양식을 매번 묻는다. 여러 개를 고를 수 있고, 하나도 안
     고르는 것도 된다.
   - 지도 형식은 `<이 스킬의 base directory>/form-map.md` 에 있다.
5. `templates/harness/spec.md` 틀대로 `docs/spec/DEV-xxx-<요약>.md` 를
   쓴다. `## 근거 요구사항` 에는 2 에서 고른 REQ 번호 하나를 적는다. 상태(Status)는 SRS 가 정본이라
   적지 않는다.
   Convention·Template·규칙 본문은 옮겨 적지 않고 링크만 적는다. `## 참조`
   에는 공통 개발 규칙(harness Plugin 의 `conventions/common.md`)을 GitHub
   링크 `https://github.com/jaeheeMin/blueward-harness/blob/main/plugins/harness/conventions/common.md`
   로 적는다 — 어느 저장소에서 이 Spec 을 읽어도 그대로 열리도록 상대 경로가
   아니라 이 고정 URL 을 쓴다. 이 프로젝트 `conventions/*.md` 는 저장소 안
   상대 경로로 함께 링크한다. 이번 설계와 관련된 CR 번호가 있으면 적는다 —
   예를 들어 설계에 반복문 안에서 DB 를 조회하는 부분이 있으면 CR-002 를
   적는다. 설계에서 아직 불명확한 점은 추측으로 채우지 않고 사용자에게 묻되,
   그래도 안 정해진 것은 `## 상세 설계` 아래 "미정" 으로 남긴다.
   `## 사용 객체` 표(`| 종류 | 이름 | 작업 | 비고 |`)에는 이 개발 건이 만들거나(생성)
   고치거나(수정) 읽기만 하는(참조) SAP 객체를 한 줄씩 적는다. 종류는 틀에 적힌 목록
   (`conventions/naming.md` 의 원어: Database Table, CDS View, Service Definition …)에서만
   고르고, 이름은 영문자로 시작하는 객체 이름이다(대소문자 무관, 네임스페이스는 `/DMO/I_TRAVEL` 꼴,
   공백·하이픈·한글 불가). 설계에서 객체가 정해지지 않았거나 이름을
   모르면 추측으로 채우지 않고 사용자에게 묻는다. 그래도 모르면 그 줄을 쓰지 않고(표를 비워
   둠) `## 상세 설계` 에 "미정" 으로 남긴다. 다른 개발 건과 같은 객체를 겹쳐 쓰는지 이 표로
   비교하므로 객체마다 한 줄이다.
   4 에서 양식을 골랐으면 고른 지도를 읽어 `## 양식 항목` 절을 `## 사용 객체`
   뒤에 쓴다. 표기와 키의 뜻은 `form-map.md` 를 따른다.
   - **파일명에 들어가는 항목부터 먼저 묻는다.** 지도 `산출.파일명` 의 `{이름}`
     자리마다 출처(`산출.자리`, 없으면 같은 이름의 칸)를 찾아 그 값을 받는다
     (예: 개발사양서는 개발 ID·Title, 버전은 처음이면 변경이력 0.1). 받은
     값으로 파일명을 만들어 지도 `검사_규칙` 의 filename 패턴(`패턴`/`pattern`)과
     바로 대조하고, 파일 이름에 못 쓰는 문자(`\ / : * ? " < > |`)가 있는지
     본다. 안 맞으면 무엇이 왜 안 맞는지(예: 개발 ID 는 `CO-006-01` 처럼
     `모듈-번호-순번`) 알리고 다시 묻는다. 맞으면 산출될 파일명(예:
     `BW_개발사양서_CO-006-01_예산관리 센터 사용자 필드 추가_v0.1.xlsx`)을
     보여 주고 확인받은 뒤 나머지 항목으로 넘어간다. 이 항목들은 `미정` 으로
     남기지 않는다 — 사용자가 아직 모른다고 하면 남기되, 양식 파일을 만들 수
     없다는 점을 그 자리에서 알린다.
   - 지도의 모든 시트를 담고, 칸·표·서술을 모두 적는다.
   - 해당 없는 시트는 `해당 없음`(시트 단위로만), `자동: true` 칸은 `자동`,
     `예시` 값은 옮기지 않는다.
   - 모르는 값은 추측하지 않고 묻는다. 그래도 없으면 `미정`.
   - `최대_행` 을 넘으면 사용자에게 알린다.
   - 지도를 못 읽거나 형식이 틀리면 통과로 넘기지 않고 멈춰서 알린다. 사용자가
     양식 없이 쓰라고 할 때만 양식 없이 쓴다.
   - 정본 관계: 양식에 칸·표·서술이 있는 내용은 `## 양식 항목` 이 정본이다.
     `## 상세 설계` 에는 같은 내용을 다시 쓰지 않고 "양식 항목 참조" 와 양식에
     자리가 없는 설계만 적는다.
   - 변경이력: 양식의 변경이력 표(예: Title 변경이력, Cover Change History,
     개정이력)는 Spec `## 변경 이력` 과 같은 사건을 적는다. 처음 만들 때는
     한 행(버전 0.1).
   - DEV 번호(`DEV-001`)와 양식의 개발 ID(예: `CO-006-01`)는 다른 체계다. 둘 다
     적되 섞지 않는다.
   - 양식 xlsx 파일은 작업본이 다 채워진 뒤 아래 "양식 파일 산출" 로 만든다.
6. 진행 원장에 등록한다. 그 프로그램의 `## 개발 건` 표에
   `| DEV-xxx | 내용 | [spec](../../docs/spec/DEV-xxx-<요약>.md) | 담당 |
   대기 |  |` 행을 추가하고, 2 에서 고른 REQ 번호가 `## 관련 요구사항` 에
   없으면 더한다. 3 에서 `/harness:start` 가 만든 줄을 이어받았으면 행을 새로
   추가하지 않고 그 줄의 Spec 칸만 위 링크로 채운다 — 상태·담당·마지막 PR 은
   건드리지 않는다.
7. 저장 전에 doc-guard 훅(`pre_write_guard.py`)이 `rules/spec.yaml` 로 파일
   이름과 필수 절을 검사한다. 막히면 사유를 읽고 빠진 절을 채운다. 훅이 죽어
   검사를 못 한 경우에는 통과나 위반이 아니라 검사를 못 했다고 알린다.
8. 마무리를 안내한다. 개발자에게 새 Spec 의 경로를 알려 준다. 필수 항목이 `미정` 이거나
   `최대_행` 을 넘은 것이 있으면 목록으로 알리고, 이대로는 양식 파일 산출이
   거부된다고 알린다. 양식을 골랐으면 양식 파일로 뽑을지 묻는다. 개발 결과를
   올리는 PR 은 `/harness:deliver` 로 만든다.

## 고치기 (SRS 가 바뀌었거나 설계가 바뀌었을 때)

1. 무엇이 왜 바뀌는지와 어느 REQ 가 바뀌었는지 받는다. `/harness:srs` 로
   SRS 를 고쳤다면 그때 남긴 변경 기록(`audit/changes/`)을 근거로 쓴다. 기존 개발의 하위 작업(이슈 제목 끝
   `(DEV-xxx)`)도 새 Spec 을 만들지 않고 그 DEV 의 Spec 을 고친다.
2. 해당 Spec 을 고친다. `## 변경 이력` 에 날짜, 바뀐 내용, 근거가 된 변경
   기록 링크를 한 행 추가한다.
   설계가 바뀌어 쓰는 객체가 달라지면 `## 사용 객체` 표도 함께 고친다. 그 절이 없는
   옛 Spec 이면 표를 넣을지 사용자에게 묻고(선택 절이라 없어도 검사는 통과한다), 넣기로
   하면 모르는 객체는 추측하지 않고 묻는다.
   `## 양식 항목` 이 있으면 바뀐 설계에 맞게 그 값도 함께 갱신한다.
   양식 변경이력 표에도 같은 행을 더한다(버전은 0.1 올림, 큰 변경이면 사용자에게
   묻는다).
3. 이번 변경에 대응하는 변경 기록이 아직 없으면(예: 설계만 바뀌고 SRS 는
   그대로인 경우) `audit/changes/YYYYMMDD-<요약>.md` 를
   `templates/harness/audit-change.md` 틀로 새로 쓴다. 종류는 "설계 변경"
   으로 적는다.
4. 진행 원장은 상태를 그대로 두고, 필요하면 `## 메모` 에 한 줄 남긴다.
5. 마무리를 안내한다. 개발자에게 바뀐 Spec 을 다시 AI 에 넣어 고치라고
   알린다.

## 양식 파일 산출

Spec 을 만들거나 고친 뒤 사용자가 양식 파일을 원할 때("양식 파일로 뽑아줘",
"xlsx 로 만들어줘") 쓴다. 작업본 `## 양식 항목` 의 값을 지도의 `템플릿` 복사본에
채워 `산출.폴더` 에 `산출.파일명` 으로 만든다. 서식·병합 셀·그림·다른 시트는
그대로 두고 값만 바꾼다. 양식이 없는 Spec 에는 쓰지 않는다.

```bash
e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "산출 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
uvx --from "$e" \
  python -m checker.export --spec docs/spec/DEV-001-<요약>.md --root "$(git rev-parse --show-toplevel)"
```

Bash 도구로 실행한다(Windows Git Bash 에서도 같다). 엔진 판은 플러그인 판과 같은 태그(`v{version}`)이고
`engine_spec.py` 가 정한다(`DOC_GUARD_ENGINE` 이 있으면 그것이 우선). 첫 줄이 실패하거나 빈 값이면(uv 가 없거나
플러그인 설치가 깨져 판을 정하지 못함) `uvx` 로 넘어가지 말고 거기서 멈춰 사유(`engine_spec.py` 가 낸 stderr)를
알리고 "산출 불능" 이라고 말한다. `@main` 이나 다른 판으로 대신 받지 않는다. PowerShell 도구는 `$e = uv run --no-project python
"${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py"; if ($LASTEXITCODE -ne 0 -or -not $e) { throw "산출 불능: 엔진 판을 정하지 못했다" }`
로 정한 뒤 `uvx --from $e python -m checker.export --spec … --root …` 로 부른다.
양식이 여럿이면 모두 만들고, 하나만 만들려면 `--form <양식 이름 또는 지도 파일 경로>` 를 더한다
(`--form Backlog` 와 `--form templates/forms/Backlog.yaml` 은 같다. 경로는 `--root` 기준 상대 또는 절대이고
`templates/forms/` 안의 지도 파일이어야 한다. 없는 파일이면 종료코드 2). 같은 이름 산출 파일이 이미 있으면
엔진이 그 파일이 `origin/main` 에 있는지 본다 — 없으면(이 브랜치에서 만든 판) 같은 버전으로 다시 산출하고
결과 JSON 에 `replaced: true` 가 붙는다. 엔진은 fetch 하지 않으므로 산출 전에 `/harness:sync` 나 `git fetch origin` 으로
`origin/main` 을 최신으로 맞춘다. 결과는
stdout 의 JSON 한 줄이다. stdout 이 JSON 으로 읽히지 않으면(uvx 실패, 엔진 못 받음 등)
종료코드와 무관하게 "산출 불능" 이라고 알린다. 거부(rejected)로 취급하지 않고 통과로도 넘기지 않는다.

- `status: ok` (종료코드 0) — `files` 의 경로를 알린다. 엑셀로 한 번 열어
  서식이 양식대로인지 확인하라고 사용자에게 권한다. 이 확인은 사람 몫이다.
  `warnings` 가 있으면 항목별 내용을 그대로 사용자에게 보여 준다(예: 해당 없음 시트에 템플릿
  샘플 그림·셀이 남아 있다, 제어 문자를 지웠다). 지도 밖 샘플은 산출이 지우지 않으므로
  엑셀에서 직접 확인해 지우게 한다. `rejected`·`error` 에서도 `warnings` 는 보여 준다.
- `status: warning` (3) — 파일은 만들었지만 표 값이 양식의 드롭다운 목록 밖이거나(`type: dropdown`), 허용 값을 읽지 못해
  검사하지 못한 열이 있다(`type: dropdown-unchecked` — 통과가 아니니 그렇다고 알린다). `warnings` 의 `type: dropdown`
  항목(행·열·값·허용 값)을 그대로 보여 주고 허용 값 중에서 고치게 한다. 고친 뒤 다시 산출하려면 방금 만든 파일을
  (아직 커밋 전이면) 지우거나 `--check` 로 먼저 확인한 뒤 산출한다.
- `status: rejected` (1) — 아무 파일도 만들지 않았다. `problems` 의 양식·시트·항목·
  사유를 그대로 보여 주고 작업본을 고친 뒤 다시 돌린다. 값을 추측해 채우지 않고
  모르는 값은 사용자에게 묻는다. 같은 이름 파일이 이미 있어 거부된 것이면 아래 "버전 올리기".
  사유가 "main 에 있는 판인지 판단하지 못해" 이면(git 없음·origin/main 못 읽음) 검사 불능이다 — fetch 한 뒤 다시 한다.
- `status: error` (2) — 작업본·지도·템플릿을 읽지 못했거나 작업본이 지도에 없는 것을
  가리키거나, 경로가 저장소 밖이거나, 예상하지 못한 오류가 났다. 산출하지 못했다고
  알리고 `problems` 의 원인을 보여 준다. 통과로 넘기지 않는다.

**버전 올리기.** main 에 이미 있는 판은 덮어쓰지 않고 지우지도 않는다(거부 사유 "main 에 이미 있는 판이다").
이 브랜치에서 만든 판(origin/main 에 없음)은 버전을 올리지 않아도 그대로 다시 산출된다. 내용이 바뀌면
작업본의 양식 변경이력 표(예: Change History, 변경이력, 개정이력)에 행을 더해 새
버전으로 올린 뒤(Spec `## 변경 이력` 에도 같은 사건을 적는다) 다시 산출한다. 파일
이름의 `v<버전>` 은 그 표의 마지막 행에서 오므로 새 파일이 만들어지고 이전 판은 남는다.

**검사는 이 스킬이 하지 않는다.** 저장 전 훅은 xlsx 같은 바이너리를 못 보므로 산출한
파일의 검사(파일 이름, 필수 시트, 표 머리글)는 PR 을 열 때 Actions(doc-guard)가
맡는다. 산출 성공은 doc-guard 통과가 아니다.

## 저장 전 검사

`docs/spec/` 아래 파일을 쓰거나 고칠 때마다 doc-guard 훅이 `rules/spec.yaml`
로 파일 이름(`DEV-\d{3,}-<요약>.md`)과 필수 절을 검사한다. 검사를 통과하지
못하면 저장이 막히고 사유가 나온다 — 그 사유대로 고친다.
