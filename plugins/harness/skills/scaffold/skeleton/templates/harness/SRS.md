# <프로젝트> SRS

이 프로젝트의 SSOT(Single Source of Truth) 다. 요구사항이 바뀌면 이 문서를
고치고, 바뀐 이유와 영향받는 Spec 은 `audit/changes/` 에 남긴다. 새로 만들
때도 고칠 때도 `/harness:srs` Skill 을 쓴다.

버전: 0.1

## 배경과 목표

이 프로젝트를 왜 하는지, 끝났을 때 무엇이 달라져 있어야 하는지를 적는다.

## 범위

- 하는 것: 이번 프로젝트가 다루는 범위를 적는다.
- 하지 않는 것: 일부러 빼는 범위를 적는다. 나중에 "이것도 되나요" 를 줄인다.

특정 요구사항에서 뺀 일이면 `하지 않는 것` 항목 끝에 `(REQ-001)` 을 붙인다(여러 개면 `(REQ-001, REQ-002)`).
꼬리표가 없으면 프로젝트 전체에서 하지 않는 일이다.

## AS-IS / TO-BE

지금 어떻게 하고 있는지(AS-IS)와, 이 프로젝트가 끝나면 어떻게 바뀌는지
(TO-BE)를 적는다.

## 요구사항

| ID | Title | Status | Priority (PO) | 출처 | 다음 단계 |
|---|---|---|---|---|---|
| REQ-001 |  | New |  |  | 미정 |

요구사항 1건은 개발 또는 설정 1건이고 표의 1줄이다. 한 개발 안의 세부 기능은 줄을
나누지 않고 그 요구사항의 상세 절에 쓴다. 번호(`REQ-001`)는 이슈 제목에 찜한 번호를
쓰고(`/harness:srs` 가 받는다), 그 Spec(`DEV-001`)과 진행 원장의 개발 건이 같은
번호를 쓴다. 번호는 다시 쓰지 않는다. 출처는 그 요구사항이 어느
문서·회의·질문 답에서 왔는지를 적는다.

열은 고객사 양식 지도(`templates/forms/`)가 있으면 그 지도의 열을 따르고(`/harness:srs`
가 읽는다), 없으면 위 여섯 열이 기본이다. 지도에 따라 `Development RICEFW ID` 같은 열이
표에 더 들어간다 — 다음 단계가 개발이면 REQ 와 같은 번호의 `DEV-001` 을 적고, 설정·미정이면 비운다.
지도가 없을 땐 이 열은 선택이다.
표의 열과 상세 절 소제목은 그 지도의 열 이름(지도에 없는 저장소는 이 틀의 열)과 md 전용 열만 쓴다. 이름을 새로 만들거나 틀리게 쓰면
doc-guard 가 "양식 밖 열" 로 거절한다 — 지도에 없는 열이 필요하면 양식 지도를 먼저 고친다.

`다음 단계` 는 이 요구사항이 SRS 다음에 어디로 가는지를 적는 md 전용 열이라 엑셀 양식에는 나가지 않는다.
값은 `개발`(→ Spec 을 만든다) / `설정`(→ Spec 없이 진행 원장에서 관리한다) / `미정`(→ `## 미결 사항` 에 남기고
정해지면 고친다) 셋뿐이다. 보류·취소는 이 열이 아니라 상태(On Hold / Dropped / Duplicate)로 적는다. 설정을 한
내용은 상세 절 `#### Configuration Considerations` 에 적는다. 상태는 Backlog 의 Status 하나로 적는다 —
New / Planned / In Process / Done / On Hold / Dropped / Duplicate. 없앤 요구사항은 줄을
지우지 않고 Dropped 로 남기고, 다른 요구사항과 겹치면 Duplicate 로 둔다. 우선순위는
Backlog 의 값(`1. Must-Have` …)을 쓴다. 양식에 드롭다운이 있는 열은 그 목록 안의 값만 쓴다.

긴 글(설명, 완료 조건, 제안 해결책, 의존성 등)은 표에 넣지 않고 요구사항마다 표 아래에
상세 절을 둔다. 상세 절 제목은 `### REQ-001 <요구사항 제목>`, 그 아래 소제목은 양식 열
이름(`#### Short Description`, `#### Acceptance Criteria`, `#### Proposed Solution`,
`#### Dependencies` …)이다. 양식이 없으면 `#### 설명`, `#### 완료 조건` 을 쓴다.

상세 절 본문에 다른 요구사항 번호(`REQ-002`, `DEV-002`)를 적으면 doc-guard 가 거절한다. 같은 개발이면 새 요구사항으로
쪼개지 말고 그 요구사항의 범위를 넓힌다. 정말 별개이면 `### REQ-001 …` 제목 바로 아래, 첫 `####` 소제목 앞에
`관계: 별개 — <이유>` 한 줄을 적는다(이 자리는 엑셀로 나가지 않는다). 자기 번호의 `DEV-001` 과 `옛 REQ-003` 처럼
앞에 `옛 ` 이 붙은 옛 표기는 세지 않는다.

`#### Short Description` 은 몇 줄짜리 요약이고 첫 줄은 요청 출처다(엑셀에 가는 칸이라 `출처`
열과 따로 적는다). 세부 기능·조건은 Acceptance Criteria 로 나눈다 — 한 셀이 너무 길면 엑셀에서
잘린다. 이슈 번호는 넣지 않는다(추적은 DEV 번호). 예:

```
### REQ-001 <요구사항 제목>

#### Short Description

요청: <사람(부서)>, <YYYY-MM-DD>, <근거(회의·메일·문서 링크)>
<요약 몇 줄>

#### Acceptance Criteria

- <세부 기능·조건>
```

## 참조

Convention 과 Template 과 규칙은 본문에 옮겨 적지 않고 링크만 적는다. 예:
`conventions/`, `templates/`.
