# audit

무엇이 왜 바뀌었고 어디까지 진행됐는지를 남기는 자리다. 세션이 끊겨도 이어서
진행하고, 나중에 "왜 이렇게 됐나" 에 답하기 위해 쓴다. 두 종류를 둔다.

## audit/changes/ — 변경 기록

`YYYYMMDD-<요약>.md` 형식으로, 기록 하나에 파일 하나를 쓴다(예:
`20260926-결재단계추가.md`). 무엇이 왜 바뀌었는지(요구사항 변경 / 설계 변경 /
결정 / 기타, 바뀐 REQ 와 파일, 근거, 영향, 관련 PR)를 담는다. 기록을 파일
하나에 몰아 적지 않는 이유는, 여러 사람이 같은 시각에 각자 기록해도 파일이
겹치지 않아 PR 이 충돌하지 않기 때문이다.

템플릿은 `../templates/harness/audit-change.md` 다.

## audit/ledger/ — 진행 원장

프로그램 하나에 파일 하나를 쓴다(예: `구매요청승인.md`). 그 프로그램에 걸린
REQ 목록과, 개발 건이 어디까지 왔는지(대기 / 진행 / 리뷰 / 완료)를 표로
담는다. 개발 건의 ID 는 `docs/spec/` 의 Spec 파일과 같은 DEV 번호를 쓰고,
Spec 칸에 그 파일 링크를 적는다 — 원장의 ID 로 Spec 을 곧장 찾을 수 있게
하기 위해서다.

템플릿은 `../templates/harness/audit-ledger.md` 다.

## 누가 쓰나

`/harness:srs`, `/harness:start`, `/harness:spec`, `/harness:deliver` Skill 이
작업하면서 이 형식으로 기록을 남긴다. 사람이 직접 적어도 된다.

진행 원장의 개발 건 줄은 이렇게 채워진다.

- `/harness:start` — feat·fix 작업을 시작할 때 이슈 제목에 번호를 찜하고, 개발 건으로
  등록할지 묻는다. 등록하면 `| DEV-xxx | <이슈 제목> | - | <담당> | 진행 |  |` 줄을
  만든다(번호는 찜한 번호). Spec 이 아직 없으므로 Spec 칸은 `-` 이고, 이슈 본문에
  `진행 원장: DEV-xxx (파일)` 줄을 남긴다.
- `/harness:spec` — start 가 만든 줄이 있으면 같은 번호로 Spec 을 만들고 그 줄의
  Spec 칸을 링크로 채운다. 줄이 없으면(start 를 거치지 않았으면) 근거 REQ 의 번호
  (없으면 찜한 번호)로 줄을 만들고 상태는 `대기` 다.
- `/harness:deliver` — PR 을 올리기 전에 상태를 `리뷰`, 마지막 PR 을 `#번호` 로 바꾼다.
- `완료` — 대표 `[DEV-xxx]` 이슈를 Closes 하는 PR 이면 `/harness:deliver` 가 처음부터 상태를 `완료`, 마지막 PR 을
  그 PR 번호로 써서 PR 에 담는다(병합되면 main 원장도 완료가 된다). 하위 작업 PR 은 `리뷰` 이고 대표 이슈를 안 닫은
  PR 도 그대로이니 그때 `완료` 는 사람이 PR 로 쓴다. 병합 뒤 Actions(`ledger-complete.yml`)는 원장을 쓰지 않고, 대표
  이슈를 닫은 PR 이 병합됐는데 그 행이 `완료` 가 아니면 이슈를 열어 알린다.

번호: 요구사항(`REQ-003`)·Spec(`DEV-003`)·원장의 개발 건(`DEV-003`)은 한 번호를 쓴다.
번호는 작업을 시작할 때 GitHub 이슈 제목에 `[DEV-003]` 로 찜한다(`/harness:start`,
`/harness:srs`). 다음 번호는 main 의 SRS·Spec·원장 번호와 모든 이슈 제목의 찜 번호
가운데 가장 큰 것에 1을 더한 값이다. 두 사람이 거의 동시에 찜해 같은 번호가 되면,
이슈를 만든 직후의 확인에서 더 늦게 만든 이슈의 번호가 바뀌고 알림이 뜬다.

## 검사

`rules/audit-changes.yaml` 과 `rules/audit-ledger.yaml` 이 파일 이름과 필수
절을 doc-guard 로 검사한다. 필수 절 목록은 각 템플릿의 `##` 제목에서 그대로
읽으므로, 템플릿을 고치면 검사 기준도 함께 바뀐다.
