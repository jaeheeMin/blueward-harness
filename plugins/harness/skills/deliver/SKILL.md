# /harness:deliver

커밋과 원격 동기화와 푸시와 PR 생성까지 한 번에 수행하는 스킬이다.
`<이 스킬의 base directory>` 는 이 스킬이 로드될 때 위에 표시되는 경로다.

인자로 `--base {브랜치}` 를 받는다. 생략하면 main 을 기준으로 삼는다.

1. 컨텍스트를 먼저 모은다. 현재 브랜치와 `git status --short` 와
   `git diff HEAD --stat` 와 `git diff HEAD` 와 최근 커밋 세 건을 읽는다.
   최근 커밋은 이 저장소의 메시지 문체를 맞추기 위한 참고 자료다.
2. 현재 브랜치가 main 이면 거부하고 `/harness:start` 를 안내한다. 변경이 없으면 그
   사실을 알리고 멈춘다.
3. 기준 브랜치를 `git fetch origin {base}` 로 가져오고,
   `git rev-list HEAD..origin/{base} --count` 로 새 커밋이 있는지 확인하고,
   있을 때만 리베이스한다.
4. 새 커밋이 있으면 `git rebase origin/{base}` 를 수행한다. **리베이스
   충돌이 나면 스스로 해결하지 않는다.** 충돌 파일 목록과 상황을 사용자에게
   보고하고, 리베이스를 중단한 뒤 기준 브랜치에서 딴 `-v2` 브랜치로 옮겨
   갈지 확인받는다. 새 브랜치 이름은 기존 이름 뒤에 `-v2` 를 붙인 것이고,
   이 이름도 브랜치 규칙을 만족한다. **확인 없이 브랜치를 갈아타지 않는다.**
5. 관련 개발 건(DEV 번호)을 찾는다. 브랜치 이름이나 이슈 본문에 `DEV-xxx`
   가 있는지, 이번 변경에 `docs/spec/DEV-xxx-*.md` 가 포함됐는지 본다. 이
   방법으로 못 찾았는데 이번 변경이 개발 작업으로 보이면(소스 코드 변경이
   있는 등) 사용자에게 관련 개발 건이 있는지 물어본다. 관련 개발 건이
   없으면 이후 단계의 진행 원장 관련 처리를 건너뛴다 — 이 스킬은 Audit 이
   없는 저장소(이 플러그인 저장소 자신 포함)에서도 그대로 쓰인다.
6. 변경을 의미 단위로 나눈다. 성격이 다른 변경이 섞여 있으면 여러 커밋으로
   나눈다. 커밋 메시지 형식은
   `<이 스킬의 base directory>/../../rules/commit-and-pr.md` 를 따르고,
   제목은 명사형으로 끝내며, 본문에 `Refs #{이슈번호}` 를 넣는다.
7. 스테이징에서 `.superpowers/` 와 `*handoff*.md` 를 뺀다. `.claude/` 와
   `CLAUDE.md` 와 `rules/` 는 이 저장소의 정식 산출물이므로 빼지 않는다.
8. `git push` 를 실행할 때는 명령 앞에 `DELIVER=1` 을 붙인다. **4단계에서
   리베이스를 실제로 수행했으면(원격에 새 커밋이 있어서 로컬 이력이
   바뀐 경우) `--force-with-lease` 를 붙이고, 리베이스를 하지 않았으면
   평범한 푸시를 쓴다.**

   - 리베이스를 하지 않은 경우: `DELIVER=1 git push -u origin HEAD`
   - 리베이스를 한 경우: `DELIVER=1 git push --force-with-lease origin HEAD`

   이 접두어는 이 스킬의 절차를 따르고 있다는 선언이며, harness 플러그인의
   push 가드 훅(`hooks/pre-bash-git-guard.sh`)이 이것을 보고 맨손
   `git push` 거부를 통과시킨다. **이 접두어가 통과시키는 것은 그 거부뿐이다.**
   `--force` 는 이 접두어를 붙여도 거부되고, main 커밋도 접두어와 무관하게
   거부된다. **이 명령은 다른 명령과 묶지 않고 단독으로 실행한다.** 훅은
   명령 문자열이 정확히 `DELIVER=1` 로 시작할 때만 이것을 알아본다.
   `cd /tmp && DELIVER=1 git push -u origin HEAD` 처럼 앞에 다른 명령을
   붙이거나 `env DELIVER=1 git push -u origin HEAD` 처럼 다른 방식으로
   변수를 넘기면 시작 문자열이 달라져 거부된다. 이 명령은 반드시 Bash
   도구로 실행하고 PowerShell 도구로 실행하지 않는다. PowerShell 에는
   `VAR=값 명령` 접두 문법이 없어 훅이 `DELIVER=1` 선언을 알아보지 못하고
   푸시를 거부한다.
9. 해당 브랜치의 PR 이 없으면 만들고, 있으면 본문을 갱신한다. PR 은 항상
   본인을 담당자로 지정한다. 지정에 실패하면 조용히 넘어가지 않고 실패
   사실을 보고한다. 관련 개발 건이 있으면 PR 본문에 `## 진행 원장` 절을
   넣는다(아래 "PR 본문 형식" 참고).
10. 관련 개발 건이 있으면(진행 원장이 있는 저장소면) PR 을 만들거나 갱신한
    뒤 그 개발 건의 행을 갱신한다. 상태를 `리뷰` 로, 마지막 PR 을
    `#{PR 번호}` 로 고친다. 이 갱신을 `docs: 진행 원장 갱신` 커밋(본문에
    `Refs #{이슈번호}`)으로 남기고, 8단계와 같은 `DELIVER=1` 규칙으로 다시
    `git push` 한다 — 이번에는 방금 만든 커밋 하나뿐이라 리베이스가 필요
    없으므로 평범한 푸시(`DELIVER=1 git push origin HEAD`)를 쓴다. 그사이
    원격 브랜치에 다른 커밋이 올라와 푸시가 거절되면 3·4단계로 돌아가
    `git fetch` 와 리베이스를 한 뒤 `--force-with-lease` 로 푸시한다. 리베이스
    충돌이 나면 4단계와 같이 스스로 해결하지 않고 보고한다. 관련
    개발 건이 없거나 이 저장소에 `audit/ledger/` 자체가 없으면 이 단계를
    조용히 건너뛴다 — 이 스킬은 Audit 이 없는 저장소에서도 쓰이기 때문이다.
    개발 건을 완료로 표시하는 것은 이 스킬이 아니라 PR 이 merge 된 뒤
    다음 `/harness:deliver` 나 사람이 한다(자동화는 아직 없다).
11. PR 주소를 사용자에게 보고한다.
12. 이 PR 이 `<이 스킬의 base directory>/../../rules/governance.md` 의
    "예외: 에이전트가 자기 PR 을 병합해도 되는 경우" 조건을 모두 만족하면 —
    변경 파일이 허용 범위 안에 있고, 언제나 사람이 병합해야 하는 경로를
    건드리지 않았고, `gh pr checks` 가 전부 통과했고 충돌 없이 병합
    가능하면 — squash 로 병합하고(`gh pr merge --squash`) 병합 결과를
    보고한다. 조건이 하나라도 애매하면 병합하지 않고, PR 링크와 함께 사람이
    병합해야 한다고 안내한다.

## PR 본문 형식

`## Summary` 와 `## Changes` 로 구성하고, 별도로 봐 줘야 할 것이 있을 때만
`## Review notes` 를 덧붙인다. 본문 끝에 `Closes #{이슈번호}` 를 넣는다.

관련 개발 건이 있으면 `## 진행 원장` 절을 추가해 그 개발 건이 등록된 진행
원장 파일과 DEV 번호를 링크한다(예: `[DEV-003](audit/ledger/구매요청승인.md)`).
`docs/ssot/` 아래 파일이 이번 변경에 포함되면(PRD 변경) `## Review notes` 에
"PRD 변경: 사람 승인이 필요하다" 한 줄을 넣고, 이 브랜치에서 추가한
`audit/changes/` 변경 기록 링크를 함께 적는다.

## 원격이 없을 때

원격이 연결되어 있지 않으면 커밋까지만 수행한다. 푸시와 PR 생성은 원격
연결이 필요하다는 사실을 사용자에게 보고하고 멈춘다.
