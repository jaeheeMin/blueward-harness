# /harness:start

작업을 시작하는 입구다. 다음 순서로 수행한다.

1. 현재 브랜치가 main 이 아니고 미커밋 변경이 남아 있으면, 먼저 `/harness:deliver` 로
   정리할 것인지 사용자에게 확인한다.
2. main 으로 이동하고 `fetch` 와 `pull --rebase` 를 실행한다. 세션이 worktree 에서
   열려 main 이 다른 worktree 에 체크아웃돼 있으면 `git checkout main` 이
   `'main' is already used by worktree` 로 실패한다. 이때는 그 main 을 건드리지 않고
   `git fetch origin` 만 한 뒤, 4단계에서 브랜치를 `origin/main` 에서 바로 딴다
   (`git checkout -b <브랜치> origin/main`).
3. 사용자가 설명한 작업 내용으로 GitHub 이슈를 만든다. 제목과 본문과 라벨을
   `<이 스킬의 base directory>/../../rules/issue-and-release.md` 의 형식에
   맞춘다. `<이 스킬의 base directory>` 는 이 스킬이 로드될 때 위에 표시되는
   경로다. 저장소 꼭대기에 `audit/ledger/` 가 있고 작업 type 이 `feat` 또는
   `fix` 면 먼저 아래 "기존 개발과의 관계" 를 확인하고, 새 개발일 때만
   `gh issue create` 대신 "번호 찜" 의 `reserve` 로 만든다.
4. 발급된 이슈 번호로 `{type}/{issue-number}-{work}` 브랜치를 만들고 이동한다.
   `type` 은 작업 성격에서 판단하고, `work` 는 영문 소문자와 붙임표로 요약한다.
5. 개발 건 등록 여부를 정한다(아래 "진행 원장 등록"). 해당하지 않으면 묻지 않고
   건너뛴다.
6. 만들어진 이슈 번호와 브랜치 이름을 사용자에게 보고한다. 원장에 등록했으면
   DEV 번호와 원장 파일도 함께 알린다.

이미 존재하는 이슈 번호를 사용자가 지정한 경우에는 3단계를 건너뛰고 그 이슈를
읽어 브랜치 이름을 만든다. 원장이 있는 저장소의 `feat`·`fix` 면 그 이슈를
"번호 찜" 의 `claim` 으로 받는다.

## 기존 개발과의 관계

원장이 있는 저장소의 `feat`·`fix` 는 번호를 찜하기 전에 이 작업이 기존 개발의 일부인지 먼저 확인한다. 한 개발이
REQ·DEV 두 개로 쪼개지는 일(#258)을 막으려는 단계다. 기존 이슈를 지정해 시작한 경우(`claim`)도 제목에 번호가
없으면 똑같이 확인한다.

```bash
uv run --no-project python "<이 스킬의 base directory>/reserve_number.py" list
```

결과는 JSON 한 줄이다. `devs[]` 마다 `number`, `req_title`, `lob`, `next_step`, `status`, `ledger`(원장 파일과
그 줄의 내용·상태), `spec`, `issues`(제목 앞 `[DEV-xxx]` 이슈), `subtasks`(하위 작업 이슈)가 있고, SRS 표에 없는
열은 키가 빠진다. 종료코드는 "번호 찜" 과 같다 — 3(원장 없음)이면 이 절을 건너뛰고, 2(판정 불능)면 사유를 알리고
멈춘다. 목록을 못 읽은 채 "새 개발" 로 넘어가지 않는다.

`devs` 가 비면 묻지 않고 새 개발이다. 아니면 번호·제목·LoB·다음 단계·상태를 표로 보여 주고 `AskUserQuestion`
으로 묻는다. 쉬운 말로, 보기마다 무엇이 달라지는지 적는다.

- **기존 개발의 하위 작업이다**(어느 번호인지도 고르게 한다) — 새 번호도 새 원장 줄도 만들지 않고, 이미 있는 그
  개발에 붙는다. 그 개발의 Spec·원장 줄을 이어서 쓴다.
- **새 개발이다** — 새 번호를 받고 원장에 새 줄이 생긴다. 이 개발은 다른 개발과 따로 Spec 을 갖는다.

**하위 작업이면 `reserve` 를 부르지 않는다.** `gh issue create` 로 일반 이슈를 만든다. 기존 이슈를 지정해 시작한
경우(`claim` 경로)는 `claim` 도 부르지 않고, 그 이슈를 `gh issue edit` 로 고친다(아래 두 항목을 그 이슈에 적용).

- 제목은 `<요약> (DEV-xxx)` 로, 끝에 번호를 붙인다. 맨 앞 `[DEV-xxx]` 는 쓰지 않는다 — 번호 계산이 맨 앞 대괄호만 읽으므로
  앞에 붙이면 새 번호를 받은 이슈처럼 잡힌다. 끝에 붙인 것은 번호 계산에 안 잡힌다. 기존 이슈는 제목 끝에 ` (DEV-xxx)`
  만 덧붙인다. 그 이슈 제목 맨 앞에 이미 `[DEV-…]` 가 있으면 새 개발 이슈이므로 이 경로에 오지 않는다(있으면 떼지 말고
  멈춰 사용자에게 알린다).
- 본문 배경에 `DEV-xxx 하위 작업` 이라고 쓰고 대표 이슈 링크를 건다(`[DEV-xxx]` 이슈. 없으면 원장 줄이나 Spec 링크).
  기존 이슈는 `gh issue edit` 로 본문 배경에 덧붙인다.
- 라벨은 작업 성격대로 붙인다. 브랜치는 기존 규칙 그대로 `{type}/{이슈번호}-{work}` 다.
- 원장에 새 줄을 만들지 않는다. 아래 "진행 원장 등록" 의 "이미 원장에 있는 DEV" 단계가 본문의 `DEV-xxx` 로 그 줄을
  찾아 상태를 `대기` 일 때만 `진행` 으로 바꾸고(`리뷰`·`완료` 면 묻는다), `/harness:deliver` 는 같은 DEV 번호로 그 줄을
  `리뷰`·마지막 PR 로 갱신한다. 하위 작업이 여럿이면 각 PR 이 같은 줄을 갱신하므로 마지막 PR 칸은 가장 최근 PR 번호로 덮인다.
  `완료` 는 사람이 모든 하위 작업을 보고 바꾼다.
- 이 하위 작업이 그 요구사항(REQ)의 범위를 넓히는 것이면(예: `하지 않는 것` 에 적혀 있던 항목을 하게 됨) 먼저
  `/harness:srs` 로 그 REQ 의 범위·완료 조건을 넓히라고 안내한다. 새 REQ 줄을 만들지 않는다.

## 번호 찜

요구사항·Spec·원장·이슈가 한 번호(`DEV-003`)를 쓴다. 번호는 작업을 시작할 때
이슈 제목 앞에 `[DEV-003] ` 로 찜해, 두 사람이 동시에 시작해도 서로 다른 번호를
받게 한다. 계산(origin/main 의 SRS·Spec·원장 번호와 모든 이슈 제목의 찜 번호 중
가장 큰 것 + 1)과 만든 직후 겹침 확인은 스크립트가 한다 — 손으로 계산하지 않는다.
`/harness:srs` 와 `/harness:spec` 도 같은 스크립트를 쓴다.

```bash
uv run --no-project python "<이 스킬의 base directory>/reserve_number.py" reserve \
  --title "<제목>" --body-file <본문 파일> --label type:feat
uv run --no-project python "<이 스킬의 base directory>/reserve_number.py" claim --issue <번호>
uv run --no-project python "<이 스킬의 base directory>/reserve_number.py" next
```

`uv` 가 없으면 `python` 으로 바로 부른다. `reserve` 는 제목을 `[DEV-xxx] <제목>`
으로 이슈를 만들고, `claim` 은 이미 있는 이슈에 번호가 없으면 붙이고 있으면 그
번호를 낸다. 결과는 JSON 한 줄이다(`number`, `issue`, `title`, `renumbered_from`).
제목은 `[DEV-xxx]` 를 뺀 내용만 넘긴다.

- 종료코드 0 — `number` 가 찜 번호다. `renumbered_from` 이 있으면 더 앞선 이슈와
  번호가 겹쳐 바뀐 것이다. 사용자에게 "번호가 겹쳐 DEV-xxx 로 바꿨다" 고 알린다.
- 종료코드 3 — 원장이 없어 찜하지 않는다. 이슈는 `gh issue create` 로 만들고
  제목에 번호를 붙이지 않는다.
- 종료코드 4 — 확인 필요(#261). 새 제목이 origin/main SRS 의 기존 REQ 제목을 포함하거나 그 반대라서, 이슈도 번호도
  만들지 않고 멈춘 것이다. stdout JSON(`status: confirm`)의 `matches`(번호·제목)를 사용자에게 보여 주고 "기존 개발의
  하위 작업인가, 새 개발인가" 를 `AskUserQuestion` 으로 묻는다(위 "기존 개발과의 관계" 와 같은 질문이다). 하위 작업이면
  그 절의 하위 작업 절차로 가고 `reserve`·`claim` 을 다시 부르지 않는다. 새 개발이 맞다고 하면 같은 명령에
  `--confirmed-new` 를 붙여 다시 부른다. 사용자 답 없이 `--confirmed-new` 를 붙이지 않는다. 번호를 새로 받을 때만
  보며, 이미 `[DEV-xxx]` 가 붙은 이슈의 `claim` 은 보지 않는다.
- 종료코드 2 — 판정 불능(git·gh 실패, 3번 다시 매겨도 겹침). 출력된 사유를 그대로
  알린다. 번호를 추측하거나 번호 없이 넘어가지 않는다. `reserve` 가 이슈를 만든
  뒤에 실패했을 수 있으니 이슈 목록을 확인하고 중복으로 만들지 않는다.

번호는 등록 여부를 묻기 전에 찜한다. 겹침을 막으려면 시작 시점에 잡아 두어야
하기 때문이다. 사용자가 원장 등록을 하지 않겠다고 하면 이슈 제목의 번호는 남고,
원장·Spec 에 쓰이지 않은 빈 번호가 될 수 있다(다음 계산은 이슈 제목도 훑으므로
다시 쓰이지 않는다).

## 진행 원장 등록

브랜치를 만든 뒤, 저장소 꼭대기에 `audit/ledger/` 가 없으면(이 플러그인 저장소
자신 포함) 이 절 전체를 건너뛴다. 있으면 아래 두 단계를 차례로 본다.

**먼저: 이미 원장에 있는 DEV.** 작업 type 과 상관없이(`docs`·`chore` 여도) 이슈 제목의 `[DEV-xxx]` 나
본문의 `진행 원장: DEV-xxx` 줄, 하위 작업 이슈의 제목 끝 `(DEV-xxx)`·본문 `DEV-xxx 하위 작업` 번호가 `audit/ledger/*.md` 의 `## 개발 건` 표에 이미 있으면(SRS 에서 `설정` 으로
정해져 Spec 칸이 `설정` 인 건, 또는 `/harness:spec` 이 Spec 만 올려 둔 건) 새 줄을 만들지 않는다. 그 줄의 상태를 본다.
`대기` 면 묻지 않고 `진행` 으로만 바꾸고, `진행` 이면 그대로 둔다. `리뷰`·`완료` 면 바꾸지 않고 사용자에게 알린 뒤
`진행` 으로 바꿀지 묻는다(`완료` 는 사람이 손으로 바꾸는 값이라 사용자가 허락하기 전에는 덮지 않는다). 어느 경우든 Spec·마지막 PR 은
건드리지 않고, 담당이 비어 있으면 `gh api user --jq .login` 으로 채운다. 아래 5(커밋)는 같게 하고, 6(이슈 본문 줄)은 본문에 그 줄이 이미 있으면
덧붙이지 않는다. 완료는 사람이 `완료` 로 바꾼다. 번호가 원장 여러 파일에 있으면 어느 파일인지 묻는다. 이 단계를
했으면 아래 새 등록(1~6)은 하지 않는다.

**그다음: 새 등록.** 번호가 원장에 없을 때, 작업 type 이 `feat` 또는 `fix` 일 때만 진행한다.
`docs`·`chore`·`refactor`·`test` 면 묻지 않고 건너뛴다. 기존 이슈를 지정해 시작했고 그 이슈 본문에 이미
`진행 원장: DEV-xxx` 줄이나 `DEV-xxx` 가 있으면 새로 등록하지 않는다.

1. 이 작업을 진행 원장에 개발 건으로 등록할지 사용자에게 묻는다. 아니라고 하면
   여기서 끝낸다.
2. 개발 건이 속할 프로그램(원장 파일)을 정한다. `audit/ledger/*.md` 목록을 보여
   주고 고르게 하거나, 새 프로그램이면 `templates/harness/audit-ledger.md` 틀로
   `audit/ledger/<프로그램>.md` 를 새로 만든다.
3. DEV 번호는 위 "번호 찜" 으로 이슈 제목에 잡은 번호다. 새로 계산하지 않는다.
4. 그 원장의 `## 개발 건` 표에 `| DEV-xxx | <이슈 제목> | - | <gh 사용자> | 진행 |  |`
   줄을 추가한다. Spec 칸은 Spec 이 아직 없으므로 `-` 이고, 담당은
   `gh api user --jq .login` 으로 얻는다. 표의 빈 줄(템플릿이 둔 자리 표시 줄)이
   있으면 그 줄을 쓴다.
5. 이 변경을 새 브랜치에서 `docs: 진행 원장 등록` 커밋으로 남긴다. 본문에
   `Refs #{이슈번호}` 를 넣고, 커밋 메시지 형식은
   `<이 스킬의 base directory>/../../rules/commit-and-pr.md` 를 따른다.
   `git add` 와 `git commit` 은 한 명령으로 묶지 않고 따로 실행한다(커밋 전
   비밀정보 검사가 staged 를 보기 때문). 푸시는 하지 않는다 — `/harness:deliver`
   가 한다.
6. 이슈 본문 끝에 `진행 원장: DEV-xxx (audit/ledger/<파일>.md)` 한 줄을 `gh issue edit`
   로 덧붙인다. `/harness:deliver` 가 이 줄로 개발 건을 찾아 `리뷰` 로 바꾸고,
   `/harness:spec` 이 같은 번호로 Spec 을 잇는다.

## 브랜치 이름 규칙

브랜치 이름 형식과 허용하는 타입 여섯 가지는
`<이 스킬의 base directory>/../../rules/branching.md` 를 따른다.

## 이슈 형식

이슈 제목과 본문 구성과 라벨 체계는
`<이 스킬의 base directory>/../../rules/issue-and-release.md` 를 따른다.

## 이슈 생성 방법

이슈는 `gh issue create` 로 만든다. 명령의 출력에서 발급된 이슈 번호를 읽어
브랜치 이름에 넣는다.

## 원격이 없을 때

원격 저장소가 연결되어 있지 않으면 `gh issue create` 가 실패해 이슈를 만들 수
없다. 이 경우 그 사실을 사용자에게 알리고 원격 연결을 요청한 뒤 멈춘다. 이슈
번호 없이 임의로 브랜치를 만들지 않는다.
