# /harness:manual

`docs/manual/<LoB>/` 의 사용자 매뉴얼 작업본(md)을 쓰고, 고객 양식 pptx 로 산출하는 입구다. 매뉴얼은 LoB(업무 영역)
폴더 아래 **업무 제목별로 파일 하나**이고, 한 파일에 어떤 개발 건(DEV)을 묶었는지 작업본에 적는다. 양식은 Project
Repository 의 `templates/` 에 있고 양식 지도는 `templates/forms/*.yaml` 이다. 양식은 바뀔 수 있으므로 이 스킬과 엔진에는
양식 고유 글자를 적지 않는다 — 쪽·항목 이름은 항상 지도에서 읽는다. `<이 스킬의 base directory>` 는 이 스킬이 로드될 때
위에 표시되는 경로다.

화면 위의 빨간 네모·번호는 캡처 도구(`checker.manual_capture`, #533)가 그림에 직접 그린다. 산출(pptx)은 **그림 경로만** 받는다.
캡처는 아래 "캡처" 절의 순서로 따로 돈다 — 사람이 로그인한 전용 Chrome 이 있어야 해서 산출과 한 번에 묶지 않는다.
거꾸로, 사람이 개발 전에 양식 pptx 에 직접 써서 올린 매뉴얼은 엔진(`checker.import_pptx`, #742)이 작업본과 그림으로 읽어 들인다 — 아래 "올린 pptx 읽어 들이기" 절.

`git rev-parse --show-toplevel` 로 Project Repository 루트를 확인한다.

## 작업본 형식

위치와 이름: `docs/manual/<LoB>/<번호>.<업무 제목>.md` (예: `docs/manual/Production/1.생산계획 보드.md`). `<LoB>` 폴더
이름은 작업본 표지의 `LoB` 값과 **대소문자까지 같아야 한다** — 지도 `산출.폴더` 의 `{LoB}` 자리를 채운 폴더가 작업본이 있는 폴더와
다르면 산출이 거부한다(`산출.폴더` 항목). 자리 값에 제어 문자, `/ \ : * ? " < > |`, 점만 있는 값, 끝의 점·공백, Windows 예약어(CON·PRN·AUX·NUL·COM1-9·LPT1-9,
확장자가 붙어도)가 있으면 역시 거부한다. 번호는 그 LoB 안의 순번이고 표지 `제목` 값이 `<번호>.<업무 제목>` 이다(파일명
앞부분과 같게). 파일명 규칙(`^\d+\..+\.md$`)은 `rules/manual.yaml` 이 강제한다.

```markdown
# 1.생산계획 보드

버전: 0.1

## 묶은 개발 건

| DEV | 제목 |
|---|---|
| DEV-012 | 생산계획 보드 |

## 양식 항목

### <양식> · 표지

| 항목 | 값 |
|---|---|
| LoB | Production |
| 제목 | 1.생산계획 보드 |
| 작성일 | 2026-11-01 |

### <양식> · 목차

해당 없음

### <양식> · 본문 · <화면 이름>

| 항목 | 값 |
|---|---|
| 업무명 | 생산계획 보드 |
| 화면 제목 | 조회 조건 |
| 기능 설명 | 이 화면이 하는 일 한두 문장 |

#### 그림

docs/manual/img/Production/조회조건_v0.1.png

#### 번호 설명

1. 번호 1 이 가리키는 곳의 설명
2. 번호 2 가 가리키는 곳의 설명

### <양식> · 끝

해당 없음
```

- **머리.** 첫 `##` 앞의 `버전: 0.1` 줄이 산출 파일명의 버전(`v0.1`)이 된다. 처음은 0.1, 올릴 때 0.1 씩이다. 줄이 없거나
  `x.y` 모양이 아니면 산출이 파일명을 만들지 못해 거부한다.
- **`## 묶은 개발 건`.** 이 파일이 다루는 DEV 를 한 줄씩(`| DEV | 제목 |`). DEV 칸은 `DEV-012` 꼴이고 절이 없거나 형식이 틀리면
  `rules/manual.yaml` 이 거절한다. 같은 DEV 를 두 매뉴얼 파일이 묶어도 되지만 제목이 겹치지 않게 업무 제목으로 나눈다.
- **`## 양식 항목`.** `### <양식> · <쪽 이름>` 이 표지·목차·끝이고, 반복 쪽은 `### <양식> · <쪽 이름> · <화면 이름>` 소절이
  화면마다 하나씩이다(위 예의 쪽 이름 표지·목차·본문·끝과 `LoB`·`제목` 같은 항목 이름은 **지도에서 읽은 것**이고, 양식이 바뀌면
  지도의 이름을 따른다). 소절 표기·`#### 그림`·`#### 번호 설명` 문법의 정본은 `<이 스킬의 base directory>/../spec/form-map.md`
  "pptx 지도" 절이다. 지도에 없는 쪽·항목·`####` 소제목(오타 포함)은 쓰지 않는다 — 저장할 때(훅)와 PR(doc-guard `form_columns`)이
  "양식 밖 항목" 으로 거절하고 산출도 멈춘다.
- **그림.** `#### 그림` 아래 **저장소 루트 기준** PNG 경로 한 줄(`![](경로)` 도 된다). 이미지는 `docs/manual/img/<LoB>/` 에 두고
  파일 이름 끝(확장자 앞)에 이번에 산출할 판을 붙이기를 권한다(`조회조건_v0.1.png`) — Spec 화면 캡처(#348)의 규칙을 따른 관례다.
  **pptx 산출은 이 이름 규칙을 검사하지 않는다**(Spec 캡처의 "캡처가 옛 판" 검사는 xlsx 산출에만 있다). 판을 올릴 때는 캡처를 다시
  찍어 새 이름으로 바꾸는지 사람이 챙긴다.
- **번호 설명.** `1. 글` 목록이고 번호는 그림에 캡처 도구가 그린 번호와 같다. 이어지는 줄은 들여 쓴다. 한 쪽에 다 안 들어가면 산출이
  같은 화면을 다음 쪽으로 넘긴다(`pages-split` 경고).
- 값을 모르면 추측하지 않고 사용자에게 묻는다. 비었거나 `미정` 인 값은 산출이 거부하므로, 그래도 모르면 `미정` 으로 남기고 산출이
  거부된다고 알리거나(그림은 아래 "캡처 없는 화면") 그 화면을 넣지 않고 "못 쓴 것" 으로 적는다.

## 0단계: 브랜치 확인

작업본을 쓰기 전에, 지금 브랜치가 이번 매뉴얼 작업에 맞는지 확인한다. 확인은 `<이 스킬의 base directory>/../start/SKILL.md` 의
"다른 스킬이 부르는 브랜치 확인" 을 그대로 따른다 — 미커밋 변경, main 이면 start 절차, 다른 작업 브랜치면 같은 일인지 판단·질문,
판정 불능이 거기 있다. start 를 따로 부르라고 하지 않는다. 이 스킬에서 정하는 것은 아래뿐이다.

- **이번 작업 설명**은 "매뉴얼 — `<LoB>` `<업무 제목>`" 한 줄이다. LoB·업무 제목·묶을 DEV 를 받은 뒤에 브랜치를 비교한다(그 전에는
  읽기만 하고 파일을 쓰지 않는다).
- **같은 일의 판단 기준.** 브랜치 이슈 제목이 같은 업무 제목의 매뉴얼 작업이거나, 이슈의 DEV 가 묶을 DEV 중 하나와 같고 사용자가
  매뉴얼을 이 브랜치에서 쓰겠다고 하면 같은 일이다. 아니면 묻는다.
- **main 이면 번호 없는 작업 이슈를 만든다.** start 절차를 `docs` 작업으로 수행한다 — 제목은 `매뉴얼 — <LoB> <업무 제목>`, 브랜치는
  `docs/{이슈번호}-…`. 묶는 DEV 의 대표 `[DEV-xxx]` 이슈를 브랜치 이슈로 쓰지 않는다(개발 PR 이 병합될 때 닫혀야 하는 이슈라서다).

## 만들기

1. **LoB·업무 제목·묶을 DEV 를 묻는다.** 모르는 값은 추측하지 않는다. LoB 폴더가 이미 있으면(`docs/manual/*/`) 목록을 보여 주고
   고르게 하며, 같은 LoB 의 기존 파일(`<번호>.*.md`)로 다음 번호를 정한다. 같은 업무 제목의 작업본이 이미 있으면 새로 만들지 않고
   아래 "고치기" 로 간다. 파일명(`<번호>.<업무 제목>.md`)에는 파일 이름에 못 쓰는 문자(`\ / : * ? " < > |`)를 쓰지 않는다.
2. **자료를 읽는다.** 묶을 DEV 마다 `docs/spec/DEV-<번호>-*.md` 의 `## 상세 설계`, `## Launchpad 노출`(메뉴 경로·타일 이름), `## 권한`
   (누가 쓸 수 있는지)을 읽는다. 기존 `docs/manual/*.md` 매뉴얼이 있으면 같이 읽는다. Spec 에 없는 동작·화면은 지어내지 않는다 —
   Spec 이 `미정` 인 곳과 Spec 에 없어 모르는 곳은 사용자에게 묻고, 그래도 없으면 그 화면을 넣지 않고 마무리 안내의 "못 쓴 것" 에
   적는다. 시험하지 못한 동작은 Spec·`audit/changes/` 에 확인했다고 적힌 만큼만 쓴다.
3. **양식 지도를 찾는다.** `templates/forms/*.yaml` 중 `템플릿` 이 `.pptx` 인 지도(`쪽` 목록이 있다)를 모두 읽는다.
   - 지도 폴더가 없거나 pptx 지도가 하나도 없으면 **멈추고** 지도가 없다고 알린다. 안내만 한다: 양식 pptx 를 `templates/` 에 넣고
     `python -P -m checker.export_pptx --dump <양식.pptx>`(엔진 호출은 아래 "산출" 과 같은 `uvx`)로 쪽마다 도형의 글자·위치와 `찾기` 가
     유일한지 본 뒤 `form-map.md` "pptx 지도" 대로 지도를 쓴다. 지도를 이 스킬이 대신 추측해 만들지 않는다.
   - 읽지 못한 지도(파싱 오류, `쪽` 없음)가 있으면 목록에서 조용히 빼지 않고 어느 파일이 왜 안 읽히는지 알리고 멈춘다.
   - pptx 지도가 여럿이면 `양식`·`설명` 을 보여 주고 고르게 한다. 하나면 그것으로 한다.
   - 지도의 `검사_규칙` 이 가리키는 파일(`rules/manual-output.yaml`)이 없거나, `rules/manual.yaml`·`templates/harness/manual.md` 가
     없으면 아래 "규칙 설치" 로 안내한다. 산출 폴더·파일명 모양은 지도의 `산출` 이 정한다(`산출.폴더` 에 `{LoB}` 같은 자리를 쓸 수
     있다 — 파일명과 같은 자리 규칙).
4. **작업본 초안을 쓴다.** 지도의 쪽 이름·항목 이름을 그대로 써서 `docs/manual/<LoB>/<번호>.<업무 제목>.md` 를 위 형식으로 쓴다.
   - 화면은 사용자가 쓰는 순서(메뉴 진입 → 조회 → 처리 → 결과 확인)로 한 화면씩 `본문` 소절로 나눈다. 한 화면의 `번호 설명` 은 그림에
     번호를 그릴 곳마다 한 항목이다.
   - `기능 설명` 은 그 화면이 무엇을 하는지 한두 문장으로, 지도의 칸 크기에 들어갈 길이로 쓴다. 긴 내용은 번호 설명으로 나눈다.
   - 이미 캡처가 있으면 그 경로를, 없으면 아래 "캡처 없는 화면" 대로 한다. 경로를 지어내지 않는다.
   - 표지의 `작성일` 같은 날짜 항목은 오늘 날짜로 채운다. 이름·담당자처럼 모르는 값은 묻는다.
5. 저장 전에 doc-guard 훅(`pre_write_guard.py`)이 `rules/manual.yaml` 로 파일 이름·필수 절·`묶은 개발 건` 표·양식 밖 항목을 검사한다.
   막히면 사유대로 고친다. 훅이 죽어 검사를 못 한 경우는 통과나 위반이 아니라 검사를 못 했다고 알린다. 훅이 막으면 우회하지 않고
   사유를 알린다.

## 캡처 없는 화면

그림 파일이 없는 화면을 빈칸이나 임시 그림으로 통과시키지 않는다(`CLAUDE.md` 7번 — 검사를 못 한 것을 통과로 뭉개지 않는다).

- 작업본은 쓸 수 있다. 그림 경로를 아직 모르는 화면은 `#### 그림` 에 **예정 경로**(`docs/manual/img/<LoB>/<화면>_v<판>.png`)를 적어 두거나
  `미정` 으로 둔다. 어느 쪽이든 파일이 없으면 산출이 거부한다.
- 산출 전에 `--check` 를 돌린다. 캡처가 없는 화면마다 `problems` 에 화면 이름(`본문 · <화면 이름>`)과 `그림` 항목이 한 줄씩 나온다.
  그 목록을 **그대로 사용자에게 보이고** "이 N 개 화면의 캡처가 없어 산출하지 못했다. 아래 "캡처" 절로 찍을지 알려 달라" 고 묻는다.
- 일부 화면만 빼고 산출하자는 제안은 사용자가 먼저 말하지 않으면 하지 않는다. 사용자가 그렇게 정하면 그 화면 소절을 작업본에서 빼고
  마무리 안내의 "못 쓴 것" 에 빠진 화면 이름을 적는다.

## 캡처

사용자가 "매뉴얼 캡처해 줘", "화면 찍어 줘" 라고 하면 쓴다. 사람이 로그인해 둔 **전용 Chrome** 에 붙어 화면마다 1600x900 그림을 찍고, 화면에 보이는
이름으로 요소를 찾아 빨간 네모와 번호를 그림에 직접 그린 뒤, 작업본의 `#### 그림`·`#### 번호 설명` 을 채운다. 로그인·화면 이동에 필요한 값은
받아 적지 않는다 — 비밀번호·토큰을 파일이나 명령에 쓰지 않는다. **실제 테넌트(로그인 필요)에서는 사람이 로그인해야 하므로 이 절차는 사람과 함께 돈다.**

### 1. 찍을 화면 목록을 쓴다

작업본 옆에 같은 이름으로 `docs/manual/<LoB>/<번호>.<업무 제목>.capture.yaml` 을 쓴다. 화면 이름은 작업본 `### <양식> · 본문 · <화면 이름>` 소절의
마지막 이름과 **같아야** 한다(소절이 없으면 먼저 만든다 — 도구는 소절을 새로 만들지 않고 그 안의 `#### 그림`·`#### 번호 설명` 만 채운다).

```yaml
화면:
  - 이름: 조회 조건                      # 작업본 소절의 화면 이름
    앱: "#ProductionPlanBoard-display"   # 선택. 테넌트 주소 뒤에 붙는 Launchpad 해시(`#` 로 시작)
    준비:                                # 선택. 필터 값 넣기, 드롭다운 고르기, 버튼 누르기, 팝업 열기
      - {입력: 플랜트, 값: "1010"}       # 값은 따옴표로 감싼다(1010 → 숫자가 되고 01 은 앞의 0 이 사라진다). 앱이 기억한 값이 이미 같으면 넘어가고, 다른 값이면 지우고 넣는다
      - {선택: 생산방식, 값: "반복제조"}  # Select·ComboBox 에서 보이는 항목 글자가 값과 같은 것을 고른다
      - {누르기: 이동}
      - {팝업: 그루핑}                   # 선택. 그 버튼을 눌러 뜬 팝업(대화상자 하나)을 찍는다. 마지막 단계 하나만. 표시는 팝업 안에서만 찾는다. `팝업` 단계는 팝업의 확인·저장을 누르지 않는다
      - {팝업: 백로그상태, 행: 3}         # 버튼이 아니라 표 칸을 더블클릭해야 열리는 팝업. 그 열(이름이 유일해야 한다)의 보이는 본문 3번째 행 칸(칸 안 아이콘이 있으면 그 아이콘)을 더블클릭한다. 칸이 없거나 팝업이 안 뜨면 검사 불능
      - {행 고르기: 상태, 행: 1}          # 쓰기 시험용. 그 열(이름이 유일해야 한다)의 보이는 본문 1번째 행의 행 선택 칸을 실제로 클릭하고 선택됐는지 확인한다(못 찾거나 선택이 안 되면 검사 불능)
      - {창 누르기: OK}                  # 쓰기 시험용, `바꿈: true` 화면에서만. 지금 떠 있는 대화상자(정확히 하나, MessageBox 포함) 안에서 글자·aria-label·title 이 같은 버튼 하나를 누른다. 버튼이 없거나 여럿이면 검사 불능
    바꿈: true                           # 선택. 데이터를 바꾸는 화면(`창 누르기` 를 쓰려면 필요). --allow-write 없이는 연습으로 돌고 첫 `창 누르기` 앞에서 멈춘다(아래 "쓰기 시험")
    배율: 0.9                            # 선택(0.5~1.0). 넓은 표가 한 화면에 안 들어갈 때 이 화면만 축소해 찍는다(그림은 그대로 1600x900)
    확인:                                # 선택. 준비가 끝난 뒤 찍기 직전에 화면의 값이 맞는지 본다(읽기만 한다)
      - {열: 플랜트, 값: "1010"}         # 그 열의 보이는 모든 행이 이 값이어야 맞음(값은 따옴표로 감싼 글자로 쓴다 — 숫자 그대로 쓰면 거부)
      - {열: 상태, 행: 1, 값: "완료"}     # 그 열의 보이는 본문 1번째 행 칸 하나만
      - {글자: 조회 결과가 없습니다}      # 화면에 보이는 요소에 이 글자가 있어야 맞음
      - {알림: 취소 완료}                # 준비 단계 동안 보인 MessageToast 글 중 이 글이 든 것이 있어야 맞음(쓰기 시험용)
      - {열: Message, 행: 1}             # 값 없이 행만 쓰면 그 칸 값을 기록한다(판정 없음. 생긴 문서 번호 등)
    표시:                                # 필수. 번호는 이 목록 순서다
      - {종류: 필터, 이름: 플랜트, 설명: 생산 플랜트를 고른다}
      - {종류: 열, 이름: 상태, index: 2, 설명: 오더 상태를 본다}
```

- **종류**: `필터`(라벨과 입력 칸을 묶은 영역), `버튼`, `열`(머리글부터 표 아래 끝까지), `그 밖`(그 글자가 든 요소). `이름` 은 화면에 보이는 글자 그대로
  (끝의 `:`·`*` 는 무시). `설명` 은 작업본 `번호 설명` 의 그 번호 문장이 된다(한 줄).
- **넓은 표(`열` 여럿)**: 같은 화면의 `열` 표시가 둘 이상이면 도구가 열마다 따로 넘기지 않고, 그 열들이 다 보이는 가로 스크롤 위치 하나로 한 번에 넘긴다.
  열들의 가로 범위가 표의 보이는 폭보다 넓으면 찍지 않고 `검사 불능` 으로 알리며, 사유에 **나누기 제안**(왼쪽부터 들어가는 만큼 묶은 1화면·2화면, `열` 이 아닌
  버튼·필터는 첫 묶음 화면에 둔다)과 **필요 `배율`** 을 적는다. 화면을 나눠 목록에 따로 적거나, 그 화면에 `배율: 0.9` 를 적는다(축소하면 글자가 작아지니 나누는 쪽이 먼저다).
- **확인** 은 값을 읽기만 한다(확인 자체는 누르거나 바꾸지 않는다). 항목은 `{열, 값}`·`{열, 행, 값}`·`{글자}`·`{알림}`·`{열, 행}`(기록) 중 하나이고, 모르는 키·`열`·`글자`·`알림` 을 함께 쓴 항목·`값`도 `행`도 없는 `열`·1 미만이거나 정수가 아닌 `행`·빈 글은
  `--check` 에서 거부한다. `값` 은 따옴표로 감싼 글자만 받는다 — 따옴표가 없으면 YAML 이 `0010` 을 8 로, `12:30` 을 750 으로 읽으니 숫자도 `"0010"` 처럼 감싼다(숫자·실수·bool 은 거부).
  비교는 양쪽의 공백을 접고 앞뒤 공백·끝의 `:`·`*` 를 뗀 뒤 **정확히 같은지** 본다. 열은 머리글에 `aria-colindex` 가 있는 표만 읽는다.
  `글자` 는 보이는 요소의 글과 보이는 입력칸(input·textarea)의 값에서 찾는다. 열 칸의 글자가 비었는데 입력칸·체크박스·아이콘이 들어 있으면 글자로 읽을 수 없는 칸이라 그 항목은 `검사 불능` 이다(진짜 빈 칸은 `다름`).
  `행: N` 은 지금 화면에 온전히 보이는 본문의 N번째다(표가 스크롤돼 있으면 다른 행이 된다).
- **앱** 은 해시만 적는다. 테넌트 주소는 `env/manual-capture.yaml` 의 `테넌트: https://호스트/경로`(`https` 만. 클라이언트를 가르려면 `?sap-client=100`(숫자 3자리)·`&sap-language=KO`(영문 2자리) 쿼리만 붙일 수 있고, 앱 해시는 그 뒤에 붙는다. 그 밖의 쿼리 키·`#`·계정·비밀번호·토큰이 있으면 거부한다). 포트를
  바꾸면 같은 파일에 `포트:`(숫자가 아니면 검사 불능). 도구는 화면마다 현재 탭의 출처가 이 주소의 출처와 같은지 확인한다(다르면 로그인 화면일 수 있어 검사 불능). 이 파일이 없으면 사용자에게 주소를 묻고, 파일로 남길지 묻는다(`env/` 는 Project Repository 에 둔다).
- **준비 단계는 최소한** 으로 둔다. 팝업을 열거나 여러 화면을 거치는 흐름, 조건부 단계는 이 목록이 다루지 않는다(여러 화면을 거치는 흐름은 범위 밖 — 사람이 그 상태를 만들어 둔 채
  `앱` 을 빼고 찍거나, 그 화면은 "못 찍은 것" 으로 알린다). 한 화면 안에서 행을 고르고 확인 창의 버튼을 누르는 쓰기 흐름은 `바꿈: true` 와 아래 "쓰기 시험" 절로 한다.
- 같은 이름이 화면에 둘 이상이면 도구가 고르지 않는다(`ambiguous`). **화면 밖(가로 스크롤 밖 등)에 같은 이름이 더 있어도** 마찬가지다 — 보이는 것이 하나뿐이어도 고르지 않는다.
  사람이 `index`(1부터, 화면 밖을 포함한 전체의 위에서 아래·왼쪽에서 오른쪽 순)를 적는다. 고른 번째가 화면 밖이면 `not_found` 다.
- 화면마다 **강제로 다시 연다**(같은 주소여도 다시 로드). 앞 화면에서 넣은 값·열린 상태가 남지 않는다.

목록을 쓴 뒤 브라우저 없이 형식을 확인한다(아래 `--check`). 통과하면 다음으로 간다.

### 2. 전용 Chrome 을 띄우고 사람이 로그인한다

**보안.** 디버깅 포트는 `127.0.0.1` 에만 연다. 엔진도 `127.0.0.1` 이 아닌 주소(`localhost`·다른 PC)는 거부한다. 로그인 쿠키가 든 프로필 폴더는 **저장소 밖**
임시 폴더에 둔다(저장소 안·클라우드 동기화 폴더·공유 폴더에 두지 않는다). 평소 쓰는 Chrome 과 섞이지 않게 `--user-data-dir` 로 별도 프로필을 쓴다.

PowerShell(Windows). 프로필 경로는 **짧게** 둔다(긴 경로에서는 Chrome 이 만든 파일을 나중에 못 지운다):

```powershell
$profile = "$env:TEMP\manual-chrome"
Start-Process "C:\Program Files\Google\Chrome\Application\chrome.exe" -ArgumentList `
  "--remote-debugging-address=127.0.0.1","--remote-debugging-port=9222","--user-data-dir=$profile","--no-first-run","--disable-backgrounding-occluded-windows","--disable-renderer-backgrounding","--disable-background-timer-throttling","<테넌트 주소>"
```

- 사용자에게 **그 창에서 로그인**하게 하고, 캡처할 앱이 속한 테넌트 탭을 **하나만** 남기라고 한다(탭이 여럿이면 도구가 고르지 않고 멈춘다. 필요하면 `--tab <주소나 제목의 글>`).
  로그인을 대신 입력하지 않는다.
- 캡처하는 동안 그 창을 최소화하거나 다른 창으로 가리지 않는다(가려지면 화면이 그려지지 않는다. 도구가 맨 앞으로 가져온다). 위 `--disable-…` 세 옵션은 가려진 창을 Chrome 이 멈추지 않게 한다.
  창을 최소화하면 Chrome 이 그리지 않아 도구가 창 상태를 `normal` 로 되돌린다. 그래도 `visibilityState` 가 `visible` 이 아니면 **검사 불능**이다(창을 화면에 띄우고 다시).

### 3. 캡처를 돈다

```bash
e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "캡처 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
uvx --from "$e" \
  python -P -m checker.manual_capture --list "docs/manual/<LoB>/<번호>.<업무 제목>.capture.yaml" --root "$(git rev-parse --show-toplevel)" [--check] [--screen "<화면 이름>"] [--allow-write]
```

엔진 판·`uvx`·PowerShell 호출 방법은 `<이 스킬의 base directory>/../spec/SKILL.md` "양식 파일 산출" 과 같다. 먼저 `--check`(브라우저에 붙지 않고 목록·작업본 소절·주소를 확인),
통과하면 `--check` 를 빼고 돈다. 한 화면만 다시 찍을 때는 `--screen`. stdout 은 JSON 한 줄이고 종료코드는 다음과 같다.

- `0` `ok` — 모든 화면을 찍었고 요소를 다 그렸다. 그림은 `docs/manual/img/<LoB>/<화면 이름>_v<판>.png`(판은 작업본 머리 `버전:`)에 저장되고, 작업본의
  그 화면 `#### 그림` 은 이 경로로, `#### 번호 설명` 은 `1. 설명 …`(목록 순서)으로 바뀐다. 바뀐 내용은 `git diff` 로 사용자에게 보인다.
- `1` `incomplete` — 찾지 못한(`not_found`) 또는 같은 이름이 여럿인(`ambiguous`) 요소가 있다. 그 화면은 찾은 것만 그려 `<화면 이름>_미완_v<판>.png` 로 따로 저장하고
  **작업본은 고치지 않는다.** `screens[].못 찾은 것` 을 번호·종류·이름·사유로 **그대로 보인다.** 추측해서 그리거나 통과시키지 않는다. 사람이 이름·`index` 를 고쳐 다시 돌리거나
  (사유 예: 가로 스크롤 밖 열은 도구가 스크롤하지만 다른 열과 한 화면에 함께 못 보이면 못 찾은 것이다 — 화면을 나눠 찍는다), 그 요소를 뺀다.
- 확인 결과. 화면에 `확인` 이 있으면 결과 JSON 의 그 화면에 `확인` 배열이 붙고 항목마다 `결과` 가 `맞음`·`다름`·`검사 불능` 이다. 그림은 확인 결과와 상관없이 기존 규칙대로 찍는다(파일 이름 `_미완` 은 표시를 못 찾았을 때만).
  - `다름` — 값을 읽었는데 기대와 다르다. `실제` 에 다른 행 번호와 값(`[{"행":3,"값":"1720"}]`, 5개까지, 더 많으면 `다른 행 수`)을 낸다. 글자는 화면에 없으면 `다름`.
    `{열, 값}` 은 맞음이든 다름이든 `읽은 행 수` 를 낸다. 보이는 행만 읽는다 — 맞음이라도 `읽은 행 수` 를 보이고, 화면 밖 행은 보지 않았다고 알린다.
  - `검사 불능` — 열을 못 찾았거나 여럿이거나, `aria-colindex` 가 없거나, 접힌(pop-in) 열이거나, 보이는 행이 없거나 `행` 이 보이는 행 수보다 크거나, 비교할 칸이 입력칸·체크박스·아이콘이거나, 팝업이 사라져 글자를 읽지 못했거나, 화면 값을 읽지 못했다. `사유` 를 그대로 보인다. 맞음·다름으로 뭉개지 않는다.
  - 화면 자체가 `검사 불능` 이면 그 화면의 확인은 돌지 않았다(`확인` 배열이 없다).
  - 전체 `status`·종료코드: 확인 중 `검사 불능` 이 하나라도 있으면 `unavailable`(2), 아니고 `다름` 이 있으면 `incomplete`(1). 표시가 미완인 화면(1)·화면 검사 불능(2)과 합쳐 더 나쁜 쪽을 따른다. 사용자에게는 화면·확인·결과·정답(기대)·실제를 표로 보인다.

  | 화면 | 확인 | 결과 | 정답 | 실제 |
  |---|---|---|---|---|

- 쓰기 결과(#744). `바꿈: true` 화면이 있으면 결과 JSON 에 `쓰기` 가 `연습`(`--allow-write` 없음)이나 `허락` 으로 붙는다. `--allow-write` 없이는 `창 누르기` 를 누르지 않는다 — 첫 `창 누르기` 앞까지 돌아
  그 상태(대화상자가 떠 있다)를 찍고, 그 버튼이 있는지만 확인한 뒤 Cancel·취소 버튼(없으면 Escape)으로 닫고 그 화면 `상태` 를 `멈춤` 으로 낸다(작업본은 고치지 않는다). `창 누르기` 가 없는 `바꿈` 화면은
  어디서 멈출지 몰라 브라우저를 건드리지 않고 `멈춤` 이다. `멈춤` 화면이 있으면 전체 `status` 는 `incomplete`(종료 1)다. `--allow-write` 이면 끝까지 돌고, 첫 `창 누르기` 뒤에 검사 불능·미완이 된 화면은
  `데이터 바뀜: true` 와 사유 앞 "데이터가 바뀌었을 수 있다 — " 가 붙는다(완료여도 `데이터 바뀜: true`). 준비 단계 동안 보인 MessageToast 글은 화면의 `알림` 에 모이고, `{알림}` 확인이 그 글을 본다
  (알림을 못 읽으면 `검사 불능`, 하나도 못 모았으면 `다름`). `{열, 행}` 확인은 `결과: 기록`·`실제: 칸 값` 으로 남기고 판정하지 않는다.
- `2` `error` / `unavailable` — 목록·작업본을 못 읽었거나, 브라우저에 붙지 못했거나, 30초 안에 페이지가 준비되지 않았다(UI5 로딩 대기 시간 초과, 로그인 화면일 수 있음). 첫 로드가 느리면 화면을 한 번 다시 열어 기다리고, 그래도 안 되면 `--timeout` 을 늘리라고 알린다. 브라우저 응답이 멈추면 창이 가려졌거나 최소화됐는지 사유에 붙인다.
  **검사 불능이다.** 통과도 위반도 아니라고 말하고 사유(`problems`, `screens[].사유`)를 그대로 보인다.
- 준비 단계의 `입력`·`선택`·`누르기` 대상을 못 찾거나 여럿이면 그 화면은 `검사 불능` 으로 건너뛴다(다른 화면은 계속 찍는다). 입력 칸의 지금 값을 읽지 못하거나 `선택` 의 값과 같은 항목이 없어도 `검사 불능` 이다(사유에 보이는 항목 목록).
- 준비 단계 뒤(또는 찍기 직전)에 오류·경고 창(대화상자)이 떠 있으면 그 화면은 찍지 않고 `검사 불능` 이다(사유에 창의 글이 나온다). 완료로 찍지 않는다.
  예외는 `팝업` 단계다 — 그 버튼을 눌러 대화상자가 **정확히 하나** 떠야 하고(안 뜨거나 둘 이상이거나 오류·경고 창이면 `검사 불능`), 찍기 직전에도 그 하나만 허용한다.
  `행` 이 있으면 버튼 대신 표 칸을 더블클릭한다(비어 있는 칸이라 팝업이 안 뜨면 사유에 다른 `행` 을 고르라고 안내한다). **더블클릭은 데이터를 바꾸지 않는 칸에만 쓴다** — 어느 칸인지는 사람이 고른다.
- 찾을 이름이 시간 안에 하나도 그려지지 않으면(앱이 덜 그려진 빈 화면) 못 찾음이 아니라 `검사 불능` 이다. 도구는 이름이 나타나고 화면이 멈출 때까지 기다린 뒤 찍는다.

**목록을 쓸 때 조심할 것(실제 테넌트 시험, #533).**

- **이미 기본값이 든 입력 칸(토큰)에 같은 값을 또 넣으면 오류가 난다 — 기본값이 있으면 `입력` 단계를 뺀다.** 화면을 먼저 열어 칸에 값이 들어 있는지 보고 정한다.
- 화면에 보이는 버튼 글자는 **로그인 언어 기준**이다(예: `Go` 가 아니라 `실행`). `이름` 은 사용자가 보는 화면의 글자 그대로 적는다.

### 4. 끝나면 닫고 프로필을 지운다

로그인 쿠키가 남지 않게 **캡처가 끝나면 바로** 전용 Chrome 창을 닫고 프로필 폴더를 지운다. 닫기 전에 디버깅 포트(9222)를 쓰는 다른 도구가 없는지 확인한다.

```powershell
Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" | Where-Object { $_.CommandLine -like "*manual-chrome*" } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
Start-Sleep 3
Remove-Item -Recurse -Force -LiteralPath "\\?\$env:TEMP\manual-chrome"
```

닫지 못했거나 폴더가 남았으면(`Test-Path "$env:TEMP\manual-chrome"`) 지웠다고 말하지 않고 남은 것을 알린다.

캡처 PNG 에는 화면에 보이는 업무 데이터(오더 번호·이름 등)가 그대로 찍힌다. 고객에게 내도 되는 데이터인지 올리기 전에 사용자가 확인한다.

### 5. 작업본을 마무리한다

작업본의 `#### 번호 설명` 문장이 목록의 `설명` 과 같다. 다시 캡처해 기존 번호 설명(`미정` 제외)이 목록과 다르면 **목록 값으로 덮어쓰고**, 결과 JSON 의 해당 화면 `replaced_descriptions`
(`before`·`after`)로 알린다 — 이 값을 사용자에게 보이고, 작업본에서 다듬은 문장이 있었다면 목록 `설명` 에 옮기라고 안내한다. 작업본은 화면마다 쓰기 직전에 다시 읽어 임시 파일로 쓴 뒤 바꾼다(캡처 중 사람이 고친 부분은 남는다).
이어서 아래 "6. 설명 보충" 으로 간다.

### 6. 설명 보충

캡처로 그림은 새로 찍혔지만 `기능 설명` 은 그대로고 번호 설명은 목록 문장일 뿐이다. 화면이 개발 중에 바뀌었거나 설명에 없던 항목이 생겼어도 도구는 알려 주지 않는다.
그림과 설명을 맞대 보는 이 단계는 매뉴얼을 먼저 쓴 경우든 Spec 으로 쓴 경우든 똑같이 한다.

- **언제.** 캡처가 `ok`(종료코드 0)로 끝나 작업본이 바뀐 화면마다 한다. `incomplete`·검사 불능 화면은 작업본을 고치지 않았으므로 하지 않는다(그 화면은 위 사유 처리가 먼저다).
- **맞대 본다.** 새 그림(`docs/manual/img/<LoB>/<화면 이름>_v<판>.png`)을 Read 로 열어 보고, 그 화면 소절의 `기능 설명`·`#### 번호 설명` 과 캡처 목록의 `표시` 를 맞댄다.
- **찾는 것 세 가지.**
  - (가) 빠짐 — 그림에 보이는 필터·버튼·열인데 번호 설명에 없는 것.
  - (나) 달라짐 — 설명에 적힌 이름·값·순서가 그림과 다른 것(예: 버튼 글자가 바뀜, 설명한 필터가 그림에 없음).
  - (다) 확인 필요 — 그림만으로 맞는지 판단할 수 없는 것(누른 뒤의 동작, 계산 결과, 권한 등).
- **근거.** 그림에 보이는 것과 작업본·Spec 에 이미 적힌 것만 쓴다. 그림에 없는 동작이나 데이터를 지어내지 않는다. 판단할 수 없으면 고친 안을 쓰지 않고 (다) 로 둔다 —
  검사를 못 한 것을 맞음으로 뭉개지 않는다(`CLAUDE.md` 7번).
- **보인다.** 화면별로 표 하나를 사용자에게 보인다. 찾은 게 없으면 화면 이름과 함께 "보충할 곳 없음" 이라고 말한다.

  | 화면 | 종류(빠짐/달라짐/확인 필요) | 지금 문장 | 고친 안 | 그림에서 본 것 |
  |---|---|---|---|---|

- **반영.** **사용자가 고르기 전에는 작업본을 고치지 않는다.** AskUserQuestion(여러 개 고르기)으로 반영할 항목을 고르게 하고, 고른 것만 반영한다. (다) 는 사용자의 답을 받아 그 답대로 쓴다.
- **반영 규칙.**
  - `기능 설명` 은 작업본에서 고치고 지도의 칸 크기에 들어갈 길이를 지킨다(위 "만들기" 4 와 같다).
  - 번호 설명을 고치면 캡처 목록 `표시` 의 그 항목 `설명` 도 같은 문장으로 고친다. 그러지 않으면 다음 캡처가 목록 문장으로 되돌린다(위 5).
  - 빠진 항목을 더하려면 작업본에 번호 설명만 더하지 않는다(그림의 번호와 어긋난다). 캡처 목록 `표시` 에 항목을 더하고 그 화면만 `--screen` 으로 다시 캡처한다(사람의 로그인이 필요하다고 알린다).
- 반영한 변경은 `git diff` 로 사용자에게 보인다.

이어서 "산출" 절의 `--check` → 산출로 간다. 그림 파일은 `docs/manual/img/` 에 새로 생기므로 deliver 때 함께 올린다.

### 매뉴얼 데이터로 시험 목록 만들기

작업본에 적힌 값으로 화면이 맞게 나오는지 시험하고 싶다고 하면 쓴다(#743). 이 절은 **조회 화면(데이터를 바꾸지 않는 동작)** 을 다룬다. 저장·전기·삭제처럼 데이터를 바꾸는 동작은 이 절의 목록에 넣지 않고 아래 "쓰기 시험" 절로 따로 한다.

1. **시험할 곳을 먼저 확인한다.** 시험할 화면과 테넌트·클라이언트를 사용자에게 묻고 확인받는다. **운영 테넌트는 쓰지 않는다**(개발·시험 테넌트만).
2. **뽑는다.** 해당 화면 소절의 `기능 설명`·`#### 번호 설명` 글에서 (가) 넣는 값 → `준비`(`입력`·`선택`·`누르기`), (나) 나와야 할 결과 → `확인`(`열`·`글자`)으로 쓸 후보를 뽑는다.
   글에 적힌 것만 쓴다. 값이나 결과를 지어내지 않는다. 글이 애매하면 **"확인 필요"** 로 두고 목록에 쓰지 않는다.
3. **표로 보인다.** 후보를 화면별 표 하나로 보인다.

   | 화면 | 구분(준비/확인/확인 필요) | 항목 | 근거 문장 |
   |---|---|---|---|

4. **사람이 고른다.** **사용자가 고르기 전에는 `capture.yaml` 을 고치지 않는다.** AskUserQuestion(여러 개 고르기)으로 쓸 항목을 고르게 하고, 고른 것만 목록에 쓴다. "확인 필요" 는 사용자의 답을 받아 그 답대로 쓴다.
5. **작업본은 그대로 둔다.** 이 절은 `capture.yaml` 의 `준비`·`확인` 만 고친다. 작업본 형식과 문장을 바꾸지 않는다.
6. 쓴 뒤 `--check` → 위 "3. 캡처를 돈다" 로 돌리고, 결과 표(화면·확인·결과·정답·실제)를 보인다. `다름` 은 화면이 틀린 건지 작업본이 틀린 건지 사람이 가른다 — 도구는 추측하지 않는다.

### 쓰기 시험(데이터를 바꾸는 흐름)

"취소해 봐", "전기해 봐" 처럼 화면에서 데이터를 바꾸는 흐름까지 시험하고 싶다고 하면 쓴다(#744). 해당 화면에 `바꿈: true` 를 적고 `행 고르기`·`누르기`·`창 누르기` 로 흐름을 쓴다.
**`--allow-write` 는 사용자가 아래 1을 답하고 3에서 허락하기 전에는 쓰지 않는다.** 훅이나 도구가 막으면 우회하지 말고 멈춰 알린다.

1. **먼저 사용자에게 묻는다.** (가) 어느 테넌트·클라이언트에서 돌릴지 — **운영 테넌트는 쓰지 않는다**(개발·시험 테넌트만). (나) 시험 흐름(어느 화면에서 어느 행을 골라 어느 버튼을 누르는지). (다) 시험으로 생긴 문서·전표를
   어떻게 할지(그대로 둠 / 취소·역전기). 답을 받기 전에는 목록을 쓰지도 돌리지도 않는다.
2. **연습으로 먼저 돈다(`--allow-write` 없이).** 도구가 행 고르기와 창 찾기까지만 돌아 첫 `창 누르기` 앞에서 멈추고 대화상자를 닫는다(`멈춤`). 그림에 확인 창이 찍혀 있고 `행 고르기`·`창 누르기` 대상이 찾아졌는지
   사용자에게 보인다. 못 찾으면(`검사 불능`) 사유대로 목록(열 이름·`행`·버튼 글자)을 고쳐 다시 연습한다. 연습은 데이터를 바꾸지 않는다(행 선택·확인 창 열기만 한다).
3. **사용자가 허락하면 `--allow-write` 로 한 건만 돈다.** 허락은 그 한 번이다 — 다시 돌릴 때마다 다시 묻는다. 화면 하나만 `--screen` 으로 돈다.
4. **결과를 표로 보인다.** 화면·`알림`(모인 MessageToast 글)·`확인` 결과·기록한 값(`{열, 행}` 의 `실제` — 생긴 문서 번호 등)·`데이터 바뀜` 을 보이고, 생긴 문서 번호(기록 값)를 사용자에게 남긴다(1의 (다) 대로 처리하도록 알린다.
   취소·역전기는 이 스킬이 하지 않는다).

   | 화면 | 알림 | 확인 | 결과 | 기록한 값 | 데이터 바뀜 |
   |---|---|---|---|---|---|

   `데이터 바뀜: true` 인 화면이 `검사 불능` 이면 데이터가 바뀌었을 수 있다 — 통과나 실패로 말하지 말고 사람이 그 테넌트에서 상태를 확인하게 한다.

실제 화면에서 확인되지 않은 것: 행 선택 칸(`.sapUiTableRowSelectionCell` 등), MessageBox 버튼의 한국어 글자(`OK`·`Cancel` 인지 `확인`·`취소` 인지 — `창 누르기` 에 화면의 글자 그대로 적는다), 토스트의 클래스(`.sapMMessageToast`).
다르면 `검사 불능` 사유로 나오니 그대로 보이고 고친다.

## 산출

작업본이 다 채워지고 사용자가 pptx 를 원하면("매뉴얼 pptx 로 뽑아줘") 먼저 `--check` 로 확인한 뒤 산출한다. `--check` 는 파일을
쓰지 않는다.

```bash
e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "산출 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
uvx --from "$e" \
  python -P -m checker.export --spec "docs/manual/<LoB>/<번호>.<업무 제목>.md" --root "$(git rev-parse --show-toplevel)" --check
```

`--check` 가 거부 없이 끝나면 `--check` 를 빼고 같은 명령을 다시 돈다. 엔진 판·`uvx`·PowerShell 호출 방법·stdout JSON 한 줄·`산출 불능`
처리는 `<이 스킬의 base directory>/../spec/SKILL.md` "양식 파일 산출" 과 같다(`@main` 이나 다른 판으로 대신 받지 않는다). 양식이 여럿이면
`--form <양식 이름>` 을 더한다. 산출 pptx 는 `산출.폴더`(예: `docs/manual/<LoB>/`)에 `산출.파일명` 으로 생긴다. `git fetch origin` 이나
`/harness:sync` 로 `origin/main` 을 최신으로 맞춘 뒤 산출한다 — 이미 있는 판이 main 에 있는지 엔진이 거기서 본다.

종료코드:

- `0` — 이 양식 산출에서는 나오지 않는다(항상 아래 3 이다). 나오면 `files` 를 알린다.
- `3` `status: warning` — 파일은 만들었다. `warnings` 가 **`layout-unchecked` 뿐**이면 산출은 됐고, 글 넘침·겹침·그림 위치를 화면 없이 확인하지
  못했다는 뜻이다(검사 불능, 통과 아님). 파일 경로와 함께 그렇게 알리고 **PowerPoint 로 열어 쪽마다 사람이 확인하라고 한다**(번호 설명이
  그림과 겹치지 않는지, 기능 설명 글이 상자를 넘지 않는지, 그림이 비어 보이지 않는지). 이 확인은 사람 몫이고 이 스킬은 통과라고 하지 않는다.
  `format-merged`(서식이 다른 글을 하나로 합침)·`animation-removed`·`pages-split`(번호 설명 때문에 쪽을 나눔)·`slide-dropped` 경고도 항목대로
  그대로 보여 준다.
- `1` `status: rejected` — 파일을 만들지 않았다. `problems` 의 쪽·항목·사유를 그대로 보이고 작업본을 고친 뒤 다시 돈다. 캡처 없는 화면은
  위 "캡처 없는 화면" 대로 목록으로 알린다. 같은 이름 파일이 main 에 있어 거부된 것이면 아래 "버전 올리기".
- `2` `status: error` — 작업본·지도·양식 pptx 를 읽지 못했거나 작업본이 지도에 없는 쪽·항목을 가리킨다. 산출하지 못했다고 알리고 원인을
  보여 준다.
- stdout 이 JSON 으로 읽히지 않으면(uvx 실패, 엔진 못 받음) "산출 불능" 이다. 거부로도 통과로도 취급하지 않는다.

**양식 예시 글자가 산출물에 남는지.** 지도의 `유지` 가 있는 쪽(반복 본문 쪽)은 지도가 안 가리킨 도형을 모두 지워 예시 글자가 남지 않는다.
`유지` 가 없는 쪽(표지·목차·끝)은 지도의 `칸`·`지우기`·`목록` 이 가리킨 도형만 바뀌고 나머지 글은 그대로 남는다 — 양식에 예시 글(날짜, "예시:"
안내 문구 등)이 있으면 지도에서 `칸` 이나 `지우기` 에 넣어야 한다. 산출 뒤 PowerPoint 확인 때 예시 글자가 남았는지 같이 본다.

**파일명 패턴이 강제하지 않는 것.** `manual-output.yaml` 의 패턴(`^.+_v\d+\.\d+\.pptx$`)은 지도의 `산출.파일명` 모양을 읽어 만든 것이 아니라 느슨한 사본이다.
그래서 "첫 판은 0.1", "버전은 0.1 씩 올림", 파일명 속 제목이 표지 `제목` 과 같은지는 어느 검사도 강제하지 않는다. 사람이 챙기고, 양식이 바뀌어 파일명 모양이 바뀌면 패턴도 직접 고친다.

**검사는 이 스킬이 하지 않는다.** 산출한 pptx 의 파일 이름은 PR 을 열 때 Actions(doc-guard)가 `rules/manual-output.yaml` 로 맡는다. 산출 성공은
doc-guard 통과가 아니다.

## 고치기와 버전 올리기

- **내용을 고친다.** 같은 작업본(`docs/manual/<LoB>/<번호>.<업무 제목>.md`)의 해당 화면만 고친다. 묶는 DEV 가 늘면 `## 묶은 개발 건` 에 줄을 더하고
  그 DEV 의 Spec 을 읽어 화면을 더한다. Spec 이 바뀌어 고칠 때는 바뀐 설계에 해당하는 화면만 고친다.
- **버전 올리기.** main 에 이미 있는 판의 pptx 는 덮어쓰지도 지우지도 않는다(거부 사유 "main 에 이미 있는 판이다"). 내용이 바뀌어 새 판을
  내려면 작업본 머리의 `버전:` 을 0.1 올리고(큰 변경이면 사용자에게 묻는다) 다시 산출한다. 파일 이름의 `v<버전>` 이 달라지므로 새 파일이
  생기고 **이전 판 pptx 는 그대로 남는다**. 이 브랜치에서 만든(origin/main 에 아직 없는) 판은 버전을 올리지 않아도 같은 버전으로 다시 산출된다.
- 판을 올릴 때 그림 파일 이름 끝의 `_v<판>` 도 새 판으로 바꾸고 캡처를 다시 찍었는지 사용자에게 확인한다(위 "그림" — 산출이 검사하지 않는다).
- 작업본 md 는 하나이고 판마다 따로 두지 않는다. 판의 기록은 git 이력과 남아 있는 이전 판 pptx 다.

## 올린 pptx 읽어 들이기

매뉴얼을 개발 전에 먼저 쓰는 사람은 Project Repository `templates/` 의 고객 양식 pptx 에 **실제 데이터로 직접 써서** 올린다. Claude 가 대신 쓰지 않는다 —
이 스킬은 올린 파일을 작업본(md)과 그림으로 옮기기만 한다. 사용자가 "내가 쓴 매뉴얼 pptx 읽어 들여줘" 라고 하면 쓴다.

- **파일 이름.** 지도 `산출.파일명` 규칙 그대로다(예: `사용자매뉴얼_<LoB>_<번호>.<업무 제목>_v0.1.pptx`). 첫 판은 `v0.1` 이다. 엔진이 이 이름을 거꾸로 읽어
  LoB·업무 제목·판을 얻으므로 규칙과 다르면 읽지 못한다(종료코드 2). 올린 파일은 저장소 안 어디에 있어도 된다.
- **엔진을 부르기 전에 묶을 DEV 를 묻는다.** 이 매뉴얼이 다루는 개발 건(DEV) 번호를 사용자에게 먼저 묻고 `--dev DEV-012,DEV-013` 으로 넘긴다(번호는 `DEV-` 뒤 숫자 3자리 이상,
  아니면 종료코드 2). 모르면 `--dev` 를 빼고 부른 뒤 나중에 채운다.
- **엔진 호출.** 판 정하기·`uvx`·PowerShell 호출은 위 "캡처" 3 과 같다(`engine_spec.py`). 먼저 `--check`, 거부 없이 끝나면 `--check` 를 빼고 돈다.

  ```bash
  e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "읽기 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
  uvx --from "$e" \
    python -P -m checker.import_pptx --pptx "<올린 pptx 경로>" --root "$(git rev-parse --show-toplevel)" [--form "<양식 이름>"] [--dev "<DEV-번호,…>"] --check
  ```

  pptx 지도가 여럿이면 `--form` 이 필요하다. 쓰기 전에 0단계(브랜치 확인)를 한다 — 작업 설명은 "매뉴얼 — `<LoB>` `<업무 제목>`" 이다. stdout 은 JSON 한 줄이다.
- **읽는 방식.** 지도의 `찾기` 는 견본의 예시 글자라 올린 파일에서는 쓰지 못한다. 대신 견본 쪽에서 칸 도형의 위치를 얻어 올린 쪽의 같은 위치(허용 오차 안)
  도형 글을 읽는다. 번호 설명은 번호 도형마다 오른쪽 같은 높이의 가까운 글상자와 짝짓고, `쪽당_최대` 로 넘어간 쪽은 화면 제목이 같으면 한 화면으로 합친다.
  쪽 번호 필드는 뺀다. 표는 읽지 않는다.
- **종료코드.**
  - `0` `ok` — 모든 칸을 읽었고 옮기지 못한 글이 없다. 작업본(`docs/manual/<LoB>/<번호>.<업무 제목>.md`)과 그림(`docs/manual/img/<LoB>/<화면 제목>_v<판>.<확장자>`)을 썼다.
    `--check` 면 쓰지 않고 `planned` 만 보인다. 그림이 PNG 가 아니면 `warnings` 의 `image-not-png` 로 알린다(산출은 받는다). 이미지로 읽히지 않는 그림은 파일을 쓰지 않고
    `#### 그림` 을 `미정` 으로 두며 `missing` 에 올린다. **종료코드 0 은 문서 검사 통과가 아니다** — `doc_guard.status` 가 `pass` 가 아니면(`violation`·`unavailable`·`out_of_scope`) 통과가 아니고, 엔진의 `next` 도 그렇게 적는다.
    작업본 파일 이름 자리는 지도에서 정한다(`산출.작업본_자리`, 생략하면 폴더·메타가 아닌 파일명 자리가 하나일 때 — `spec/form-map.md`). 그림 폴더는 캡처 도구와 같다(`docs/manual/img/<작업본 폴더 이름>/`).
  - `1` `incomplete` — 작업본은 썼다. `missing`(못 찾은 칸 — 작업본에 `미정`)과 `unmapped`(옮기지 못한 글 — 쪽 번호·도형 글)를 **그대로 사용자에게 보인다.**
    옮기지 못한 글은 버리지 않는다 — 각 글이 어느 칸·번호 설명에 들어가야 하는지, 아니면 매뉴얼에 넣지 않는지 사용자에게 묻고 정한 대로 작업본을 고친다.
    못 찾은 칸은 올린 파일을 확인하거나 사용자에게 값을 묻는다. 추측으로 채우지 않는다.
  - `2` `error` — 지도·양식·올린 pptx 를 못 읽었거나, 쪽을 견본에 분류하지 못했거나(쪽 크기가 다른 파일 포함), 파일 이름에서 값을 못 읽었거나, 같은 작업본·그림이 이미
    있다(덮어쓰지 않는다), 파일 이름의 자리 값이 여러 방식으로 나뉘거나 폴더 이름으로 못 쓰는 값(`..`·`CON` 등)이다. 아무것도 쓰지 않았다. 검사 불능이니 통과도 위반도 아니라고 말하고 `problems` 를 그대로 보인다. stdout 이 JSON 이 아니면 "읽기 불능" 이다.
- **`## 묶은 개발 건`.** pptx 에 정보가 없다. `--dev` 를 줬으면 DEV 칸이 그 번호로 채워지고(제목 칸은 규칙이 검사하지 않아 비워 둔다 — 아는 제목은 사용자에게 받아 채운다),
  안 줬으면 `미정` 이라 문서 검사(`doc_guard`)가 위반으로 본다 — 사용자에게 DEV 를 물어 `| DEV-xxx | 제목 |` 으로 채운다(위 "작업본 형식").
  `doc_guard.status` 가 `unavailable` 이면 검사를 못 한 것이다.
- **올린 pptx 는 그대로 두고 첫 판으로 남긴다.** 개발 뒤 위 "캡처"(와 6. 설명 보충)를 반영한 산출은 작업본 `버전:` 을 `0.2` 로 올려 새 파일로 낸다(아래 "고치기와 버전 올리기").
  그림 파일 이름의 판도 새 판으로 바뀐다.
- **넣은 값·기대 결과** 시험 목록은 위 "매뉴얼 데이터로 시험 목록 만들기" 에서 다룬다.

## 기존 md 매뉴얼을 새 형식으로 옮기기

예전 매뉴얼은 `docs/manual/DEV-012-생산계획보드-사용자매뉴얼.md` 처럼 개발 건별로 손으로 쓴 글이다. 옮길 때는 **글을 새로 쓰지 않고** 옛 글에서
화면 단위로 잘라 담는다.

1. 옛 md 를 읽고 LoB·업무 제목을 정한다(같은 LoB 의 다른 옛 매뉴얼이 같은 업무면 한 작업본으로 묶을지 사용자에게 묻는다). 묶는 DEV 는 옛 글의
   `개발 번호` 줄이나 파일명에서 찾는다.
2. 옛 글에서 "(화면: …)" 처럼 캡처 자리가 표시된 곳이나 화면 이름이 붙은 절을 화면 후보로 뽑는다. 화면마다 `본문` 소절 하나로 하고, 그 화면에 대한
   옛 설명 문단을 `기능 설명`(짧게)과 `번호 설명`(항목별)으로 나눠 옮긴다. 의미를 바꾸거나 새 사실을 더하지 않는다.
3. 옛 글에서 시험하지 못했다고 적힌 문구는 지우지 않고 그 화면에 그대로 옮긴다(예: 번호 설명 항목에 "(화면에서 아직 시험하지 못했다)").
4. **화면 소절로 옮길 자리가 없는 글**(자주 묻는 질문, 문의처, 반영 규칙 표 등 화면에 묶이지 않는 설명)은 양식 쪽에 담을 곳이 없다. 버리지 말고 목록으로
   사용자에게 알리고, 옛 md 를 지울지·남길지는 사용자가 정한다. 옛 파일은 이 스킬이 지우지 않는다.
5. 옛 글에 화면 캡처가 없었으면 그림 경로는 비어 있다. "캡처 없는 화면" 대로 목록으로 알리고, 캡처가 생길 때까지 산출하지 않는다.
6. 옮긴 작업본으로 `--check` → 산출까지 돌려 본다. 옛 md 는 같은 PR 에서 지울지 사용자에게 묻는다.

## 규칙 설치

Project Repository 에 매뉴얼 검사 규칙이 없으면 이 스킬 폴더의 세 파일을 복사한다(이 PR 은 `rules/`·`templates/` 를 바꾸므로 승인자 Approve 가
필요하다고 알린다. 엔진은 `rules/` 만 읽는다).

| 이 스킬 폴더 | Project Repository |
|---|---|
| `manual.yaml` | `rules/manual.yaml` (작업본: 파일명·필수 절·묶은 개발 건 표·양식 밖 항목) |
| `manual-output.yaml` | `rules/manual-output.yaml` (산출 pptx 파일명 패턴. 지도의 `검사_규칙` 이 이 파일을 가리킨다) |
| `manual-template.md` | `templates/harness/manual.md` (필수 절의 기준) |

양식을 바꿔 파일명 모양(`산출.파일명`)이 달라지면 `manual-output.yaml` 의 패턴도 같이 고친다. 작업본의 관할은 `docs/manual/**/*.md` 라서
`docs/manual/` 바로 아래에 있는 예전 md 매뉴얼은 이 규칙에 걸리지 않는다(옮긴 뒤에는 `<LoB>` 폴더 안에만 둔다).
