# /harness:manual

`docs/manual/<LoB>/` 의 사용자 매뉴얼 작업본(md)을 쓰고, 고객 양식 pptx 로 산출하는 입구다. 매뉴얼은 LoB(업무 영역)
폴더 아래 **업무 제목별로 파일 하나**이고, 한 파일에 어떤 개발 건(DEV)을 묶었는지 작업본에 적는다. 양식은 Project
Repository 의 `templates/` 에 있고 양식 지도는 `templates/forms/*.yaml` 이다. 양식은 바뀔 수 있으므로 이 스킬과 엔진에는
양식 고유 글자를 적지 않는다 — 쪽·항목 이름은 항상 지도에서 읽는다. `<이 스킬의 base directory>` 는 이 스킬이 로드될 때
위에 표시되는 경로다.

화면 위의 빨간 네모·번호는 캡처 도구(#533)가 그림에 직접 그린다. 이 스킬은 **그림 경로만** 받는다. 캡처를 찍거나 그림을
고치지 않는다.

`git rev-parse --show-toplevel` 로 Project Repository 루트를 확인한다.

## 작업본 형식

위치와 이름: `docs/manual/<LoB>/<번호>.<업무 제목>.md` (예: `docs/manual/Production/1.생산계획 보드.md`). `<LoB>` 폴더
이름은 작업본 표지의 `LoB` 값과 **대소문자까지 같아야 한다** — 지도 `산출.폴더` 의 `{LoB}` 자리를 채운 폴더가 작업본이 있는 폴더와
다르면 산출이 거부한다(`산출.폴더` 항목). 자리 값에 제어 문자, `/ \ : * ? " < > |`, 점만 있는 값, 끝의 점·공백, Windows 예약어(CON·PRN·AUX·NUL·COM1-9·LPT1-9,
확장자가 붙어도)가 있으면 역시 거부한다. 번호는 그 LoB 안의 순번이고 표지 `제목` 값이 `<번호>.<업무 제목>` 이다(파일명
앞부분과 같게). 파일명 규칙(`^\d+\..+\.md$`)은 `rules/manual.yaml` 이 강제한다.

```markdown
# 1.생산계획 보드

버전: 0.1

## 묶은 개발 건

| DEV | 제목 |
|---|---|
| DEV-012 | 생산계획 보드 |

## 양식 항목

### <양식> · 표지

| 항목 | 값 |
|---|---|
| LoB | Production |
| 제목 | 1.생산계획 보드 |
| 작성일 | 2026-11-01 |

### <양식> · 목차

해당 없음

### <양식> · 본문 · <화면 이름>

| 항목 | 값 |
|---|---|
| 업무명 | 생산계획 보드 |
| 화면 제목 | 조회 조건 |
| 기능 설명 | 이 화면이 하는 일 한두 문장 |

#### 그림

docs/manual/img/Production/조회조건_v0.1.png

#### 번호 설명

1. 번호 1 이 가리키는 곳의 설명
2. 번호 2 가 가리키는 곳의 설명

### <양식> · 끝

해당 없음
```

- **머리.** 첫 `##` 앞의 `버전: 0.1` 줄이 산출 파일명의 버전(`v0.1`)이 된다. 처음은 0.1, 올릴 때 0.1 씩이다. 줄이 없거나
  `x.y` 모양이 아니면 산출이 파일명을 만들지 못해 거부한다.
- **`## 묶은 개발 건`.** 이 파일이 다루는 DEV 를 한 줄씩(`| DEV | 제목 |`). DEV 칸은 `DEV-012` 꼴이고 절이 없거나 형식이 틀리면
  `rules/manual.yaml` 이 거절한다. 같은 DEV 를 두 매뉴얼 파일이 묶어도 되지만 제목이 겹치지 않게 업무 제목으로 나눈다.
- **`## 양식 항목`.** `### <양식> · <쪽 이름>` 이 표지·목차·끝이고, 반복 쪽은 `### <양식> · <쪽 이름> · <화면 이름>` 소절이
  화면마다 하나씩이다(위 예의 쪽 이름 표지·목차·본문·끝과 `LoB`·`제목` 같은 항목 이름은 **지도에서 읽은 것**이고, 양식이 바뀌면
  지도의 이름을 따른다). 소절 표기·`#### 그림`·`#### 번호 설명` 문법의 정본은 `<이 스킬의 base directory>/../spec/form-map.md`
  "pptx 지도" 절이다. 지도에 없는 쪽·항목·`####` 소제목(오타 포함)은 쓰지 않는다 — 저장할 때(훅)와 PR(doc-guard `form_columns`)이
  "양식 밖 항목" 으로 거절하고 산출도 멈춘다.
- **그림.** `#### 그림` 아래 **저장소 루트 기준** PNG 경로 한 줄(`![](경로)` 도 된다). 이미지는 `docs/manual/img/<LoB>/` 에 두고
  파일 이름 끝(확장자 앞)에 이번에 산출할 판을 붙이기를 권한다(`조회조건_v0.1.png`) — Spec 화면 캡처(#348)의 규칙을 따른 관례다.
  **pptx 산출은 이 이름 규칙을 검사하지 않는다**(Spec 캡처의 "캡처가 옛 판" 검사는 xlsx 산출에만 있다). 판을 올릴 때는 캡처를 다시
  찍어 새 이름으로 바꾸는지 사람이 챙긴다.
- **번호 설명.** `1. 글` 목록이고 번호는 그림에 캡처 도구가 그린 번호와 같다. 이어지는 줄은 들여 쓴다. 한 쪽에 다 안 들어가면 산출이
  같은 화면을 다음 쪽으로 넘긴다(`pages-split` 경고).
- 값을 모르면 추측하지 않고 사용자에게 묻는다. 비었거나 `미정` 인 값은 산출이 거부하므로, 그래도 모르면 `미정` 으로 남기고 산출이
  거부된다고 알리거나(그림은 아래 "캡처 없는 화면") 그 화면을 넣지 않고 "못 쓴 것" 으로 적는다.

## 0단계: 브랜치 확인

작업본을 쓰기 전에, 지금 브랜치가 이번 매뉴얼 작업에 맞는지 확인한다. 확인은 `<이 스킬의 base directory>/../start/SKILL.md` 의
"다른 스킬이 부르는 브랜치 확인" 을 그대로 따른다 — 미커밋 변경, main 이면 start 절차, 다른 작업 브랜치면 같은 일인지 판단·질문,
판정 불능이 거기 있다. start 를 따로 부르라고 하지 않는다. 이 스킬에서 정하는 것은 아래뿐이다.

- **이번 작업 설명**은 "매뉴얼 — `<LoB>` `<업무 제목>`" 한 줄이다. LoB·업무 제목·묶을 DEV 를 받은 뒤에 브랜치를 비교한다(그 전에는
  읽기만 하고 파일을 쓰지 않는다).
- **같은 일의 판단 기준.** 브랜치 이슈 제목이 같은 업무 제목의 매뉴얼 작업이거나, 이슈의 DEV 가 묶을 DEV 중 하나와 같고 사용자가
  매뉴얼을 이 브랜치에서 쓰겠다고 하면 같은 일이다. 아니면 묻는다.
- **main 이면 번호 없는 작업 이슈를 만든다.** start 절차를 `docs` 작업으로 수행한다 — 제목은 `매뉴얼 — <LoB> <업무 제목>`, 브랜치는
  `docs/{이슈번호}-…`. 묶는 DEV 의 대표 `[DEV-xxx]` 이슈를 브랜치 이슈로 쓰지 않는다(개발 PR 이 병합될 때 닫혀야 하는 이슈라서다).

## 만들기

1. **LoB·업무 제목·묶을 DEV 를 묻는다.** 모르는 값은 추측하지 않는다. LoB 폴더가 이미 있으면(`docs/manual/*/`) 목록을 보여 주고
   고르게 하며, 같은 LoB 의 기존 파일(`<번호>.*.md`)로 다음 번호를 정한다. 같은 업무 제목의 작업본이 이미 있으면 새로 만들지 않고
   아래 "고치기" 로 간다. 파일명(`<번호>.<업무 제목>.md`)에는 파일 이름에 못 쓰는 문자(`\ / : * ? " < > |`)를 쓰지 않는다.
2. **자료를 읽는다.** 묶을 DEV 마다 `docs/spec/DEV-<번호>-*.md` 의 `## 상세 설계`, `## Launchpad 노출`(메뉴 경로·타일 이름), `## 권한`
   (누가 쓸 수 있는지)을 읽는다. 기존 `docs/manual/*.md` 매뉴얼이 있으면 같이 읽는다. Spec 에 없는 동작·화면은 지어내지 않는다 —
   Spec 이 `미정` 인 곳과 Spec 에 없어 모르는 곳은 사용자에게 묻고, 그래도 없으면 그 화면을 넣지 않고 마무리 안내의 "못 쓴 것" 에
   적는다. 시험하지 못한 동작은 Spec·`audit/changes/` 에 확인했다고 적힌 만큼만 쓴다.
3. **양식 지도를 찾는다.** `templates/forms/*.yaml` 중 `템플릿` 이 `.pptx` 인 지도(`쪽` 목록이 있다)를 모두 읽는다.
   - 지도 폴더가 없거나 pptx 지도가 하나도 없으면 **멈추고** 지도가 없다고 알린다. 안내만 한다: 양식 pptx 를 `templates/` 에 넣고
     `python -m checker.export_pptx --dump <양식.pptx>`(엔진 호출은 아래 "산출" 과 같은 `uvx`)로 쪽마다 도형의 글자·위치와 `찾기` 가
     유일한지 본 뒤 `form-map.md` "pptx 지도" 대로 지도를 쓴다. 지도를 이 스킬이 대신 추측해 만들지 않는다.
   - 읽지 못한 지도(파싱 오류, `쪽` 없음)가 있으면 목록에서 조용히 빼지 않고 어느 파일이 왜 안 읽히는지 알리고 멈춘다.
   - pptx 지도가 여럿이면 `양식`·`설명` 을 보여 주고 고르게 한다. 하나면 그것으로 한다.
   - 지도의 `검사_규칙` 이 가리키는 파일(`rules/manual-output.yaml`)이 없거나, `rules/manual.yaml`·`templates/harness/manual.md` 가
     없으면 아래 "규칙 설치" 로 안내한다. 산출 폴더·파일명 모양은 지도의 `산출` 이 정한다(`산출.폴더` 에 `{LoB}` 같은 자리를 쓸 수
     있다 — 파일명과 같은 자리 규칙).
4. **작업본 초안을 쓴다.** 지도의 쪽 이름·항목 이름을 그대로 써서 `docs/manual/<LoB>/<번호>.<업무 제목>.md` 를 위 형식으로 쓴다.
   - 화면은 사용자가 쓰는 순서(메뉴 진입 → 조회 → 처리 → 결과 확인)로 한 화면씩 `본문` 소절로 나눈다. 한 화면의 `번호 설명` 은 그림에
     번호를 그릴 곳마다 한 항목이다.
   - `기능 설명` 은 그 화면이 무엇을 하는지 한두 문장으로, 지도의 칸 크기에 들어갈 길이로 쓴다. 긴 내용은 번호 설명으로 나눈다.
   - 이미 캡처가 있으면 그 경로를, 없으면 아래 "캡처 없는 화면" 대로 한다. 경로를 지어내지 않는다.
   - 표지의 `작성일` 같은 날짜 항목은 오늘 날짜로 채운다. 이름·담당자처럼 모르는 값은 묻는다.
5. 저장 전에 doc-guard 훅(`pre_write_guard.py`)이 `rules/manual.yaml` 로 파일 이름·필수 절·`묶은 개발 건` 표·양식 밖 항목을 검사한다.
   막히면 사유대로 고친다. 훅이 죽어 검사를 못 한 경우는 통과나 위반이 아니라 검사를 못 했다고 알린다. 훅이 막으면 우회하지 않고
   사유를 알린다.

## 캡처 없는 화면

그림 파일이 없는 화면을 빈칸이나 임시 그림으로 통과시키지 않는다(`CLAUDE.md` 7번 — 검사를 못 한 것을 통과로 뭉개지 않는다).

- 작업본은 쓸 수 있다. 그림 경로를 아직 모르는 화면은 `#### 그림` 에 **예정 경로**(`docs/manual/img/<LoB>/<화면>_v<판>.png`)를 적어 두거나
  `미정` 으로 둔다. 어느 쪽이든 파일이 없으면 산출이 거부한다.
- 산출 전에 `--check` 를 돌린다. 캡처가 없는 화면마다 `problems` 에 화면 이름(`본문 · <화면 이름>`)과 `그림` 항목이 한 줄씩 나온다.
  그 목록을 **그대로 사용자에게 보이고** "이 N 개 화면의 캡처가 없어 산출하지 못했다. 캡처 도구(#533)로 찍어 경로를 알려 달라" 고 알린다.
- 일부 화면만 빼고 산출하자는 제안은 사용자가 먼저 말하지 않으면 하지 않는다. 사용자가 그렇게 정하면 그 화면 소절을 작업본에서 빼고
  마무리 안내의 "못 쓴 것" 에 빠진 화면 이름을 적는다.

## 산출

작업본이 다 채워지고 사용자가 pptx 를 원하면("매뉴얼 pptx 로 뽑아줘") 먼저 `--check` 로 확인한 뒤 산출한다. `--check` 는 파일을
쓰지 않는다.

```bash
e="$(uv run --no-project python "${CLAUDE_PLUGIN_ROOT}/hooks/engine_spec.py")" && [ -n "$e" ] || { echo "산출 불능: 엔진 판을 정하지 못했다" >&2; exit 1; }
uvx --from "$e" \
  python -P -m checker.export --spec "docs/manual/<LoB>/<번호>.<업무 제목>.md" --root "$(git rev-parse --show-toplevel)" --check
```

`--check` 가 거부 없이 끝나면 `--check` 를 빼고 같은 명령을 다시 돈다. 엔진 판·`uvx`·PowerShell 호출 방법·stdout JSON 한 줄·`산출 불능`
처리는 `<이 스킬의 base directory>/../spec/SKILL.md` "양식 파일 산출" 과 같다(`@main` 이나 다른 판으로 대신 받지 않는다). 양식이 여럿이면
`--form <양식 이름>` 을 더한다. 산출 pptx 는 `산출.폴더`(예: `docs/manual/<LoB>/`)에 `산출.파일명` 으로 생긴다. `git fetch origin` 이나
`/harness:sync` 로 `origin/main` 을 최신으로 맞춘 뒤 산출한다 — 이미 있는 판이 main 에 있는지 엔진이 거기서 본다.

종료코드:

- `0` — 이 양식 산출에서는 나오지 않는다(항상 아래 3 이다). 나오면 `files` 를 알린다.
- `3` `status: warning` — 파일은 만들었다. `warnings` 가 **`layout-unchecked` 뿐**이면 산출은 됐고, 글 넘침·겹침·그림 위치를 화면 없이 확인하지
  못했다는 뜻이다(검사 불능, 통과 아님). 파일 경로와 함께 그렇게 알리고 **PowerPoint 로 열어 쪽마다 사람이 확인하라고 한다**(번호 설명이
  그림과 겹치지 않는지, 기능 설명 글이 상자를 넘지 않는지, 그림이 비어 보이지 않는지). 이 확인은 사람 몫이고 이 스킬은 통과라고 하지 않는다.
  `format-merged`(서식이 다른 글을 하나로 합침)·`animation-removed`·`pages-split`(번호 설명 때문에 쪽을 나눔)·`slide-dropped` 경고도 항목대로
  그대로 보여 준다.
- `1` `status: rejected` — 파일을 만들지 않았다. `problems` 의 쪽·항목·사유를 그대로 보이고 작업본을 고친 뒤 다시 돈다. 캡처 없는 화면은
  위 "캡처 없는 화면" 대로 목록으로 알린다. 같은 이름 파일이 main 에 있어 거부된 것이면 아래 "버전 올리기".
- `2` `status: error` — 작업본·지도·양식 pptx 를 읽지 못했거나 작업본이 지도에 없는 쪽·항목을 가리킨다. 산출하지 못했다고 알리고 원인을
  보여 준다.
- stdout 이 JSON 으로 읽히지 않으면(uvx 실패, 엔진 못 받음) "산출 불능" 이다. 거부로도 통과로도 취급하지 않는다.

**양식 예시 글자가 산출물에 남는지.** 지도의 `유지` 가 있는 쪽(반복 본문 쪽)은 지도가 안 가리킨 도형을 모두 지워 예시 글자가 남지 않는다.
`유지` 가 없는 쪽(표지·목차·끝)은 지도의 `칸`·`지우기`·`목록` 이 가리킨 도형만 바뀌고 나머지 글은 그대로 남는다 — 양식에 예시 글(날짜, "예시:"
안내 문구 등)이 있으면 지도에서 `칸` 이나 `지우기` 에 넣어야 한다. 산출 뒤 PowerPoint 확인 때 예시 글자가 남았는지 같이 본다.

**파일명 패턴이 강제하지 않는 것.** `manual-output.yaml` 의 패턴(`^.+_v\d+\.\d+\.pptx$`)은 지도의 `산출.파일명` 모양을 읽어 만든 것이 아니라 느슨한 사본이다.
그래서 "첫 판은 0.1", "버전은 0.1 씩 올림", 파일명 속 제목이 표지 `제목` 과 같은지는 어느 검사도 강제하지 않는다. 사람이 챙기고, 양식이 바뀌어 파일명 모양이 바뀌면 패턴도 직접 고친다.

**검사는 이 스킬이 하지 않는다.** 산출한 pptx 의 파일 이름은 PR 을 열 때 Actions(doc-guard)가 `rules/manual-output.yaml` 로 맡는다. 산출 성공은
doc-guard 통과가 아니다.

## 고치기와 버전 올리기

- **내용을 고친다.** 같은 작업본(`docs/manual/<LoB>/<번호>.<업무 제목>.md`)의 해당 화면만 고친다. 묶는 DEV 가 늘면 `## 묶은 개발 건` 에 줄을 더하고
  그 DEV 의 Spec 을 읽어 화면을 더한다. Spec 이 바뀌어 고칠 때는 바뀐 설계에 해당하는 화면만 고친다.
- **버전 올리기.** main 에 이미 있는 판의 pptx 는 덮어쓰지도 지우지도 않는다(거부 사유 "main 에 이미 있는 판이다"). 내용이 바뀌어 새 판을
  내려면 작업본 머리의 `버전:` 을 0.1 올리고(큰 변경이면 사용자에게 묻는다) 다시 산출한다. 파일 이름의 `v<버전>` 이 달라지므로 새 파일이
  생기고 **이전 판 pptx 는 그대로 남는다**. 이 브랜치에서 만든(origin/main 에 아직 없는) 판은 버전을 올리지 않아도 같은 버전으로 다시 산출된다.
- 판을 올릴 때 그림 파일 이름 끝의 `_v<판>` 도 새 판으로 바꾸고 캡처를 다시 찍었는지 사용자에게 확인한다(위 "그림" — 산출이 검사하지 않는다).
- 작업본 md 는 하나이고 판마다 따로 두지 않는다. 판의 기록은 git 이력과 남아 있는 이전 판 pptx 다.

## 기존 md 매뉴얼을 새 형식으로 옮기기

예전 매뉴얼은 `docs/manual/DEV-012-생산계획보드-사용자매뉴얼.md` 처럼 개발 건별로 손으로 쓴 글이다. 옮길 때는 **글을 새로 쓰지 않고** 옛 글에서
화면 단위로 잘라 담는다.

1. 옛 md 를 읽고 LoB·업무 제목을 정한다(같은 LoB 의 다른 옛 매뉴얼이 같은 업무면 한 작업본으로 묶을지 사용자에게 묻는다). 묶는 DEV 는 옛 글의
   `개발 번호` 줄이나 파일명에서 찾는다.
2. 옛 글에서 "(화면: …)" 처럼 캡처 자리가 표시된 곳이나 화면 이름이 붙은 절을 화면 후보로 뽑는다. 화면마다 `본문` 소절 하나로 하고, 그 화면에 대한
   옛 설명 문단을 `기능 설명`(짧게)과 `번호 설명`(항목별)으로 나눠 옮긴다. 의미를 바꾸거나 새 사실을 더하지 않는다.
3. 옛 글에서 시험하지 못했다고 적힌 문구는 지우지 않고 그 화면에 그대로 옮긴다(예: 번호 설명 항목에 "(화면에서 아직 시험하지 못했다)").
4. **화면 소절로 옮길 자리가 없는 글**(자주 묻는 질문, 문의처, 반영 규칙 표 등 화면에 묶이지 않는 설명)은 양식 쪽에 담을 곳이 없다. 버리지 말고 목록으로
   사용자에게 알리고, 옛 md 를 지울지·남길지는 사용자가 정한다. 옛 파일은 이 스킬이 지우지 않는다.
5. 옛 글에 화면 캡처가 없었으면 그림 경로는 비어 있다. "캡처 없는 화면" 대로 목록으로 알리고, 캡처가 생길 때까지 산출하지 않는다.
6. 옮긴 작업본으로 `--check` → 산출까지 돌려 본다. 옛 md 는 같은 PR 에서 지울지 사용자에게 묻는다.

## 규칙 설치

Project Repository 에 매뉴얼 검사 규칙이 없으면 이 스킬 폴더의 세 파일을 복사한다(이 PR 은 `rules/`·`templates/` 를 바꾸므로 승인자 Approve 가
필요하다고 알린다. 엔진은 `rules/` 만 읽는다).

| 이 스킬 폴더 | Project Repository |
|---|---|
| `manual.yaml` | `rules/manual.yaml` (작업본: 파일명·필수 절·묶은 개발 건 표·양식 밖 항목) |
| `manual-output.yaml` | `rules/manual-output.yaml` (산출 pptx 파일명 패턴. 지도의 `검사_규칙` 이 이 파일을 가리킨다) |
| `manual-template.md` | `templates/harness/manual.md` (필수 절의 기준) |

양식을 바꿔 파일명 모양(`산출.파일명`)이 달라지면 `manual-output.yaml` 의 패턴도 같이 고친다. 작업본의 관할은 `docs/manual/**/*.md` 라서
`docs/manual/` 바로 아래에 있는 예전 md 매뉴얼은 이 규칙에 걸리지 않는다(옮긴 뒤에는 `<LoB>` 폴더 안에만 둔다).
