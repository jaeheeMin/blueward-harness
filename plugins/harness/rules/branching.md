# 브랜치 규칙

## 이름 형식

```
{타입}/{이슈번호}-{영문요약}
```

- 예시: `feat/12-onboarding-doc`
- 예시: `fix/31-broken-link`
- 예시: `docs/7-rules-index`

허용하는 타입은 다음 여섯 가지다.

| 타입 | 언제 쓰는가 |
|---|---|
| `feat` | 새 기능이나 새 문서를 추가할 때 |
| `fix` | 잘못된 동작이나 잘못된 내용을 고칠 때 |
| `docs` | 문서만 고치고 동작에는 영향이 없을 때 |
| `refactor` | 동작은 그대로 두고 구조만 정리할 때 |
| `chore` | 설정이나 잡무성 변경일 때 |
| `test` | 검사 코드만 추가하거나 고칠 때 |

영문요약 부분은 영문 소문자와 숫자와 붙임표(`-`)만 쓴다. 한글이나 대문자,
밑줄은 쓰지 않는다.

## main 은 PR 로만 갱신된다

main 브랜치에는 직접 커밋할 수 없고, main 으로 직접 푸시할 수도 없다. main 을
바꾸는 유일한 방법은 작업 브랜치를 만들어 PR 을 여는 것이다. 여러 명이 함께
쓰는 저장소에서 main 이 항상 리뷰를 거친 상태로 유지되어야 하기 때문이다.

## 브랜치는 `/harness:start` 로 만든다

브랜치를 만드는 정상 경로는 `/harness:start` 다. 작업 내용을 설명하면 이슈를 만들고
그 이슈 번호로 규칙에 맞는 브랜치를 자동으로 만들어 준다. 이미 이슈 번호가
있다면 그 번호를 알려주면 된다.

`/harness:srs` 와 `/harness:spec` 도 문서를 쓰기 전에 브랜치를 확인한다. main 이면 start 절차를 대신 수행하고, 다른
작업 브랜치에 있으면 브랜치 이름의 이슈가 이번 일과 같은지 보고 다르거나 애매하면 이어 쓸지 새로 시작할지 묻는다.

터미널에서 직접 만들어야 한다면 아래 형식을 따른다.

```
git switch -c feat/12-onboarding-doc
```

## 이름을 잘못 지었을 때

이미 만든 브랜치의 이름이 규칙에 맞지 않으면 새로 만들지 않고 이름만 고친다.

```
git branch -m feat/12-onboarding-doc
```

## 강제하는 것

동작별로 강제하는 훅이 다르다.

- 커밋 거부는 `.githooks/pre-commit` 이 맡는다(있는 저장소에 한한다).
  브랜치가 main 이거나 이름이 형식에 맞지 않으면 커밋 자체가 거부된다.
- main 으로의 직접 푸시 거부는 `.githooks/pre-push` 가 맡는다(있는 저장소에
  한한다).
- Claude Code 세션 안에서 스킬을 거치지 않고 실행하는 `git push` 는 harness
  플러그인의 push 가드 훅(`pre-bash-git-guard.sh`)이 막는다.

git hook(`.githooks/pre-commit`, `.githooks/pre-push`)을 쓰는 저장소라면,
복제한 사람이 `scripts/install-hooks.sh` 를 한 번 실행해야 작동한다. Claude
Code 세션에서는 시작할 때 harness 플러그인의 세션 시작 훅이 이 설치를
자동으로 시도해 주지만, Claude Code 를 쓰지 않고 터미널에서 직접 작업하는
참여자에게는 이 스크립트를 실행하는 것이 훅을 활성화하는 유일한 경로다.
