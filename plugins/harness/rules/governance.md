# 거버넌스 규칙

## 리뷰와 병합

PR 은 작성자 본인이 아닌 사람이 한 번 이상 읽은 뒤에 병합한다. 본인만 읽고
병합하면 실수를 걸러줄 두 번째 시선이 없어진다.

병합 방식은 squash merge 로 통일한다. 작업 브랜치 안의 중간 커밋이 main 의
이력에 그대로 남지 않도록 하기 위해서다.

PR 여러 개가 서로 기다려야 하면 병합 순서를 따른다. 다른 열린 PR 위에 쌓은 PR, 같은 DEV 의
SRS → Spec → 개발 순, 본문 `먼저: #n` 줄이 가리키는 PR, 하네스 저장소에서 plugin.json version 이
낮은 PR 이 먼저다. `/harness:prs` 가 이 순서를 계산해 보여 준다(#370).

Claude 의 `gh pr merge` 는 훅(`pre-bash-git-guard.sh`)이 병합 직전에 이 순서를 다시 확인해, 먼저 병합해야
하는 PR 이 열려 있으면 거부한다. 거부 메시지가 앞 PR 과 이유를 알려 주니 앞 PR 부터 병합하거나, 순서가 틀렸으면
PR 본문의 `먼저:` 줄을 고친다. 순서를 정하지 못할 때(순환, GitHub 못 읽음, 엔진 실행 실패)도 통과시키지 않고
거부한다. 같은 파일을 고친 PR 은 경고만 하고 막지 않는다. 사람이 GitHub 화면에서 병합하는 것은 막을 수 없다
(무료 요금제는 서버에서 강제하지 못한다) — 그래서 사람도 `/harness:prs` 나 PR 본문 `## 병합 순서` 를 보고 순서를 지킨다.

Actions 의 `pr-checks`(승인·취소 뒤에는 `pr-review`, 병합 뒤에는 `main-checks`) 안 pr-queue 단계가 Claude 를 안 쓰는 사람에게도 같은 정보를 준다. 열린 PR 마다 병합 순서 코멘트(`<!-- pr-queue -->`) 하나를
갱신하고, 커밋 status `merge-order` 를 달아 앞 PR 이 열려 있으면 GitHub 화면에서 노란 대기로 보인다(순서를 정하지 못하면 error,
통과로 두지 않는다). 코멘트는 PR·리뷰·main 이벤트 때 갱신되어 검사 결과는 다음 이벤트까지 낡을 수 있으니, 정확한 지금
상태는 `/harness:prs` 로 본다. 본문 `먼저:` 줄을 고치거나 draft 로 바꿔도 코멘트는 바로 갱신되지 않고(`edited`·
`converted_to_draft` 로는 돌지 않는다, #411) 다음 PR·리뷰·main 이벤트까지 낡는다. 무료 요금제라 Merge 버튼은 잠기지 않으니 노란 대기는 막는 것이 아니라 드러내는 것이다. 앞 PR 이 병합돼 내
PR 의 차례가 되면 작성자를 멘션하고(Teams 웹훅이 있으면 Teams 로도) 알린다. `merge-order`·`pr-queue` 는 다른 검사(risk-gate
의 "다른 검사 실패", 병합 훅의 검사 실패 판정)에서 뺀다 — 순서 문제는 위 병합 직전 확인이 정확한 메시지로 막는다.

### PR 을 나누는 기준과 자동 병합(#437, #536)

1. 한 PR = 하위 작업 이슈 하나. 기능이 여럿인 개발은 `/harness:start` 에서 하위 작업으로 쪼갠다. DEV 가 둘 이상이거나
   SRS 와 개발이 함께면 섞임이라 나누자고 제안한다. 개발 PR 이 같은 DEV 의 Spec 을 같이 고치는 것, SRS 와 Spec 을
   함께 올리는 것은 섞임이 아니다. 개발 중 `src/` 변경이 기준(기본 1,000줄)을 넘으면 deliver 가 나누기를 묻는다(막지 않는다). 안 끝난 개발이어도 센다.
2. 안 끝난 개발은 PR 없이 브랜치에만 올린다. 하위 작업 하나가 080 에서 활성화된 뒤 그 PR 을 낸다.
3. 끝난 PR 은 GitHub 자동 병합으로 승인·검사가 끝나는 순간 합친다. **사람의 승인이 곧 병합 결정**이다.
4. 개발 PR 은 쌓지 않는다. 앞 PR 이 열려 있으면 브랜치에만 올리고, 병합되면 main 에서 다시 찍어 PR 을 낸다.
5. Spec PR 은 설계가 정해지면 병합한다. 이미 승인된 PR 에 더 고치려 하면 병합하고 새 PR 을 낸다.

`gh pr merge N --auto --squash` 는 서버가 필수 검사·승인을 기다리므로 훅이 검사 진행 중·앞 PR 대기·SRS 승인·위험도
판정을 건너뛰고 허용한다. 단 사람 병합 경로(`.github/human-merge-paths`)를 바꾼 PR 은 `--auto` 도 거부한다(사람이 GitHub 에서
병합하거나 자동 병합을 켠다). 남의 PR 금지는 그대로 적용되고, `--admin`(보호 규칙 우회)은 어떤 PR 에도 거부한다.
`/harness:deliver` 는 저장소가 자동 병합을 허용하고 base 에 필수 검사가 있을 때만 걸며(없으면 바로 병합돼 검사를 건너뛰므로
걸지 않는다), 사람이 병합해야 하는 경로를 바꾼 PR 에는 걸지 않는다.

### 예외: 에이전트가 자기 PR 을 병합해도 되는 경우

기본은 그대로 사람이 병합한다. 다만 아래 네 조건을 모두 만족하면 에이전트가
자신이 연 PR 을 스스로 병합해도 된다.

1. **바뀐 파일이 모두 허용 범위 안에 있다.** `README.md` 파일들과 `docs/`
   아래 파일들 — 단 `docs/ssot/` 와 `docs/spec/` 아래는 제외한다.
2. **다음은 언제나 사람이 병합한다.** 아래 경로가 하나라도 바뀌었으면 조건 1
   을 만족해도 이 예외를 적용하지 않는다: `docs/ssot/**`, `docs/spec/**`,
   `CLAUDE.md`, `.claude/**`, `rules/**`, `templates/**`, `conventions/**`,
   `audit/**`, `env/**`, `src/**`, `scripts/**`, `.github/**`, `.githooks/**`,
   `plugins/**`, `checker/**`, 그 밖의 모든 코드 파일.
3. **PR 의 모든 검사가 통과했다.** `gh pr checks` 로 확인했을 때 대기 중인
   검사 없이 전부 성공이고, PR 이 충돌 없이 병합 가능한 상태다.
4. **병합 방식은 squash 다(`gh pr merge --squash`).** 병합한 뒤에는 PR
   링크를 사용자에게 보고한다.

`.github/human-merge-paths` 에 적힌 경로(이 저장소는 `plugins/`, `checker/`,
`.github/`)를 바꾼 PR 은 훅이 강제한다. Claude 의 `gh pr merge` 는 거부되고,
사람이 GitHub 화면의 Merge 버튼으로 병합한다. PR 이 열리거나 병합되면
이슈와 Teams 로 소유자에게 알린다. 소유자가 아닌 사람이 올린 PR 은 바꾼
경로와 무관하게 알린다(#104).

대상 PR 의 검사(`gh pr checks`)가 실패했거나 아직 진행 중이면 Claude 의 `gh pr merge` 를
훅이 거부하고, 검사 상태를 확인하지 못해도 거부한다. 사람의 웹 Merge 버튼은 막지 못한다(#120).

조건 중 하나라도 애매하면 이 예외를 적용하지 않고 사람에게 맡긴다.

이 예외를 두는 이유는, 틀려도 동작에 영향이 없고 되돌리기 쉬운 문서만
위임하기 위해서다. 검사 통과만으로는 로직이나 요구사항과 실제로 맞는지까지
보장하지 못하므로, 코드와 기준이 되는 파일은 여전히 사람이 병합한다.

### 다른 계정이 만든 PR 은 읽기만 한다(#150)

작성자 계정이 지금 `gh` 로그인 계정과 다른 PR 은 읽기만 한다(`gh pr view`, `diff`,
`checks`, `checkout`). 내 작업이 그 PR 에 주는 영향(충돌, 같은 파일, 검사 결과 변화)만
사용자에게 알린다. 병합, 수정, 닫기, 코멘트, 리뷰, ready 전환, 그 PR 브랜치로의 push
(강제 포함), 리베이스는 하지 않는다. 계정 비교는 대소문자를 가리지 않는다.

예외로, 그 저장소의 admin 권한이 있는 계정은 남의 PR 도 제어할 수 있다.

훅(`pre-bash-git-guard.sh`)이 Claude 의 `gh pr merge|edit|close|reopen|comment|review|ready`
와 `DELIVER=1` 푸시를 막고, 작성자나 권한을 확인하지 못해도 거부한다(검사 불능). 사람이
웹이나 터미널에서 한 일은 훅이 못 막으므로 Actions(`pr-tamper-alert`)가 작성자가 아닌
계정의 push 와 리뷰 해제를 사후에 이슈·Teams 로 알린다(병합은 알리지 않는다). 무료 개인
계정이라 서버가 막지 못한다. 조직·유료 요금제로 옮기면 ruleset 으로 바꿀 자리다.

### 위험도에 따른 승인(#102)

PR 검사는 이름이 `pr-checks` 인 job 하나이고, 비밀정보·문서·SRS 승인·위험도·병합 순서가 그 안의 단계다(#412).
결과는 옛 이름(`gitleaks`·`doc-guard`·`ssot-approval`·`risk-gate`·`merge-order`) commit status 로도 달려 `gh pr checks` 와
훅이 이름으로 읽는다. 승인(리뷰)이 달리면 `pr-review` 가 승인 여부만 다시 판정하고, 병합 뒤 감시는 `main-checks` 가 한다.

Project Repository 에 `.github/risk-gate.yaml` 이 있으면 PR 마다 위험도를 판정한다. 바뀐 줄이
300 을 넘거나 파일이 10개를 넘을 때, 위험 경로(`docs/ssot/`, `rules/`, `.github/` 등과
`.github/human-merge-paths`)를 바꿀 때, 추가된 줄에 비밀값 모양이 있을 때, 다른 검사가
실패했거나 진행 중일 때 그 PR 은 위험하다. 위험하지 않은 PR 은 승인 없이 병합할 수 있고,
위험한 PR 은 `.github/ssot-approvers` 의 사람 가운데 **작성자가 아닌 사람이 PR 의 마지막
커밋에 Approve** 해야 한다. 승인이 없으면 PR 검사 `pr-checks` 가 빨간불이 되고(그 안의 risk-gate
단계가 실패하고 commit status `risk-gate` 도 빨갛다) 이유와 다음 할 일이 PR 코멘트에 남으며, Claude 의 `gh pr merge` 는 훅이 거부한다. 승인 없이 병합됐으면
병합 뒤 이슈가 열린다. 승인자 목록에 작성자 말고 사람이 없으면 위험한 PR 은 승인으로 풀 수
없으니 한 명 이상 적어 둔다.

기준은 `.github/risk-gate.yaml`(`max_changed_lines`, `max_changed_files`, `high_risk_paths`,
`secret_scan`, `require_checks_green`, `ai_review`, `size_exclude_paths`, `size_warn_only_paths`, `srs_split_hint`, `approvers_file`)에서 고친다.
`size_exclude_paths`(기본 비어 있음 = 모든 파일을 센다, #534)에 접두어(예 `src/`, `audit/`)를 적으면, 그 아래 파일은 줄·파일 수 합계에서
빼고 **남은 파일만으로** `max_changed_*` 를 판정한다. 남은 부분이 기준을 넘으면 승인 사유이고, 뺀 것까지 합쳐야 넘는 부분은 경고
(결과의 `notes`, PR 코멘트의 "참고(승인 필요 없음)")로만 낸다. 그래서 `src/` 와 Spec 을 같이 고쳐도 `src/` 줄은 승인 사유가 되지 않는다.
다른 기준(위험 경로·비밀값·AI 리뷰·다른 검사 실패)은 그대로다. 두 키를 함께 쓰면 `size_exclude_paths` 를 먼저 적용하고,
`size_warn_only_paths` 는 **센 파일**이 모두 그 아래일 때 남은 사유를 경고로 바꾼다.
`size_warn_only_paths`(기본 비어 있음, #436)에 접두어(예 `src/`)를 적으면, **센 파일**(`size_exclude_paths` 를 쓰면 그 아래를 뺀 나머지, 안 쓰면 바뀐 파일 전부)이
**모두** 그 아래인 PR 은 줄·파일 수가 기준을 넘어도 승인 사유가 아니라 경고(결과의 `notes`, PR 코멘트의 "참고(승인 필요 없음)")로만 낸다.
센 파일 중 하나라도 그 밖이면 크기도 지금처럼 승인 사유다. 두 키의 접두어는 `/` 로 끝낸다(`src/` — `src` 라고 적으면 `srcx/` 도 걸릴 수 있다). 비밀값·CR-009·AI 리뷰·다른 검사 실패는 소스만 바꿔도
그대로 승인 사유다.
`srs_split_hint`(기본 `true`)는 SRS 에 새 요구사항이 생겼는데 기존 요구사항을 넓힌 것처럼 보일 때
(상세 절의 다른 번호 언급, 범위 "하지 않는 것" 줄 변경, 제목 겹침) 근거를 위험 사유로 붙인다.
막는 기준이 아니라 승인자가 확인하게 하는 표시다. 이 파일은
기준 브랜치에서 읽으므로 고친 값은 병합된 뒤부터 적용되고, 파일을 지우면 게이트가 꺼진다.
**blueward-harness 저장소 자신은 승인자가 한 명뿐이라 아직 이 파일을 두지 않아 게이트가
꺼져 있다.**

`ai_review` 는 기본 `false` 다. 켜면 **위험한 PR 을 포함해 코드(`src/`)를 바꾼 PR** 에 Claude AI 리뷰(`ai-review`
검사, `.github/workflows/ai-review.yml`)가 돈다. 호출 워크플로의 `paths: ['src/**']` 가 문서·Spec 만 바꾼 PR 에는
검사를 띄우지 않고, `risk-gate.yaml` 의 `ai_review_paths`(기본 `[]` = 모든 PR 이 대상, scaffold 는 `[src/]`)가 같은
범위를 말해 그 PR 은 "AI 리뷰 결과 없음" 대기가 아니라 "대상 아님" 으로 통과한다(#411). 위험한 PR 은 AI 리뷰에 더해 승인자 Approve 도
필요하다(승인 판정은 그대로). 심각한 지적이 나오거나, 큰 PR 이라 일부만 봤거나, AI 리뷰를 돌리지
못하면(검사 불능·취소·시간 초과) 그 검사가 실패해 PR 이 위험으로 판정되고, risk-gate 사유가 이
경우들을 나눠 적는다(심각한 지적은 파일:줄과 요약까지). 켜려면 `claude setup-token` 으로 만든
토큰을 `gh secret set CLAUDE_CODE_OAUTH_TOKEN -R <owner/repo>` 로 등록하고 `ai_review` 를 `true`
로 바꾼다. 시크릿이 없으면 통과가 아니라 검사 불능이다.

단 **새로 들어온 줄에 비밀값 패턴이 실제로 보이는 PR 은 AI 리뷰를 돌리지 않는다** — diff 를 외부
AI 에 보내지 않기 위해서다. 대신 `ai-review` 를 "검사 불능 - 비밀값 의심" 으로 실패시켜 통과로 보이지
않게 하고, 승인자가 직접 확인한다. **값**은 어디에도 남지 않는다. 위치(파일:줄)는 risk-gate 사유처럼 job
로그에 남고, ai-review 코멘트·표식에는 패턴 이름만 적는다.
"변경이 너무 커서 비밀값 검사를 못 함" 은 이 예외가 아니다 — 큰 PR 은 계속 리뷰한다. 한계: 너무 커서 patch 가
없는 파일(unscanned)은 비밀값 검사를 못 했으므로 그 안의 비밀값은 AI 리뷰로 나갈 수 있다.
엔진이 옛 판이라 비밀값 확인 결과(`secret_found`)를 내지 않으면 리뷰를 돌리지 않고 "검사 불능" 으로 실패한다.
리뷰 결과는 `github-actions` 봇이 쓴 코멘트만 읽고, 큰 PR 의 "전체를 봤다" 는 AI 가 스스로 적은 말이라 확인되지 않는다.

## 스킬 없이 직접 해도 되는 것

다음은 스킬을 거치지 않고 직접 수행해도 된다.

- 파일 읽기
- 로컬에서의 확인 (예: `git status`, `git log` 같은 조회성 명령)
- 브랜치 확인

이런 작업은 저장소 상태를 바꾸지 않으므로 규칙에 어긋날 여지가 없다.

## 스킬을 반드시 거쳐야 하는 것

다음은 반드시 정해진 스킬을 거친다.

| 작업 | 스킬 |
|---|---|
| 브랜치 생성 | `/harness:start` |
| 커밋 | `/harness:deliver` |
| 푸시 | `/harness:deliver` |
| PR 생성 | `/harness:deliver` |
| 이슈 등록 | `/harness:start`, `/harness:wrapup` |
| 릴리즈 발행 | `/release` (아래 참조) |

`/harness:srs` 와 `/harness:spec` 은 시작할 때 브랜치를 확인한다. main 이면 `/harness:start` 절차를 대신 수행하고,
이전 작업 브랜치면 이어 쓸지 새로 시작할지 묻는다. 미커밋 변경이 있으면 `/harness:deliver` 로 먼저 정리할지 묻는다.

이 작업들은 저장소의 이력과 다른 참여자의 작업에 직접 영향을 주기 때문에,
정해진 절차를 거쳐 형식과 순서를 지키게 한다.

`/release` 스킬이 없는 저장소라면, 아직 릴리즈할 것이 없어서이거나 이
harness 플러그인이 아직 그 스킬을 담고 있지 않기 때문이다. 그런 저장소에서는
릴리즈 발행이 정상 경로가 없는 작업이므로 시도하지 않는다. `/release` 가
필요해지면 팀이 쓰는 다른 저장소나 배포에서 가져와 이 저장소에 추가한다.

## 규칙을 바꾸고 싶을 때

`rules/` 아래 문서를 고치는 것도 하나의 변경이다. 다른 변경과 똑같이 이슈를
먼저 만들고 PR 로 병합한다. 규칙이 본인 판단만으로 조용히 바뀌면 다른
참여자가 언제 무엇이 바뀌었는지 알기 어렵다.

## 훅이 막았을 때

훅이 어떤 동작을 거부했다면 그 동작을 우회하지 않고 사람에게 돌려준다.
`--no-verify` 로 git hook 을 건너뛰거나, harness 플러그인의 push 가드 훅
(`pre-bash-git-guard.sh`)의 거부를 피해 가는 다른 명령을 찾지 않는다. 거부에는
대개 다음에 무엇을 하면 되는지가 함께 안내되어 있으므로, 그 안내를 따르거나
안내가 실제 상황과 맞지 않으면 사람에게 상황을 보고하고 판단을 맡긴다.

훅·스킬 결과에 사람이 직접 할 일(플러그인 갱신과 `/reload-plugins`, 도구 설치, Claude Code 재시작,
표식 파일 정리, GitHub 에서 사람이 하는 병합·승인)이 있으면 Claude 는 답 맨 앞에
`🚨 직접 해 주세요:` 로 따로 적는다(표·긴 설명 속에 섞지 않는다). 훅 메시지의 같은 표시(#505)는
사람만 할 수 있는 일에만 붙으므로, Claude 가 스스로 할 수 있는 일에는 붙이지 않는다.

커밋 전 비밀정보 검사(`gitleaks`, #170)가 막았을 때도 같다. Claude 는 `HARNESS_SKIP_SECRET_SCAN` 을
스스로 켜지 않는다 — 환경에 설정하는 것도, `.claude/settings.json` 의 `env` 나 환경 파일(`.env`,
셸 프로필)에 적는 것도, 명령 앞에 붙이는 것도 하지 않는다. 검사를 건너뛸지는 사람만 정한다. "비밀값
발견" 이면 해당 줄을 빼고, 진짜 비밀값이면 폐기·교체가 필요하다고 사람에게 알린다. 오탐이라도
`.gitleaks.toml` 의 `[allowlist]` 는 사람이 정하므로 Claude 가 스스로 추가하지 않는다. gitleaks 가 없거나
오류로 끝난 "검사 불능" 이면 멈추고 사람에게 설치나 원인 해결을 요청한다.

**예외는 원격을 처음 연결할 때 main 을 올리는 최초 1회의 푸시뿐이다.**
그 시점에는 저장소에 아무 이력도 없어 PR 을 열 대상 자체가 없으므로,
저장소의 README 가 안내하는 "원격을 연결할 때 할 일" 절차대로 그 1회에 한해
훅을 우회한다. 그 이후의 모든 main 갱신은 예외 없이 PR 로만 이루어진다.
