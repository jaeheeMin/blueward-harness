# 커밋과 PR 규칙

## 커밋 메시지 형식

```
<type>(<scope>): <description>
```

`scope` 는 선택이다. 생략해도 된다.

**제목은 명사형으로 끝낸다.** 활용형 서술어로 끝내지 않는다.

옳은 예시:
- `feat: 온보딩 문서 추가`
- `fix(auth): 로그인 실패 시 안내 메시지 수정`

틀린 예시:
- `feat: 온보딩 문서를 추가한다`
- `fix: 로그인 실패 시 안내 메시지를 고친다`

본문에는 `Refs #{이슈번호}` 를 넣어 이슈와 연결한다.

`git add` 와 `git commit` 은 한 명령으로 묶지 않고 따로 실행한다(커밋 전 비밀정보 검사가 staged 를
보기 때문, #170). `git commit -a` 도 같은 이유로 쓰지 않는다.

## 하나의 커밋에는 하나의 의미만

성격이 다른 변경을 한 커밋에 섞지 않는다. 기능 추가와 오탈자 수정처럼 서로
관련 없는 변경이라면 커밋을 나눈다. 나중에 특정 변경만 되돌리거나 리뷰할 때
커밋이 섞여 있으면 그 작업이 어려워지기 때문이다.

## 푸시 전에는 항상 fetch 와 rebase

푸시하기 전에 기준 브랜치를 `fetch` 로 가져오고 `rebase` 로 자신의 작업을 그
위에 얹는다. 다른 사람의 변경을 확인하지 않고 푸시하면 뒤늦게 충돌을
발견하게 된다.

## `--force` 금지, `--force-with-lease` 만 허용

리베이스로 이력이 바뀌어 강제 푸시가 필요할 때는 `--force-with-lease` 를
쓴다. `--force` 는 원격에 먼저 올라온 다른 사람의 커밋을 확인 없이 덮어쓸 수
있어서 쓰지 않는다.

`git push --force` 는 harness 플러그인의 push 가드 훅(`pre-bash-git-guard.sh`)이
항상 거부한다. 이 거부는 아래에서 설명하는 `DELIVER=1` 선언과 무관하게
적용된다. 되돌릴 수 없는 동작이기 때문에 어떤 선언으로도 통과시키지 않는다.

## PR 제목과 본문

PR 제목은 커밋 제목과 같은 형식을 쓴다.

PR 본문은 다음 절로 구성한다.

- `## Summary` : 한두 문장으로 이번 변경을 요약한다
- `## Changes` : 변경 내용을 목록으로 적는다
- `## Review notes` : 리뷰어가 별도로 봐 줘야 할 것이 있을 때만 덧붙인다

본문 끝에는 `Closes #{이슈번호}` 를 넣어 PR 이 병합되면 이슈가 자동으로
닫히도록 한다.

PR 에는 항상 담당자(assignee)를 지정한다. 담당자가 없는 PR 은 누가 리뷰를
맡아야 하는지 알 수 없다.

## `/harness:deliver` 가 이 절차 전체를 수행한다

커밋, 기준 브랜치와의 동기화, 푸시, PR 생성까지 이 문서에 적은 절차 전체를
수행하는 정상 경로는 `/harness:deliver` 다.

Claude Code 안에서 스킬을 거치지 않고 직접 실행하는 `git push` 는 harness
플러그인의 push 가드 훅(`pre-bash-git-guard.sh`)이 거부한다. `/harness:deliver` 는
자신이 이 절차를 따르고 있다는 것을 명령 앞에 `DELIVER=1` 을 붙여 선언하고,
그 선언이 있어야 맨손 `git push` 거부를 통과한다. **이 선언이 통과시키는
것은 그 거부뿐이다.** `--force` 와 main 커밋 거부는 `DELIVER=1` 이 있어도
통과되지 않는다.
